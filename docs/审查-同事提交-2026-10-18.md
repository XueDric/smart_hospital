```ts
if (this.code === ErrorCode.NETWORK_ERROR) {
```

观察项（不改，记账）：

- `SessionStore.beginBooking` / `clearPending` 用了 `check(prefs.edit()…commit())`：**`commit()` 返回 false 会抛 `IllegalStateException`**，与本文件其它路径"失败降级、绝不崩"的风格不一致。落盘失败概率极低，但真发生就是一次崩溃而不是提示。
- `DoctorRepository.login()` 要求 `role == "doctor" && doctorId > 0` 才认为登录成功，否则后续 403。服务端 `POST /auth/login` 目前对医生**不返回 `doctor_id`**（只有 `/auth/me` 有），靠 `ContractParser` 的 `optLong` 回退 `ref_id` 兜住 —— 这层兜底是隐式的，服务端若哪天改 `ref_id` 语义就会静默错位。
- `values-night/*` 与 `ThemeController` 并存：`跟随系统` 走 `values-night`、手动选择走 `ThemeController` 覆盖 —— 目前没冲突，但等于两套机制各自判断明暗，建议后续统一到一个入口。

## 三、3 个真缺陷（`de47f6f` 带入，均已在本次修复）

三个都是**客户端与服务端的字段契约漂移**，共同点是：安卓用 `JSONObject.getXxx()` 读**必填**字段，而服务端从没承诺过那个字段。

### A1 · 医生队列整页崩成"响应内容不完整"（P1）

- 现象：医生账号登入后点「刷新队列」，红条 `响应内容不完整，请重新读取并联系维护人员`，队列永远空。
- 文案来源：`android-patient/app/src/main/java/com/smart/hospital/patient/DoctorActivity.kt:194` 的 `is org.json.JSONException -> "响应内容不完整，请重新读取并联系维护人员"`。
- 根因：`android-patient/app/src/main/java/com/smart/hospital/patient/data/ContractParser.kt:24` 用 `o.getLong("schedule_id")` 解析 `Appointment`，而 `GET /api/v1/doctor/visits` 的 `items` 只有
  `appointment_id, patient_id, doctor_id, department_id, visit_date, period, seq_no, status, status_label, arrived_at, started_at, finished_at, previsit_ready, record_id, record_status, record_filled, record_total, patient_name, patient_gender`
  —— **没有 `schedule_id`**（患者端 `/api/v1/appointments` 的 `data.appointments[]` 才有）。
- 修法：`schedule_id` 改可选（`o.optLong("schedule_id")`）。医生侧的队列项本来就不需要它。

### A2 · 病历编辑器打不开（P1）

- 现象：点「打开病历」立刻红条，同样那句"响应内容不完整"。
- 根因：`ContractParser.record()`（`ContractParser.kt:44-58`）用 `o.get("version")` 必填，而 `GET /api/v1/doctor/visits/:id/record` 的响应字段是
  `id, appointment_id, patient_id, doctor_id, status, locked, filled, total_sections, complete, updated_by, created_at, updated_at, missing_required, sections, patient_name, patient_gender`
  —— **没有 `version`**；服务端 `server/src/http_p4.cj:39` 的 `medicalRecordJson()` 从头到尾没输出过它。
- 修法（服务端补字段，而不是让客户端瞎猜）：`medicalRecordJson()` 在 `updated_at` 之后补 `o.put("version", JsonInt(m.updatedAt))`，并在代码里写明"版本号就是乐观锁令牌"。

### A3 · 乐观锁被静默绕过（P1，最隐蔽）

- 现象：并发/多窗口编辑同一份病历时，后写的一方**不会**被服务端拒绝，前者内容被覆盖且无任何提示。
- 根因：服务端读的字段是 `expected_updated_at`（`server/src/http_p4.cj:357` `emrExpectedUpdatedAt(ctx)`，缺省/0 表示不校验），安卓发的是 `expected_version`（`DoctorRepository.kt:67-69`）——**服务端根本不读这个键**，等于每次写都是"无条件覆盖"。鸿蒙侧是对的（`DoctorRepository.ets:127` 的 `expected_updated_at`）。
- 修法：安卓改发 `expected_updated_at`。同时把客户端的版本判断从"必须 +1"改成"必须递增"（`DoctorActivity.kt:409` `saved.version <= submitted.version` 视为失败、`:463` `locked.version > saved.version` 视为锁定成功）。

### 三处修复之外，服务端补的一条硬保证

安卓把 `version` 当"每次写必然 +1 的计数器"用，但服务端原来的 `updated_at` 是**秒级时间戳**，同一秒内连写两次会原地不动。为此在 `server/src/domain_emr.cj` 加：

```cangjie
private func emrNextStamp(prev: Int64, now: Int64): Int64 {
    if (now > prev) { return now }
    return prev + 1
}
```

`saveDraft` / `lock` / `reopen` 三处写库都改成 `emrNextStamp(...)`：时间戳前进了就用时间戳，没有前进就 `+1`。这样"版本号严格递增"与"`updated_at` 是修改时间"两个语义同时成立。

**实测**：同一秒内连续两次 `PUT /record`，`version` 从 `1792324272` → `1792324273`，严格递增成立。

## 六、不修但记账

1. **服务端没有就诊日期硬门槛**：客户端两端都加了守卫，但直接调接口仍能把未来日期的号推进到 `arrived/visiting/done`。要修得动 `server/src/domain_emr.cj` 的状态机，且 `server/tests` 里有大量固定日期夹具（`acceptance.cj` 的 9001/9002 排班写的是 2026-12-24），需要同步改造测试夹具，属于独立一轮的活。
2. **`SessionStore` 的 `check(commit())`**：`commit()` 失败会抛 `IllegalStateException`（见 §二观察项），建议改成与其它路径一致的"返回布尔 + 提示"。
3. **安卓没有契约层测试**：A1/A2/A3 这种"字段名一错就整页崩"的问题，靠人工点一遍才发现。建议把三个接口的真实响应做成金样本（`test/resources/*.json`），加 3 个纯 JVM 单测（不需要模拟器）断言 `ContractParser` 能解析 —— 这是成本最低的防复发手段。
4. **服务端字段契约没有单一出处**：`/doctor/visits` 与 `/appointments` 都返回"预约"，字段集不同且没有文档。建议在 `contract/` 下补这两个响应的 schema（仓库已有 `contract/schema` 目录，24 个文件），让两端都有据可依。
