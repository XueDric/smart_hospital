## 三、3 个真缺陷（`de47f6f` 带入，均已在本次修复）

三个都是**客户端与服务端的字段契约漂移**，共同点是：安卓用 `JSONObject.getXxx()` 读**必填**字段，而服务端从没承诺过那个字段。

### A1 · 医生队列整页崩成"响应内容不完整"（P1）

- 现象：医生账号登入后点「刷新队列」，红条 `响应内容不完整，请重新读取并联系维护人员`，队列永远空。
- 文案来源：`android-patient/app/src/main/java/com/smart/hospital/patient/DoctorActivity.kt:194` 的 `is org.json.JSONException -> "响应内容不完整，请重新读取并联系维护人员"`。
- 根因：`android-patient/app/src/main/java/com/smart/hospital/patient/data/ContractParser.kt:24` 用 `o.getLong("schedule_id")` 解析 `Appointment`，而 `GET /api/v1/doctor/visits` 的 `items` 只有
  `appointment_id, patient_id, doctor_id, department_id, visit_date, period, seq_no, status, status_label, arrived_at, started_at, finished_at, previsit_ready, record_id, record_status, record_filled, record_total, patient_name, patient_gender`
  —— **没有 `schedule_id`**（患者端 `/api/v1/appointments` 的 `data.appointments[]` 才有）。
- 修法：`schedule_id` 改可选（`o.optLong("schedule_id")`）。医生侧的队列项本来就不需要它。

### A2 · 病历编辑器打不开（P1）

- 现象：点「打开病历」立刻红条，同样那句"响应内容不完整"。
- 根因：`ContractParser.record()`（`ContractParser.kt:44-58`）用 `o.get("version")` 必填，而 `GET /api/v1/doctor/visits/:id/record` 的响应字段是
  `id, appointment_id, patient_id, doctor_id, status, locked, filled, total_sections, complete, updated_by, created_at, updated_at, missing_required, sections, patient_name, patient_gender`
  —— **没有 `version`**；服务端 `server/src/http_p4.cj:39` 的 `medicalRecordJson()` 从头到尾没输出过它。
- 修法（服务端补字段，而不是让客户端瞎猜）：`medicalRecordJson()` 在 `updated_at` 之后补 `o.put("version", JsonInt(m.updatedAt))`，并在代码里写明"版本号就是乐观锁令牌"。

### A3 · 乐观锁被静默绕过（P1，最隐蔽）

- 现象：并发/多窗口编辑同一份病历时，后写的一方**不会**被服务端拒绝，前者内容被覆盖且无任何提示。
- 根因：服务端读的字段是 `expected_updated_at`（`server/src/http_p4.cj:357` `emrExpectedUpdatedAt(ctx)`，缺省/0 表示不校验），安卓发的是 `expected_version`（`DoctorRepository.kt:67-69`）——**服务端根本不读这个键**，等于每次写都是"无条件覆盖"。鸿蒙侧是对的（`DoctorRepository.ets:127` 的 `expected_updated_at`）。
- 修法：安卓改发 `expected_updated_at`。同时把客户端的版本判断从"必须 +1"改成"必须递增"（`DoctorActivity.kt:409` `saved.version <= submitted.version` 视为失败、`:463` `locked.version > saved.version` 视为锁定成功）。

### 三处修复之外，服务端补的一条硬保证

安卓把 `version` 当"每次写必然 +1 的计数器"用，但服务端原来的 `updated_at` 是**秒级时间戳**，同一秒内连写两次会原地不动。为此在 `server/src/domain_emr.cj` 加：

```cangjie
private func emrNextStamp(prev: Int64, now: Int64): Int64 {
    if (now > prev) { return now }
    return prev + 1
}
```

`saveDraft` / `lock` / `reopen` 三处写库都改成 `emrNextStamp(...)`：时间戳前进了就用时间戳，没有前进就 `+1`。这样"版本号严格递增"与"`updated_at` 是修改时间"两个语义同时成立。

**实测**：同一秒内连续两次 `PUT /record`，`version` 从 `1792324272` → `1792324273`，严格递增成立。

## 七、记账项的处置（2026-10-18 夜，四条全部落地）

### 7.1 服务端补就诊日期硬门槛（原记账项 1）

**为什么必须放服务端**：客户端两端的守卫都能被绕过（改包、直接打接口）。这不是"防误操作"，是数据正确性问题。

**设计取舍（重要）**：只拒绝**未来**日期，**不要求"必须等于今天"** —— 跨零点接诊（23:50 到院、00:10 完成）和"昨天没处理完、今早补录"都是真实业务，卡"等于今天"会把它们一起打死。

**实现分两层**，这是为了让 700+ 条领域断言保持确定性：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 领域层 | `server/src/domain_emr.cj` `public func visitIsFuture(visitDate: String, now: Int64): Bool` | 纯计算：`visitDate > hDateStringOf(now)`（`YYYY-MM-DD` 字符串比较，Asia/Shanghai）。**不读墙上时钟** |
| HTTP 边界 | `server/src/http_p4.cj` `p4RequireVisitNotFuture(visit, appointmentId, doctorId, now, what)` | 取 `hNowEpoch()`，查单、判日期、抛 `VISIT_DATE_FUTURE` |

接线三处：`arrive` / `waiting` / `start`。**`finish` 与 `no-show` 故意不拦**（完成可能跨零点，爽约是事后动作）。

```cangjie
// server/src/domain_emr.cj
public func visitIsFuture(visitDate: String, now: Int64): Bool {
    if (visitDate.size == 0) { return false }
    return visitDate > hDateStringOf(now)
}
```

错误码登记（`server/src/http_common.cj`）：`VISIT_DATE_FUTURE` ⇒ **409**。⚠ 本轮踩到：**新错误码不登记会落到兜底 500**，首跑实测就是 `HTTP 500 code=VISIT_DATE_FUTURE` —— 正常的业务拒绝被报成服务端故障。

**断言**：
- 领域层 `server/src/acceptance_p4.cj` AC-P4-8 ⑧ 段 4 条：今天的号放行 / `"2000-01-01"` 放行 / `"2999-12-31"` 被拒 / `""` 不拦。
- HTTP 层 `server/tests/visit-timeline-check.ps1` 新增 `[5b]` 段 6 条：7 天后的号 `arrive`/`waiting`/`start` 都 ⇒ 409、错误信息同时含就诊日与今天、三次被拒后库里仍 `booked` 且 `arrived_at=0`。

**测试夹具改造**（否则门槛一上线就是"自己把自己红掉"）：
- `server/tests/emr-check.ps1`：`'2026-12-25'` → 当天（`$emrToday`，8 处）。
- `server/tests/visit-timeline-check.ps1`：`'2026-12-30'` → 当天（`$vtlToday`，7 处）；新增 707010（7 天后，**初始 `cancelled`** —— 否则会排进队列把三条顺序断言打红，`[5b]` 开头再翻成 `booked`）。

结果：`accept` **786 项 / 0 失败**（原 782，+4）；`visit-timeline-check` **53 项全 PASS**（原 46）；`emr-check` **73 项全 PASS**。

### 7.2 安卓存储失败不再抛异常（原记账项 2）

`android-patient/.../data/SessionStore.kt` 里 7 处 `check(editor.commit())` 全部改为 `persist(editor, what)`：

```kotlin
private fun persist(editor: SharedPreferences.Editor, what: String): Boolean {
    val ok = try { editor.commit() } catch (e: Exception) {
        Log.w(TAG, "写本地存储抛异常（$what）：${e.message}")
        false
    }
    if (!ok) Log.w(TAG, "写本地存储失败（$what）：进程内仍可用，重启后可能丢失")
    return ok
}
```

**理由**：`commit()` 返回 false 时 SharedPreferences 的**内存值已经改好**，本次流程照样走得通，只是没落盘。抛 `IllegalStateException` 等于把"下次冷启动可能要重试"升级成"用户现在就闪退"。

### 7.4 统一明暗机制（原记账项 4）

**结论：两套机制不冲突，但"判定入口"必须唯一。** 现场核对：

- 全仓除 `HarmonyUi.kt` 外**没有任何**地方直接读 `R.color.*`（grep 只有一条注释），而 `HarmonyUi.palette()` 一律先过 `ThemeController.attachContext()` —— 它把 `uiMode` 强制成解析结果，因此 `values-night/colors.xml` 只在那时被资源系统选中。
- 真正的重复是"暗色与否"这段判定写了两遍（`attachContext` 与 `refresh` 各算一次），以及两份 `themes.xml` 的窗口属性悄悄分叉（`values/` 缺 `windowBackground` 与 `windowLightNavigationBar`，导致浅色下的启动首帧是纯白而不是 `#F3F8F7`）。

处置：
- 新增 `ThemeController.isNight(base: Context): Boolean` 作为**唯一判定入口**，`attachContext()` 与 `refresh()` 都改用它（`val dark = isNight(activity)`）；状态栏/导航栏图标明暗与页面配色从此不可能分叉。
- 两份 `themes.xml` 对齐窗口属性（浅色补 `windowBackground=@color/background`、`windowLightNavigationBar=true`），并在文件头写明"**选择权在 `ThemeController`，`values-night/` 只提供颜色值**，不要引入第三套机制"。
- 两份 `colors.xml` 加注：键名必须一致、由 `HarmonyUi.palette()` 按名读取。

**为什么不必推倒重来**：`values-night` 是"颜色值的容器"，`ThemeController` 是"选哪一组的开关"，两者是分工不是竞争；推倒重写成 `AppCompatDelegate.setDefaultNightMode` 会牵动 Activity 重建、`ThemeShape` 的逐视图重着色逻辑，收益不抵风险。
