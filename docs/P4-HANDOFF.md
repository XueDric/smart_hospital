# P4 · 电子病历 + 运营看板 —— 交付说明

> **一句话**：把 P2 的预问诊问诊单接进**七段式电子病历**（草稿 → 锁定，锁定后不可改），
> 给医生一张**接诊队列**（状态机 + "完成就诊前必须已锁定病历"），
> 并给管理员一块**只出聚合、绝不出明细**的运营看板。
>
> ⚠ **P4 顺带改了一处架构**：`medical_record` **移出内存 Store**，改直接 SQL
> （ADR-0001 **rev.6**）。理由见 §二 —— 那是本阶段最要紧的一件事。

## 一、交付内容

### 数据层

| 文件 | 内容 |
| --- | --- |
| `src/domain_emr.cj` | 七段式病历模型 + `MedicalRecordRepo`（**直接 SQL**）+ 接诊状态机 `VisitRepo` |

### 接口层（`src/http_p4.cj`，11 个端点）

```

POST /api/v1/doctor/visits/:id/finish           完成就诊（★ 要求病历已锁定）

POST /api/v1/doctor/visits/:id/record/lock      提交锁定（校验必填段）
POST /api/v1/doctor/visits/:id/record/reopen    解锁（**仅管理员**）
GET  /api/v1/medical-records                    我的医疗档案（列表，无正文）
GET  /api/v1/medical-records/:appointmentId      某次就诊的病历（患者只读自己的）
```

| --- | --- | --- | --- |

## 二、★★ 架构改动：`medical_record` 移出内存 Store（ADR-0001 rev.6）

这是 P4 落地时**发现的问题**，不是预设的任务。两条理由：

### 理由 ① 本仓自己已经为同类数据判过一次（P2 的先例）

P2 引入 `previsit_session` 时**特意**把它排除在内存 Store 之外，原话：

> ★ 预问诊表**不属内存 Store 负责的表**（**它是医疗数据，必须立刻持久化**，
>   不能进"整表替换"范式）

而 `medical_record` 装的是**诊断与处理意见** —— 比问诊单**更**典型的医疗数据。
同一类数据两套处置，正是本项目反复点名的病。

### 理由 ② 内存 Store 在**生产路径上从未刷盘**（已核实）

```
flushToMysql() 的全部调用点：
  acceptance.cj:483   ← 只有测试
```

`main.cj` / `http_app.cj` **完全没有引用 `MemStore`**。
⇒ 若病历走内存 Store，"医生写病历"的实际效果是**只写进程内存、永不落库**。

> 📌 对科室/排班这类"可重新配置"的数据，这是**待补的工程债**；
>   对病历，它是**数据丢失**。不是一个量级。

### 处置

| 项 | rev.5 | rev.6 |
| --- | --- | --- |
| `MEM_TABLES` | 4 张 | **3 张**（科室/医生/患者） |
| 病历写入 | 内存 + 整表替换刷盘 | **直接 SQL**，逐条 upsert |
| 删除风险 | 一次刷盘 `DELETE FROM medical_record` 全表重写 | **不存在整表删除** |
| 断言 | — | `!MEM_TABLES.contains(TABLE_MEDICAL_RECORD)`（selftest + 派生式 AC-4） |

⚠ **当时的边界**（现已由 rev.7 解决）：`department` / `doctor` / `patient` 当时**仍在
内存 Store 里** —— 它们同样"生产不刷盘"，但处置它们属**另一项决策**，故当时没有顺手改。
★ 后来专门做了那项决策：**rev.7 把内存 Store 整体拆除**（见下面「五之三」）。

## 三、三条刻意的设计选择（都写在代码注释里）

| 选择 | 理由 |
| --- | --- |
| **锁定即不可改**，`lock` 用**条件 UPDATE**（`WHERE status='draft'`） | "先查再写"在并发下会双写成功；条件 UPDATE 的**影响行数**就是判据（与号源扣减同一手法） |
| **完成就诊前必须已锁定病历**，该前置条件写在**同一条 UPDATE 的 `WHERE` 里** | 否则"先查病历再改状态"在并发下会漏 —— 判据与写入必须是同一个原子动作 |
| **患者归属只从 `appointment` 派生**（先读挂号单再插病历），不接受请求体传入 | 请求体里的 `patient_id` 是最容易被篡改的字段；派生后"病历的 patient_id"与"挂号单的 patient_id"**不可能不一致** |

另：**必填段只设「诊断」与「处理意见」**（七段不设全必填）——
真实门诊里既往史/过敏史允许写"无"或留空，但**没有诊断的病历不是病历**；
把七段全必填会逼医生乱填。该策略由 `emrSections()` 单一来源给出，测试直接钉它。

## 四、★★ 看板的隐私红线（机制性，不是"记得别写"）

看板是**跨患者聚合**，是隐私最容易漏的地方。立的四条规矩：

1. 所有查询只允许 `COUNT(*)` / `SUM(...)` / 分组键；
2. 分组键只允许 `department.name` 与 `visit_date`（都不是个人数据）；
3. 响应**不含任何** `patient_id` / `doctor_id` / `phone` / `name`；
4. 三条由验收测试**逐字段**钉住（把响应当字符串搜这些键，一个都不许有）。

### ⚠ 一个刻意的遗漏（写下来免得将来有人"补齐"）

看板**没有**"按患者年龄/性别分布"这类指标。它们看起来是聚合，
但**在小科室里等价于个人识别**：某科室当天只有 1 个患者时，
"60 岁以上 1 人"就等于说出了他/她的年龄。
📌 这是"k-匿名"的朴素版本 —— 在没有明确的 k 阈值之前，不提供这类维度。

### 分诊统计表为什么**不含**主诉原文

`triage_stat` **只有**：时间、结论码、是否危急、科室名、是否截断、来源标记。
**没有** `patient_id` / 主诉原文 / 任何联系方式。

分诊是"还没挂号的人"在用的入口，输入是**患者自己写的一句话**（最敏感的自由文本）。
一旦落库，它就成了"一份没有病历的病情记录"，而看板只需要**计数**。
⇒ 按"只存得出指标所必需的最小集合"建表。
📌 不是"存了再脱敏"，而是**根本不存** —— 并且 `TriageStatRepo.record()` 的
签名里**没有**主诉参数，所以"想记主诉"在**类型层面**做不到。

## 五、本轮踩到并修掉的真问题

### 🔴 ① `INSERT ... SELECT` 在本仓（含基线）**从未被使用过**，我用它必失败

`saveDraft` 第一版写成 `INSERT INTO medical_record ... SELECT id, patient_id, ... FROM appointment`，
想让**数据库**把 `patient_id` 带过来（看起来更"原子"）。
结果仓颉侧**必失败**，而原因几乎看不到：

- 异常是 `SqlException: errorCode: 0` —— **驱动把 MySQL 的报错文本吞了**（`message` 是空串）；
- 同一条 SQL 用 `mariadb` 客户端**手工重放完全成功**。

定位后才明白：全仓扫过（**含 `baseline/`**）→ `INSERT ... SELECT` **零处使用**，
驱动的 `prepare_statement_client.getOrBuildSql()` 那条路径没被验证过。

⇒ 改为「先读 `appointment` + 纯 `INSERT`」。**那个不变量没有变**：
`patient_id` 仍然来自挂号单、仍然不信任调用方。

> 📌 教训：**不要在一个项目里第一次使用某条 SQL 形态** ——
> 尤其当失败只给空消息时。用项目已经跑熟的形态，同样能达到目的。

### 🔴 ② 四个端点全返回 500：新错误码**没注册进 `apiErrorSpec`**

`EMR_NOT_FOUND` / `EMR_LOCKED` / `EMR_NOT_LOCKED` / `VISIT_BAD_STATE` 我用了，
但没登记 ⇒ 落到兜底 `(500, "服务器内部错误")`。
于是"病历已锁定，不能改"这种**正常的业务拒绝**被报成了服务端故障。

⚠ 而**纯逻辑层的 accept 测试抓不到它**（它直接调仓储、不经过 HTTP 映射）——
这一条是**端到端脚本**抓出来的。
⇒ 教训：新增错误码必须同时补 `apiErrorSpec`，且必须有**走 HTTP 的**用例。

### 🟠 ③ 测试 fixture 连撞四次 `Duplicate entry` —— 而我前三次都在"改 id"（治症）

`hSeedTriageDept` 是**纯 `INSERT`**，而我在**同一个 criterion 内**用同一个 `seedId`
调它多次（"同一医生名下多张单"正是要测的形态）⇒ 第二次插入同一 `deptId` 必撞主键。

我先改了三轮 id 前缀（科室/医生/排班各分命名空间），**都没解决** ——
因为根因不是"id 撞车"，是**"我不该插第二次"**（幂等性问题）。
最终修法：fixture **先清后插**，且**只清自己会重复写的那三张表**
（我第一版把 `appointment` 也清了 ⇒ 队列长度变 0，又是一次"清理范围过大"）。

> 📌 教训：`Duplicate entry` 出现时，先问"**是不是我不该插第二次**"，
> 而不是急着换 id。后者只是把碰撞推到更远。

### 🟠 ④ 我自己的验证脚本给了**假红**

- 复用既有的 `13800000001` 当患者账号 —— 它绑的是 `patient_id=1`，
  而夹具用 700001 ⇒ "患者读自己的病历"全 404（**不是权限问题，是看的不是同一个人**）；
- 预问诊 `session_id` 写了 **67 字符**，而列是 `varchar(64)` ⇒ INSERT 静默被拒
  （内联拼 SQL 时 PowerShell 又把引号弄坏了）⇒ 预填全空。

> 📌 教训：**夹具必须自建并绑定自己的实体**，不能借用别人的账号；
> 夹具自己也要有**形状约束**（这里是一条列长度）。

### 🟠 ⑤ `edit` 工具重写 `.ps1` 会**丢掉 BOM** ⇒ 假语法错

本仓铁律"所有 `.ps1` 必须 UTF-8 with BOM"。BOM 一丢，PowerShell 5.1 按 ANSI 读中文
⇒ 满屏"意外的标记"、中文变乱码 —— 看起来像我把文件写坏了，其实是编码。
已把"改完 .ps1 立刻验 BOM"固化成检查项（`Get-ChildItem ... | 查前 3 字节`）。

> ⚠ 同一类坑在**文档**上也踩了：我用 `WriteAllLines` 改本 ADR / 这份文档时，
> 把原来的 **LF 变成了 CRLF**，于是 `git diff` 显示"**整个文件都改了**"（372 行全红）。
> 看起来像我把文档重写了一遍，实际只加了 74 行 —— 而中间还夹了一次"BOM 被去掉"，
> 让 diff 更没法看。
> 📌 **改文本文件时要保持原有的行尾与 BOM**。否则 review 时"看不出真实改动"
> 比改错更隐蔽 —— 改动本身对，但没人能确认它对。

### 🟠 ⑥ ★★ `accept` 与**任何 HTTP 层 e2e** 不能并发跑（子代理实测发现）

`server/src/acceptance.cj` 的 `hResetAll` 会 **整表清空**业务表
（`DELETE FROM appointment / schedule / doctor / department / patient`），
而 HTTP 层 e2e 脚本（`emr-check` / `p1-extra-check` / `stress-booking` / `triage-check`）
都在**同一张库**里插自己的夹具 ⇒ 并发时 `accept` 会把 e2e 的夹具删掉，
e2e 的断言随即全红（HTTP 404 / 队列为空）——**看起来像产品坏了，其实是两个测试在互相踩**。

更隐蔽的一层：两者收尾都 `taskkill /F /IM hospital-server.exe`，
于是并发时一边的 `serve` 会被另一边杀掉 ⇒ `curl` 返回 `HTTP 0`。

⇒ **纪律：`accept` 与 HTTP 层 e2e 必须串行**（已写进 `emr-check.ps1` 文件头）。
📌 这是"**两个测试共享同一份外部状态**"的典型症状：
每个脚本单独跑都绿，一起跑就红，而红的原因与被测代码**完全无关**。
`accept` 因其"整表清空"的语义是唯一**必然**冲突的一方 —— 它必须独占。

> 证据（子代理实测抓到的）：并发那一轮里 [0] 夹具校验 **6/6 PASS**，紧接着 [2] 队列为空、
> [3][4] 全 `404 APPOINTMENT_NOT_FOUND`，共 25 条 FAIL；而**之后才插入**的 [6][7] 却全部正常。
> 当时库里的残留物证是 `acceptance_p4.cj` 的种子（`doctor 900003`、`patient 8811/8812`、
> `department 810003`、`schedule 820003`）—— 完全吻合"夹具被中途删掉"。
> 另一种症状是 `HTTP 0`（curl 连不上）：并发流程开头的 `taskkill` 把对方的 `serve` 杀了。

### 🟠 ⑦ `POST /api/v1/admin/users/:id/password` 的 `:id` 是 **`auth_user.id`**，不是 `ref_id`

子代理实测发现：p4doctor / p4patient 的 `auth_user.id` 是 **17 / 18**，
而 `ref_id`（绑的业务实体）是 `700001` —— 两者**不是一回事**。
于是用 `ref_id` 去调那个端点会得到 `404 USER_NOT_FOUND`（口令根本没被重设），
症状表现为"登录失败"，很容易被误读成权限/令牌问题。

⚠ 这**不是缺陷**（端点语义就是"按账号 id 改口令"，账号 id 是自增主键），
但它**极易误用**，因此：
- `emr-check.ps1` 里加了 `EnsureAccount`：201 时取 `data.user_id`；
  409（已存在）时用 `GET /api/v1/admin/users?login_name=` **问出真实的 user_id** 再重设口令
  —— 这样脚本**可重复跑**，而不是"第二次必红"。

### 🟠 ⑧ `Invoke-MySqlFile` **不吞错，但也不告诉你"SQL 压根没执行"**

它只在 SQL **报错**时救你；如果 SQL 文本**没落盘**或路径写错，它一样"静默成功"。
⇒ 夹具一律走"落盘 + `Invoke-MySqlFile` + **插完查行数**"三步
（`emr-check.ps1` 的 `SqlFile` + `RowCount`）。
📌 与 P2 那条教训同源：**"跑过了"与"生效了"是两件事**，夹具也要有断言。

## 五之二、🟠 **第九份**复查（2026-10-07）：一处"出错提示里的端口"漂移

### 现象

连接失败时的**处置提示**仍指向 **3307** —— 而 3307 是**社团那台**便携 MariaDB 的端口，
本项目自管 devdb 早已迁到 **3317**（见 `docs/DEV-DB.md`）。共 4 处：

| 位置 | 原文 |
| --- | --- |
| `db_bootstrap.cj` 建库失败提示 | 「本机联调的便携版 MariaDB 是 127.0.0.1:**3307**」 |
| `db_bootstrap.cj` 连接失败提示 | 「本项目本机联调用便携版 MariaDB 的 **3307**」 |
| `db_bootstrap.cj` 的 `MySqlConfig.port` | 默认值 = **3307** |
| `main.cj` usage | 示例 DSN `…@127.0.0.1:**3307**/hospital` |

**复查的人被它误导了，我自己在本项目里也被它误导过** ——
devdb 没起来时，提示让人去查 3307，而正确处置是启动 3317 的 devdb。

📌 而同类漂移**一路修了很多处**（`DEV-DB.md`、`README.md`、脚本默认 DSN 都改成 3317 了），
**只有这几处"出错时才显示"的文案漏了** —— 偏偏这是**最需要准确**的地方：
使用者正是在"已经出错、最需要指引"的时刻读它。

### 修法（不止改数字 —— 那样下次还会漂）

| # | 做法 | 理由 |
| --- | --- | --- |
| ① | 提示改为**从 `cfg` 派生**：先回显 `${cfg.host}:${cfg.port}`（实际用的那个），再让使用者拿它去 `docs/DEV-DB.md` 核对 | **端口的事实来源是 `cfg`**（DSN 里那个）。提示里再手写一份 = 同一件事两处口径 ⇒ 迟早漂移。**本提示不复制那个数字，就没有第二次漂移的机会** |
| ② | `MySqlConfig.port` 默认值 **3307 → 3306**（MySQL 出厂默认） | 3307 是个**假默认**：本项目**没有任何实例**在那 ⇒ "什么都不传"这条路径必然失败；更坏的是它**看起来像对的**（一个具体的、像配置过的数字），于是「没拿到 DSN」与「端口写错」两种故障长得一模一样。取协议标准口，则任何"没拿到 DSN"都会以一个**明显不对**的端口暴露 |
| ③ | `main.cj` usage 示例改成**形状示例**（`…@127.0.0.1:<端口>/hospital`）+ 指向 `DEV-DB.md` | usage 是使用者**第一眼**看到的东西；写死一个本项目不用的端口会直接把人引到错地方 |
| ④ | selftest 加断言：默认端口 = 3306、且 `describe()` 口径一致 | 把"假默认"这个缺陷本身钉住 |

### 实测（决定性验证：提示**跟着实际端口走**）

```
$ check-db mysql://hospital:pw@127.0.0.1:3306/hospital_test
连接：hospital@127.0.0.1:3306/hospital_test
❌ 连接 MySQL 失败（hospital@127.0.0.1:3306/hospital_test）：…
  处置：① 确认服务器在跑、且端口与上面回显的 127.0.0.1:3306 一致
        （本项目自管 devdb 的端口以 docs/DEV-DB.md 为准 —— 本提示刻意不写死它，免得两处漂移）

$ check-db mysql://hospital:pw@127.0.0.1:3307/hospital_test
连接：hospital@127.0.0.1:3307/hospital_test          ← 提示里也跟着变成 3307
```

⇒ 提示里**不再出现任何硬编码的"本项目端口"**，而"实际用的是哪个端口"**始终回显**。

### 一处刻意的**不改**

## 五之三、★★★ P4 收尾：**内存 Store 整体拆除**（ADR-0001 rev.7）

原本的工作项是"补上配套域生产不刷盘的缺口"。**核实的结论比"缺口"彻底得多**：

| 核实项 | 实测结果 |
| --- | --- |
| `MemStore` 的**生产**实例化点 | **零处**（唯一实例在 `acceptance.cj`） |
| `loadAll()` 的**生产**调用点 | **零处** |
| `flushToMysql()` 的**生产**调用点 | **零处** |
| `MemStore` 有"往内存里写"的入口方法吗 | **没有**（只有 `loadAll`/`flushToMysql`/两个查询函数） |
| 生产代码对 department/doctor/patient 的**写** | **零处** |
| 生产代码对这三张表的**读** | 11 行（看板 3 个计数、分诊 2 处科室名查询） |
| 有"管理端建科室/医生"的端点吗 | **没有** |

⇒ **这条范式在生产上从未接线**。那三张表实际是**只读参考数据**（靠人工 SQL 灌入），
而 README 却把它描述成"内存 Store 范式"——**文档比实现更先进**；
P4 的看板还会把"上次刷盘的快照"当成现状报出去（**它根本没错，因为从来没有刷过**）。

### 三个候选与选择（已与用户确认）

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A | 补全：加写入口 + `serve` 里 `loadAll` + **定时刷盘** | ✗ 引入本项目迄今没有的**后台定时器**，且仍有"两次刷盘之间崩溃丢改动"的窗口。**这不是修洞，是"真的把配套域建起来"** |
| B | **拆掉**：删 `mem_store.cj`/`sql_recorder.cj`，三张表改直接 SQL | ★ **选它**。生产行为**几乎不变**（它们本就只被读），却消掉"两种范式并存"与"文档比实现先进" |
| C | 只改看板标注 + 写进未做清单 | ✗ 最小改动，但那份 ~490 行**未接线代码会继续误导读者** |

### 为什么"拆"是**更保守**的选择

- **没有功能被删掉**：这三张表本来就只被读，拆掉后**读法不变**（还是 SQL）。
  真正被删的是**一条从未走过的代码路径**。
- **"不接线的东西"不是中立的**：它让 README 与实现不一致、让 AC-4 去验证一个
  生产上不存在的机制、让后来者（包括我自己）以为数据流是那样走的。**这是负资产。**
- **保留了重建的余地**：将来真需要缓存（例如 ADR §8 的水平扩展触发条件），
  那时**有明确需求与验收标准**再建，比留一条半成品好。

### ★★ 一个必须写清的区分：**消失的是"范式"，不是"表"**

`department`/`doctor`/`patient` **仍在库里、仍在 `ALL_TABLES` 里、仍被人读**。
所以 `selftest` 的分类里**不是删掉那一项**，而是给它**新归属：基础数据域**
（直接 SQL 读；⚠ **目前没有写入端点**，靠人工 SQL 维护 —— 这条纪律必须写明，
否则读者会以为"系统会自动积累科室/医生数据"）。

> ⚠⚠ **我第一版就是"删掉那一项"**：结果求和 = **9** 而 `ALL_TABLES.size` = **12**，
> selftest 报「表集共 9 张」。
> 我起初怀疑是 `Array.size` 的语义（仓颉 `String.size` 是**字节**，很容易怀疑数组也有坑），
> 于是**先做最小探针**验证 `Array.size` 是**元素个数**（4→4，12→12）✅ ——
> 探针排除了那个假设，才看到真正的原因：**我把 3 张表从求和式里一起删掉了**。
> 📌 教训：**删一个概念时，先问"挂在它下面的实体去哪"。**
> 把实体一起删掉 = 数据丢失；连分类一起删掉 = 断言数不上账。
> **正确做法是重新归类，并写明新纪律。**

### `sql_recorder.cj` 为什么也删

它是 `DbBackend` 的录制装饰器，**唯一用途**是 AC-4 的"刷盘 SQL 里从未出现 `schedule`"。
没有刷盘了 ⇒ 它没有对象可录。
📌 一个**只为一个不存在的机制服务的测试工具**，留着就是"假象的一部分"。

### AC-4 不是简单删掉，而是**重写**

它守的"刷盘不波及号源域"没有对象了，但它**真正要保证的事**仍在：
**没有第二条路径能碰号源域**。⇒ 重写为「数据访问范式**唯一化**」，四层结构保留：

```
① 分类：每张业务表都归属一个域（无孤儿表）
② ★★ 号源域的表只准 BookingRepo 写，且域清单与表集不脱节
③ ★ 表名与基线内存 Store 零交集（**从旧 AC-4 保留**）
④ ★★ 反向：号源域确实有数据（否则③是"空比空"的假绿）
```

⚠ 并且**刻意不写**"没有内存 Store"这类运行期断言 —— 按踩坑表 M 条
「断言"没有 X"的前提是 X 真的**存在**」：那些名字已不存在，硬写字符串比较是**空洞**的。
⇒ 交给**编译器**：引用 `MEM_TABLES`/`MemStore` 直接**编译失败**。
**编译期保证比任何运行期断言都硬**，所以代码里写明了"不写那种断言"以及**为什么**。

### 顺带清掉的死代码

`hDumpTable` / `hDumpEquals`（整表导出与逐值比对助手）是 AC-4"刷盘前后逐值不变"的支撑。
没有刷盘后它们**失去唯一调用者** ⇒ 按"删代码要明说为什么"一并删除
（留着等于留一段"看起来还有人在做全表比对"的假象），代之以 8 行的 `hCountRows`。

### 结果

  源码 **24 → 22** 个 `.cj`（删 2 个文件）；`selftest` 47 → **43** 项；
  `accept` 248 → **238** 项（AC-4 由 14 项精简为 6 项，且**每条都还有对象**）。

## 五之四、★★ **第十份**复查（2026-10-09）："配置看起来生效、实际没接线"

复查的核心指控是准确的，而且是本项目**反复复抓的那一类**：三个旋钮
**被校验、被存库、被回显，却没有任何地方消费**。逐条处置：

### ① `ai.timeout_secs` 没接线 —— 患者请求实测挂起 21 秒

**已接线**：`ClientBuilder.readTimeout/writeTimeout` + `HttpRequestBuilder.readTimeout/writeTimeout`
都设成 `ai.timeout_secs`（请求级才是逐次生效的那一层，两层都设）。

⚠⚠ **但必须如实写清两个边界，不能假装超时是全能的**：

  ① ★ **框架没有 connect 超时**。我把 `stdx.net.http.cjo` 的 `ClientBuilder` 成员
     全列出来核对过：只有 `readTimeout` / `writeTimeout` / `poolSize` /
     `maxFrameSize` / `autoRedirect` / proxy / logger，**没有 connectTimeout**。
     ⇒ 「连一个**不可达**地址」那一段由**操作系统的 TCP 连接超时**决定
       （本机实测约 21 秒），**应用层改不了**。
       所以复查那条 21 秒**不是"接线后又没生效"**，而是**连不上时必然如此**。
  ② ⚠ **`readTimeout` 的实测语义与配置值不一致**。我用一个
     **"accept 但不回任何数据"的本地监听器**测（这正是复查点出的
     "握手成功却一直不回 ⇒ 无限挂住并占着服务线程"那种形态）：

     ```
     配置 ai.timeout_secs = 3，端点 = 假端点（accept 后不回）
     实测：HTTP 200，耗时 30222 ms，ai_reason = 出站调用异常：Failed to read data: read data timeout.
     ```

     ⇒ 超时机制**确实触发了**（`read data timeout` 而不是 OS connect 超时），
       且**如实降级到 rules**；但**耗时是 30 秒（框架默认值），不是我配的 3 秒**。
     ⇒ 结论：请求级 `readTimeout(Duration)` **被传递但未被框架采纳**。
       **改善是真实的**（从"无限挂"变成"30 秒兜底 + 明确降级"），
       但**不能声称"配多少就是多少"** —— 这一点已写进代码注释，并列为未做项。

### ② `elapsedMs` 恒为 0

**已修**。根因是我把**调用方传入的 `now` 参数**既当起点又当终点
（`let t0 = now … r.elapsedMs = now - t0` ⇒ 恒等于 0）。
⇒ 改成真读时钟（`DateTime.now()`）。
📌 教训：**用参数当"当前时间"就等于假设调用是瞬时的**；测耗时必须读真时钟。

### ③ `ai.max_concurrent` 没接线

**已接线**：`ai_call.cj` 加进程内 `Semaphore` 闸。
⚠ 口径边界（写进了代码与文档）：`max_concurrent` 是**库配置**，而信号量容量在
**启动后首次出站**时定下，之后**不随配置变**（仓颉没有"运行时改信号量容量"；
每次调用新建信号量 = **等于没限流**）。

### ④ `ai.ca_bundle_path` 没法接线 ⇒ **改成明确拒绝**

我原本打算设 `TlsClientConfig().certificate`，编译器给出的期望类型是
`Option<Tuple<Array<Certificate>, PrivateKey>>` —— 那是**客户端证书（mTLS）**，
**不是信任锚**。这个版本的 `TlsClientConfig` **没有** CA bundle 入口。

⇒ 处置（比"接线了但假的"和"静默忽略"都好）：`AiSettingSpec` 新增
`unsupported` / `unsupportedReason` 两列，`ca_bundle_path` 标为**不支持**，
**`put()` 写入即被拒**并给出「为什么 + 怎么办」（把 CA 装进系统信任库，
或升级到暴露了信任锚配置的 stdx）。
📌 本仓纪律：**配置项要么真生效，要么明确说它不生效** ——
"看起来生效"是最坏的一种（它把排查引向错误方向）。

### ⑤ 测试夹具撞名 ⇒ 看起来像产品缺陷的假红（复查独立复现）

19 PASS/**5 FAIL**。根因两条，**都是我的夹具不干净**：

    那条 INSERT **静默失败**（它用 `$null = Invoke-MySqlScalar` 且不检查结果）
    ⇒ 它的断言随后失败。

**已修**：`base-check` 的科室**一律用 `BASET`/`BASEDEL` 编码前缀**，
