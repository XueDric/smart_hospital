## 二、★★ 「密钥不落库」是怎么做到的（本阶段最要紧的一节）

brief §5.3 原文点名的**安全回归风险**：

> 「参考系统说『API Key 支持 `env:` 回落、**密钥不落库**』……
>  改成 DB 驱动时，**把密钥写进库是倒退** —— 建议库里只存引用路径 / `env:` 名。」

### 存的是**引用**，不是密钥

```
ai.key_ref = env:SMART_HOSPITAL_AI_KEY      ← 从环境变量取
ai.key_ref = file:C:\ProgramData\...\ai.key ← 从文件取
```

密钥本体**永远只在环境变量或文件里**。

### 而且是**机制性**保证，不是"我们记得别写"

`validateKeyRef()` 只放行两种形状，其余一律拒绝。关键在于它**不止判前缀**：

| 被拒的输入 | 为什么这条重要 |
| --- | --- |
| `sk-abcdef...`（裸密钥） | 最直接的情况 |
| ★ `env:sk-abcdef...` | **前缀合法但本体是密钥** —— 只判前缀的话这就绕过去了 |
| `env:123STARTS_WITH_DIGIT` | 变量名形状不对（必须是 `[A-Za-z_][A-Za-z0-9_]*`） |
| `env:HAS-DASH` | 含非法字符 |
| `file:not-a-path` | ★ 不含任何分隔符的"路径"不可能是真路径，更可能是被误当路径的密钥 |
| `https://api.x/v1?key=sk-xxx` | 直接给了带密钥的 URL |

> 📌 **设计要点**：收紧"变量名/路径的形状"不是吹毛求疵 ——
> 如果只判 `env:` / `file:` 前缀，攻击者（或手滑的运维）写
> `env:sk-abcdef...` 就能把密钥存进库，**同时满足前缀要求**。
> 那就等于整条约束不存在。

### 三层断言（一层比一层硬）

AC-P3-1 的断言不是"功能能用"，而是"**密钥进不去库**"：

1. 合法引用能存、**9 种非法形状**（含绕过尝试）全被拒；
2. 被拒的值**真的没有**进库（不是"拒了但已经写了一半"）；
3. ★★ **全表兜底扫描**：任何一行的值都不得是"像密钥"的长随机串
   —— 这一层防的是"将来有人加了别的写库路径绕过 `put()`"。

**变异测试**：把 `validateKeyRef` 改成直接放行一切 ⇒ 断言 ② 立刻报出
**8 条"未拒绝"**（含那条绕过尝试）。⇒ 这个机制真的在守。

## 三、新增的**第五类表**：`ai_setting`

加这张表时 `selftest` 又一次报红（它就是这么设计的），于是分类再扩一格：

| 类别 | 表 | 数据访问范式 |
| --- | --- | --- |
| 号源/挂号域 | `schedule` `appointment` | 直接 SQL（ADR-0001 §4.3 锁死） |
| 配套域 | `department` `doctor` `patient` `medical_record` | 内存 Store |
| 鉴权域 | `auth_user` `auth_token` `auth_login_attempt` | 直接 SQL |
| 预问诊域 | `previsit_session` | 直接 SQL（医疗数据） |
| ★ **AI 配置域** | `ai_setting` | 直接 SQL（**配置**，不是业务数据） |

并钉住两条否定断言：AI 配置表**不属号源域**（它是配置，不是可扣号路径）、
**不属内存 Store 负责的表**（配置要立刻持久化，不能进"整表替换"范式）。

**为什么用 KV 表而不是"一个字段一列"**：AI 配置项会随模型协议演进增删。
一列一项 ⇒ 每次加参数都要 DDL 变更 + 迁移；KV 表让"加配置项"只是往
`aiSettingSpecs()` 加一行（与 `previsit` 的 `form_json` 同一理由）。

## 四、「改配置零重启」是怎么做到的

写库 → `invalidate()`（把 `cacheAt` 置 0）→ 下次读重新查库。**没有重启这一步。**

两个刻意的设计选择：

| 选择 | 理由 |
| --- | --- |
| **置 0 重查**，而不是"把新值塞进缓存" | 后者在多实例/并发写下容易与库不一致（本实例以为写成功了，实际别的实例又改了库）。置 0 = **永远以库为准** |
| 缓存**仍有 TTL（5s）** | 多实例部署时别的实例收不到本实例的失效通知，只能靠 TTL 收敛。本机单实例下 TTL 不触发，但**不能因此不写** —— 那会让"将来上多实例"变成一个静默的正确性缺陷 |

另有两条"刻意不做"：

- **不把 `insecureTrustAll` 做成配置项**：它是"仅本机开发跳过证书校验"的危险开关，
  **不该有"运行时被改开"的路径**（那等于让生产环境的 TLS 校验可被远程关掉）。
  它只能由启动参数决定。📌 这是**刻意的遗漏**，写在这里免得将来有人"补齐"。
- **`ai.key_ref` 不进 `AiRuntimeOptions` 的路径字段**：引用在装配时才解析，
  "库里存引用、本体在环境/文件"这条边界在**类型上**就不会被混。

## 五、测试抓出来的一个真缺陷（endpoint 回显泄露查询串）

`aiSettingsJson()` 最初把 endpoint 当**普通非秘密项**，直接回显全值。
而有些网关把凭据放在查询串里（`...?api-key=xxx`）——
于是 `?token=SECRET_TOKEN_XYZ` 原封不动出现在回显里。

**AC-P3-4 ② 把它抓出来了**（我写的断言："回显不含 endpoint 的查询串"）。

> 📌 而且这是**同一件事两处口径**的又一例：
> 我在 `aiSafeHost()` 里**已经为日志脱敏过一次**，却在回显那条路上又原样输出。
> 修法：endpoint 的回显**统一走 `aiSafeHost()`**，并加 `redacted` 字段
> 告知管理员"这个值被脱敏过"（免得他以为配置里真的只存了 host）。

这是这个项目第 N 次栽在"同一语义两处实现"上 —— 已写进 `server/README.md` 踩坑表（P 条）。

## 五之二、🔴 **第七份**复查（2026-10-07）：2 条 MINOR

复查定性我认同 —— 两条都**不影响功能正确性**，但都是真的。

### 🟠 MINOR ① 数值类配置**写入时完全不校验**，回显与生效值不一致

复现（我逐条验过，与复查给的完全一致）：

```
PUT ai.timeout_secs = abc    -> 200，回显 value=abc，而生效值是 30
PUT ai.max_tokens   = abc    -> 200，回显 value=abc，而生效值是 2048
PUT ai.timeout_secs = 30秒   -> 200，回显 value=30秒，生效值 30
```

根因：**同一张表里两套口径** —— `ai.key_ref` 是**写入即校验**，
数值项却"写了不管、读时 `parseInt64Or` 静默回落"。

复查还探到一个更能说明危害的真实时序：库里原来是越界的 `9999`
（**正确地**给出 `enabled=false` + 明确理由），把它"改成" `abc` 之后
**`enabled` 反而翻成了 `true`** —— 一个写错的编辑把报警变成了绿灯。

**修法**（与 `key_ref` 同一道闸门，都在 `put()` 里）：
- 新增 `AiSettingSpec.numMin/numMax`，三个数值项各自带上范围（与 `aiRuntimeValidate` 的边界一致）；
- `put()` 里判"非数字 ⇒ 400 / 越界 ⇒ 400"，空值**显式例外**（表示回到默认值，不能变成 400）；
- 顺手治本：`get()` 的默认值也 `trimAscii()`，`put()` 存**trim 后**的值。

#### 顺带修掉的两处"回显 ≠ 生效"（都是被断言逼出来的）

1. **空值那条路**：`put("   ")` 原样把 3 个空格写库 ⇒ 回显 `"   "`、生效 30。
   —— 与复查指出的缺陷**同一个病**，只是入口从"非数字"换成了"全空白"。
2. **回显的语义**：原来回显 `repo.get()` 的**原始值**（空 = 没设），
   而**生效值**是默认值。空串回显会让管理员以为"这项没配"，而实际生效的是 30。
   ⇒ 现在回显 `value` 一律是**生效值**（原始值非空则用它，否则用默认值），
   并加 `is_default` 字段区分"我设的"与"默认来的"。

> 📌 这两处都是**我自己写的断言**（"回显值与生效值一致"）抓出来的 ——
> 而且第一次抓到时我的**断言写错了对象**（拿了 `repo.get()` 而不是接口回显），
> 还差点把正确的行为判成缺陷。教训：**断言"回显 == 生效"时，要断言回显接口的输出。**

### 🟠 MINOR ② 预问诊"是否采完"的判据**可被答案内容影响**

我原来用 `form_json LIKE '%槽位名%'` 计数，并论证"六个 key 两两不是彼此的子串"。
那个前提**成立，但不充分** —— 复查指出：**答案文本里可以出现槽位名**。

我实测复现：

```
form_json = {"chief":"咳嗽 duration severity associated history allergy"}
真实键数 = 1 ；LIKE 计数 = 6 ⇒ 被判成"已完成"
⇒ 一个只答 1 项的会话**永远不被压实**，存储上限可被**对抗性绕过**
```

（业务正确性不受影响：HTTP 层读的是内存里解析后的表单，
仍正确地报 `complete=false` / `filled=1` —— 复查也确认了这点。）

**修法**：`IFNULL(JSON_LENGTH(JSON_KEYS(form_json)), 0)` —— 数**真实键**，与值的内容无关。

#### ⚠ 这里有两个坑，我都实测验证过，值得记下来

| 坑 | 实测结果 | 处置 |
| --- | --- | --- |
| 复查建议的 `JSON_LENGTH(form_json)` | MariaDB 对**对象**给的就是**键数**（1/6 都对） | 可用；但我更倾向更明确的写法 |
| ★ `JSON_LENGTH(''或坏 JSON)` | 返回 **NULL** ⇒ `NULL >= 6` 得 NULL ⇒ 驱动层 `getInt` **抛异常** | ⇒ 加 `IFNULL(..., 0)` |
| ★ 为什么不用 `JSON_LENGTH(JSON_EXTRACT('$.*'))` | 同样对非法输入返回 NULL | 用 `JSON_KEYS`（对同样输入返回 **0**，是干净的整数比较） |

★ 第二个坑**不只影响测试**：生产里一条坏 JSON 就能让"清理陈旧会话"抛异常，
而它跑在 `create()` 里 ⇒ **新会话也建不出来**。那是一条坏数据升级成
"整个预问诊不可用"的路径。加 `IFNULL` 后坏 JSON ⇒ 键数 0 ⇒ 判为"未采完" ⇒ **会被正常清理**
（坏数据该被清掉，而不是把功能拖死）。

#### 这引入了一个方向相反的取舍（如实记录）

之前我特意**不**依赖 DB 高级特性（`previsitSlotCountSql` 的注释里写过这个偏好），
现在改用 JSON 函数，方向相反。**这是权衡后的选择**：
正确性 > 可移植性，而且我们本来就用 JSON 语义存 `form_json`，
依赖 JSON 函数不新增约束面。理由已写进代码注释。

补的是 brief §2.2 创新点① 的另两部分（第一块「配置底座」见 §一~§四）。

### 交付

| 端点 | 内容 |
| --- | --- |
| `GET /api/v1/admin/ai/prompts` | 读三个 Prompt 模板（正文**原样回显** —— 它不是机密，管理员要能核对） |
| `PUT /api/v1/admin/ai/prompts/:name` | 改模板（**缺必需占位符直接拒**） |
| `DELETE /api/v1/admin/ai/prompts/:name` | 恢复默认模板 |
| `GET /api/v1/admin/ai/tools` | 六个 AI 工具的开关状态 |
| `PUT /api/v1/admin/ai/tools/:name` | 开关某工具（只接受 `true`/`false`） |

**复用而非新造**（"同一语义只留一处"）：Prompt 与工具开关都落在**同一张
`ai_setting` KV 表**上，用 `prompt.` / `ai.tool.` 前缀做命名空间，
共用同一套缓存与失效逻辑。⇒ **缓存失效只有一份实现**。

三处 Prompt 都对应本项目**已有的一处真实逻辑**（接模型时要替换/增强的点）：

| Prompt | 对应现有逻辑 | 必需占位符 |
| --- | --- | --- |
| `dept` | `guessDepartment()`（关键词规则） | `{主诉}` `{候选科室}` |
| `previsit` | `previsitAssistantLines()`（规则话术） | `{主诉}` `{已有信息}` `{待问项}` |
| `redflag` | `detectRedFlag()`（纯规则保险丝） | `{主诉}` |

> ⚠ `redflag` 那条刻意只要求 `{主诉}`，且注释里写明：**真正的保险丝仍是纯规则**——
> 绝不能让"模型是否认得出危急"变成唯一防线。

### ★★ 占位符校验：守的是"AI 静默变笨"

Prompt 模板最容易出的错是**漏了变量** —— 改了模板、忘了留 `{主诉}`，
模型收到一段没有患者信息的空白人设，输出**看起来正常但完全没用**。
这种错**不报错、不崩溃**，只是"AI 变笨了"，是最难查的一类故障。

⇒ 所以"必需占位符"写成**契约**，写入时就拦（4 个缺占位符的模板全部被拒）。
并且断言"**默认模板自身也必须合法**"—— 否则"默认值"这条路会把校验绕过去。

### ★★ 工具开关：被禁用的工具必须**真的**不可用

断言刻意打在**判据函数**（`aiToolEnabled`）上，而不是接口回显上 ——
"看起来生效了"（回显 `enabled=false`）与"真的不可用"是两件事。

语义三条：
1. **未登记的工具 ⇒ 不可用**（白名单纪律：模型不能新增工具）；
2. 库里没该行 ⇒ 默认值（**默认全开** —— 白名单里列出的就该可用）；
3. 库里存 `1` ⇒ 开；**其它任何值（含 `0`/空/垃圾）⇒ 关**。
   ⚠ 第 3 条刻意**从严**：只有明确的 `1` 才算开。反过来（"不是 0 就算开"）
   会让一个写坏的值变成"开着"——那是**静默放宽**；从严的失败方向是"工具被关掉"，
   **可见、可查、无害**。📌 与 ADR/限流那几处的取舍一致：**失败方向选安全的那侧**。

### 🔴🔴 本轮最有价值的发现：一个**语言陷阱**（我自己抓到的）

我原来这样分派默认模板：

```cangjie
match (name) {                       // name: String
    case PROMPT_DEPT => ...          // PROMPT_DEPT 是 String 常量
    case PROMPT_PREVISIT => ...
}
```

**探针实测**（`let A: String = "dept"` / `let B: String = "previsit"`）：

```
match(A)     -> 命中 case A     ✓
match(B)     -> 也命中 case A   ✗   （B = "previsit"）
match("zzz") -> 还是命中 case A ✗
```

⇒ **String 常量在 `case` 里被当成"绑定变量"（catch-all），按值比较根本不发生。**
于是 `promptDefaultBody(PREVISIT)` **一直返回 dept 的模板**。

**危害形态**：不报错、不崩溃，**只是返回错的数据**。
我是被"**默认模板必须含齐自己的占位符**"这条断言抓出来的
（previsit 的模板缺 `{已有信息}`/`{待问项}`）—— 断言写在**值**上，
才照出了这个"看起来对"的实现。

**全仓审计**：扫过所有 `case 标识符 =>`，只有这三处是 String 常量；
其余是**枚举构造子**（`Patient`/`Admin`/`Cancelled`…）与 `None`，
按值匹配**正常**。⇒ 只有这一处要改，改成 `if (name == 常量)`。

**加了两道闸门**：
- ① 已有的"默认模板必须含齐占位符"（**碰巧**抓到，因为两个模板占位符不同）；
- ①b ★ **"三个默认模板两两不同"**（**直接**守住这个陷阱 —— catch-all 会破坏的正是这条性质）。
  变异测试：把分派改回 `match` + 常量标签 ⇒ **两条断言都变红**。

### 🟠 顺带修掉一个真 500

新加的 `bodyBool` 直接 `v.asBool().getValue()`，于是
`{"enabled":"yes"}`（字符串）**抛异常 ⇒ 500**。
而"字段类型不对"是**客户端错误**，该 400。

⇒ 改为**先 `is JsonBool` 判类型再取值**，不符就返回 `None`，由调用方给准确 400。
📌 一般规律：**`asXxx()` 在类型不符时是抛异常，不是返回 None** —— 读用户输入必须先判类型。
（HTTP 层的测试抓到；纯逻辑层碰不到这段。）

## 五之四、🔴 **第八份**复查（2026-10-07）：1 条真问题 + 1 条测试卫生

### 🔴 ① `create-db` 建出来的库，同一个账号用不了（已复现）

复查给的复现链我逐条验过，与它完全一致：

```
create-db → ✅ 库已就绪：iso_test2
check-db  → An exception has occurred:
            SqlException: ALTER command denied to user 'hospital'@'localhost'
            for table `iso_test2`.`appointment`
            at migrateSchema(schema.cj:520) → checkDb(main.cj:73)
            exit=1
```

根因（我实查 `SHOW GRANTS` 确认）：

```
GRANT CREATE ON *.*                          ← 全局：只能"建库"
GRANT ALL PRIVILEGES ON `hospital`.*         ← 权限是**按库逐个授**的
GRANT ALL PRIVILEGES ON `hospital_test`.*
```

⇒ 它能 `CREATE DATABASE iso_test2` 成功，但**对新库没有任何权限**。

**修法**（两处）：

1. **`create-db` 建完库后必须让库"真能用"** —— 新增 `ensureDatabaseUsable()`：
   探测 → 不可用则尝试自助授权 → 还不行就**明确报"已建好但用不了"** + 给出
   可复制的 root 命令 + 返回失败（exit=2）。
   📌 纪律：**不许把"不可用"报成"就绪"**。
2. **新增 `--admin-dsn`**（推荐路径）：给一个带 `GRANT OPTION` 的 DSN，
   **建库 + 授权 + 探通一步到位**。管理员 DSN **允许不带库名**（`GRANT` 不需要）。

> ⚠ 业务账号**不能**给自己授权，这是**正确**的安全设计 —— 所以正确做法是
> **显式提供**一个管理员 DSN（一次性使用），而不是让业务账号拿到 GRANT OPTION。

#### 修的过程里我错了三次，每次都记下来（都是"探错了能力"）

| # | 我探的 | 为什么错 |
| --- | --- | --- |
| ❌ 1 | `CREATE TABLE` 一个探测表 | `CREATE ON *.*` 是**全局**的 ⇒ 在新库上**永远允许**（实测：新库上 CREATE 允许，而 ALTER/DROP/SELECT 全被拒）⇒ **必然误报"可用"**，还会**留下垃圾表** |
| ❌ 2 | 对"**已存在**的应用表做 ALTER" | 真·全新库里一张应用表都没有 ⇒ 走"保守判不可用"的兜底 ⇒ **管理员明明授好权了也报"用不了"**（实测：`GRANT` 成功却打印 ❌） |
| ✅ 3 | `CREATE TEMPORARY TABLE`（无残留）+ 对已存在应用表 `ALTER ... ENGINE=InnoDB`（幂等改写），**两者必须都过** | 临时表随连接消失、零残留；ALTER 才是 `migrateSchema` 的真正需求 |

> 📌 教训：**"探测"必须探"我们真正需要的那件事"，而不是一件相关但更弱的事。**
> 拿更弱的能力去探，会得到一个"看起来通过"的假阳性 —— 比不探更坏。

#### 还修掉一处同类隐患：授权语句**不要硬编码 host**

我第一版写 `TO 'user'@'localhost'` —— 而 host **不是**由 DSN 决定的：
同一个 DSN 连上去，MySQL 可能把你认成 `user@localhost`（socket/named pipe）
或 `user@127.0.0.1`（TCP）。写死 `localhost` 对后者就是**授给了一个不存在的账户**
（GRANT 甚至报成功，因为 MySQL 默认会创建账户）。
⇒ 现在一律用**数据库自己报告的 `CURRENT_USER()`**（`user@host`）拼授权语句，
这样"授给谁"与"我是谁"**必然一致**。

### 🟠 ② `check-db` 的未捕获异常 + 完整堆栈

`migrateSchema` 在 `check-db` 里**在 try/catch 之外**（`main.cj:73`），
于是权限不足时抛未捕获异常 + 一堆驱动内部帧 ——
违反本仓自己立的规矩「**失败必须被说出来，不能靠崩溃表达**」。

⚠ 对照：同一个 `migrateSchema` 在 **`accept` / `serve` / `create-admin` 三处
早就都包好了**。⇒ 这是**同一类疏漏的最后一份**，不是新问题
（我全仓扫过 4 个调用点，确认只有 `check-db` 漏了）。

**修法**：纳入 try/catch，给 `❌` + 处置（含精确到本库的 GRANT 命令）。
⚠ 顺手修了一个**作用域**问题：`cfg` 原在 try 内声明，而 catch 里要用它拼命令 ——
仓颉**没有变量提升**（踩坑表 B 条），所以把声明提到 try 之外。

### 新增回归脚本 `tests/create-db-check.ps1`（17 项，可重复）

覆盖：① 不给 `--admin-dsn` 必须**明确失败**（且无成功话术、无堆栈、有 GRANT 处置）；
② `check-db` 权限不足时**干净报错**；③ 给 `--admin-dsn` **一步到位**；
④ 授权后 `check-db` 与 `accept` **都通过**（复查的原始断言）；⑤ 管理员 DSN **不带库名**也能用。

#### ⚠ 我又踩了一个"测试卫生"问题（正是复查第 2 点批评的那类）

第一版断言②**只 DROP 库、没撤授权**。于是第二次跑时库虽被删、**授权仍留在 `mysql.db` 里**
⇒ 重建同名库时权限**立刻生效** ⇒ "必须失败"那条变成成功（`exit=0`），**假红**。

⇒ 修法：前置清理**既撤权又删库**，并**直接查 `mysql.db` 断言"残留授权 == 0"**
（不假设 `REVOKE` 一定成功）。现在**连跑两次结果完全一致**。

> 📌 `GRANT` 是**独立于库**存在的 —— 删库不等于撤权。这条值得记住。
