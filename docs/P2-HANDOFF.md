### 2.2 ★★ 核心不变式：绝不给"没有号"的推荐

这是 brief 创新点 ②（先取证后结论）在分诊上的落点 ——
也是**唯一**能让"AI 分诊"变成医疗事故的地方：
患者拿着推荐去挂号，发现没号，**比不给推荐更坏**（他可能因此耽误就诊）。

实现上它是**一条 SQL + 一条断言**：

```sql
WHERE d.name = ? AND s.enabled = 1 AND s.remain_num > 0 AND s.work_date >= ?
```

四个条件缺一不可，各挡一类错：

| 条件 | 挡住的错 |
| --- | --- |
| `d.name = ?` | 规则认出的科室本院**不存在** |
| `s.enabled = 1` | 排班**已停用** |
| ★ `s.remain_num > 0` | 排班**已约满**（最容易漏的一条，见 §四变异测试①） |
| `s.work_date >= ?` | 排班**已过期** |

**"今天"由调用方传参**（不在 SQL 里 `CURDATE()`）：后者会让测试依赖数据库时区、偶发变红。

### 2.3 危急征象兜底的三个判定层（为什么不能只做关键词 contains）

中文没有词边界，裸 `contains` 会踩两个坑，**都造成误报**
（把没病的人赶去急诊，与漏报同样是伤害）：

| 层 | 规则 | 例子 |
| --- | --- | --- |
| ① 高危词 | 单独命中**即红牌** | `胸痛` / `口角歪斜` / `呕血` / `误服` / `胎动减少` … |
| ② **否定** | 命中词**前 4 个字符**内有否定词 ⇒ 本次命中**作废** | 「**没有**胸痛」不报；「没有胸痛，**但是呕血了**」仍报（切段后否定只作用于本小句） |
| ③ **共现** | 模糊词（`心慌`/`头晕`/`疼`…）**单独不算**，需与程度/频次修饰共现 | 「有点心慌」不报；「心慌**越来越**严重」报 |

**词表刻意不收**泛化词（`疼痛`/`发烧`）：它们单独出现绝大多数不是急症，
收进来会让红牌率飙到不可用（急诊被挤爆，等于没有兜底）。

### 2.4 三态与原因码

`source` 目前**只有** `rules`。照 baseline `ai_client.cj` 的 R-8 口径，
**刻意不设 `"none"`** —— "AI 没配置"时的正确表现是 `rules` + **有内容的结论**，
而不是"什么都没有"。

原因码（稳定、可断言，与给患者看的文案分离）：

| 码 | 含义 |
| --- | --- |
| `RED_FLAG` | 命中危急征象 → 转急诊，**不给任何科室推荐** |
| `OK` | 推荐且**已验证有号** |
| `ALTERNATIVES` | 首选科室没号/不存在，但给出了**有号的**备选 |
| `NO_BOOKABLE` | 该科当前没号，且全院也没有可挂号源 |
| `NO_SUCH_DEPT` | 规则认出的科室本院未开诊（且全院无号） |
| `NEED_CLARIFY` | 规则认不出主诉 → **不猜** |
| `NO_COMPLAINT` | 主诉为空/太短 → **不猜** |

> 分离的理由：改**文案**不该弄红测试，改**语义**才该（那时码变了）。

## 三、接口

`POST /api/v1/triage`（权限 `Action.Book`，即患者）

```jsonc
// 请求
{ "chief_complaint": "咳嗽三天有痰" }

// 响应（非流式，一次性）
{
  "ok": true,
  "data": {
    "red_flag": false,
    "reason_code": "OK",
    "source": "rules",                  // ← 如实标注，本轮不是 model
    "patient_note": "根据您的描述，建议就诊：呼吸内科。",
    "truncated": false,
    "options": [
      { "department_id": 1, "department_name": "呼吸内科",
        "doctor_id": 1, "doctor_name": "李医生", "doctor_title": "主任医师",
        "schedule_id": 11, "work_date": "2026-12-01", "period": "AM",
        "remain_num": 5, "total_remain": 5 }
    ],
    "count": 1
  }
}
```

三条设计要点：

1. **结论非流式**（brief §5.2）：分诊结论是**业务值**（要拿它去挂号）。
   流式会让客户端先拿到"推荐心内科"再拿到"其实推荐呼吸科"，而它可能已经拿第一句去挂号了。
2. **`red_flag_evidence` 不在响应里**：它是内部依据（命中哪些词）。
   给患者看是"你自己说你胸痛"式的复述，没有价值；给攻击者看则**暴露词表结构**（可试探绕过）。只进服务端日志。
3. **超长主诉按字符截断**并上报 `truncated`（不静默）。⚠ 必须按**字符**：
   `String` 下标是**字节**偏移，按字节切会撕裂汉字 ⇒ 非法 UTF-8 ⇒ 500。见 §四。

## 四、变异测试（证明测试**真的**在守）

抽掉守卫必须**变红**，否则那个守卫没有测试覆盖：

| # | 变异 | 结果 |
| --- | --- | --- |
| ① | 危急征象保险丝失效（`detectRedFlag` 恒 false） | ✅ accept **3 FAIL** |
| ② | 验证层失效：`remain_num > 0` → `>= 0`（约满的也推荐） | ⚠ **首次未被发现** → 见下 |
| ③ | 日期边界失效（过期排班也算可用） | ✅ accept **2 FAIL** |
| ④ | 否定判定失效（"没有胸痛"被误报红牌） | ✅ triagetest **10 FAIL** |

### ★ 变异② 首次未被发现 —— 一个真实的覆盖率缺口

我最初的 AC-P2-2 ④ 造的是**"科室完全没有排班行"**，
而 `remain_num > 0` 改成 `>= 0` 时**92 项断言全绿**。

根因：断言"没有推荐"时，**诱惑源不存在** —— 测试在"空比空"。
只有造出**"排班存在但 remain_num = 0"**这种工况，才能证明那条 SQL 条件在起作用。

已补该用例，重跑变异② → **2 FAIL**（`④ 约满的排班不得被推荐`）。

> 📌 教训（值得记住）：**断言"没有 X"时，必须让 X 真的存在过。**
> 否则测试写的是"这个列表是空的"，而不是"这个不该出现的项没出现"。

## 五、本轮踩到并修掉的真缺陷（都是"只在特定输入下才炸"）

### 🔴 缺陷①：按**字节**截断主诉 ⇒ 超长中文输入直接 **500**

`text[0..500]` 切在汉字中间 ⇒ 非法 UTF-8 ⇒ 下游 `redFlagSegments` 抛
`Invalid utf8 byte sequence`。

**形态很恶劣**：只在"输入足够长**且**长度不是字符宽度整数倍"时才炸 ——
我用 12 个字手工测是好的，是 `triage-check.ps1` 的**超长主诉用例**才把它逼出来。
已改成按 `Rune` 逐字符截断。

### 🔴 缺陷②：`String.indexOf` 返回的是**字节**下标，不是字符下标

实测 `"没有胸痛".indexOf("胸痛")` = **6**（不是 2）。
我按"字符下标"处理，把 `at - 4`（**字节**运算）当成字符窗口边界，
切出来的是「有胸」—— 恰好**跳过了"没有"**，于是判定"未被否定" ⇒ **误报红牌**。

**表现极具迷惑性**：`"无发热，无胸痛"` 反而**通过**（"无"是单字符，字节偏移恰好落在窗口里），
而 `"没有胸痛"` / `"否认胸痛"` / `"未曾呕血"` 全失败 ——
看起来像"否定词表不全"，实际是**单位混用**。

修法：窗口统一用**字节**，且 `from` 一定落在**字符边界**上
（先按字符取前 4 个、量出它们的字节长度、再从 `at` 往回减）。

### 🟡 缺陷③：`String.toArray()` 给的是字节，逐字节拼回会撕裂字符

第一版 `redFlagSegments` 按字节累积再 `String.fromUtf8` ⇒ 段边界处撕裂多字节字符。
正确做法：`for (r in text.runes())` 逐字符 + `String(Rune[])`。

> 三个缺陷**同一类**：**在"字节"与"字符"之间混用单位。**
> 仓颉里 `String` 的下标/切片/`indexOf` 都是**字节**语义，而 `size` 是**字节数**；
> 只有 `runes()` 是字符语义。**跨语言时这是最容易带错的一个直觉。**
> 已全部记进 `server/README.md` 踩坑表。

## 五之二、🔴🔴 **第五份**复查（2026-10-07 深夜）：字节/字符混用的**第 3、4 处**

复查的判断我完全同意，而且它点出了比缺陷本身更重要的一件事：
**我前一轮是在"逐点修"，而不是"按类别扫"。**

### 🔴 缺陷一：普通主诉直接 HTTP 500（字节/字符混用第 4 处）

| 主诉 | 修复前 | 说明 |
| --- | --- | --- |
| `CT显示没有胸痛` | **500** | 真实临床写法 |
| `BP160没有胸痛` | **500** | 血压 + 否认胸痛 |
| `1234没有胸痛` | **500** | |
| `aaaa没有胸痛` | **500** | |
| `aaaa持续头痛` | **500** | 模糊词 + 程度那条路也崩 |
| `血压160没有胸痛` | 200 | **恰好**落在字符边界 |
| `糖尿病10年没有胸痛` | 200 | **恰好**落在字符边界 |
| `aaa没有呕血` | 200 | **恰好**落在字符边界 |

我实测**逐条复现**，包括那三条"恰好正常"的 —— 它们的宽度组合刚好让偏移落在字符边界上。

**根因**：我上一轮的"修法"本身就还是错的。它取的是
"**片段开头**前 4 个字符的字节数"，而不是"**命中词之前** 4 个字符的字节数"。
于是当片段以 ASCII 开头（`CT显示…`，前 4 字符只占 4 字节）而命中词前是汉字
（每字 3 字节）时，`from = at - 4` 落在**第二个汉字中间** ⇒ `seg[from..at]` 切出非法
UTF-8 ⇒ 抛异常 ⇒ 500。

**而紧挨着的注释还写着"这样 from 一定落在字符边界上"** —— 那句话对它自己的代码不成立，
只在"全汉字等宽"时才碰巧成立。属于"注释与代码不符"，也是同一类问题。

> 📌 真正的教训：**不要在字节空间里做减法。**
> 我上一轮只是把"字符减 4"换成"字节减 4"，**换汤不换药** ——
> 两种写法都假设了"前面那几个字符的宽度是均匀的"。正确做法是
> **把这类运算全部收口到一个口径**（见下面的修法）。

**测试为什么没抓到**：所有否定用例都是**等宽纯汉字**（"没有胸痛"），
边界永远不会落在字符中间。**与上一轮变异②漏掉的原因完全同构**：
用例只覆盖了一种形态，于是它验的是那种形态，而不是那条规则。

**修法（按类别收口，不是再打一个补丁）**：

| 新函数 | 作用 |
| --- | --- |
| `redFlagRunes(seg)` | 把片段拆成 `Rune[]` —— **所有下标判断的唯一入口** |
| `redFlagWindowBefore(chars, chat, width)` | 纯粹在**字符空间**取"往前 width 个字符" |
| `redFlagCharToByte` / `redFlagByteToChar` | 字符下标 ↔ 字节偏移的**显式换算**；后者遇到"不在字符边界"返回 **-1**（拒绝，而不是静默切坏） |
| `redFlagIsNegatedAt(chars, chat)` | 只认字符下标，内部不再出现任何字节减法 |

`redFlagHit` 的循环也一起改了：`from = i + 1`（字节 +1，可能落进字符中间）改为
`chat = at + 1`（**字符** +1）。这一处是复查指出的"潜在风险"，
我探的 3 例确实都对，但**它同样是"碰巧对"** —— 所以一并按正确口径改写。

### 🔴 缺陷二：科室判定不处理否定 ⇒ 被否认的症状主导推荐

**实测（让心血管内科有号后）**：

```
'不胸闷，只是咳嗽'    -> 推荐【心血管内科】   ✗
'没有胸闷，就是咳嗽'  -> 推荐【心血管内科】   ✗
'否认胸闷，主要咳嗽'  -> 推荐【心血管内科】   ✗
'咳嗽'（对照）        -> 推荐【呼吸内科】     ✓
```

**危害比"分错科"更隐蔽**：因为**有号校验是通过的**，
响应 `reason=OK`、还附了真实医生与号源 ⇒ **看起来权威而确定**，
患者很可能照着去挂错科。

**根因**：红色保险丝那条路处理了否定，科室判定这条路用的是**裸 `seg.contains(kw)`** ——
同一语义两处实现，**只改了一处**。这正是本项目反复吃过的"两套口径"病
（登录名归一、连接参数、文档数字……这次是第三次换了个面孔）。

**修法**：`guessDepartment` **复用同一套函数**（`redFlagSegments` + `redFlagHit`），
不再自己写匹配。`negated` 传 `None`，把"科室判定不需要留被否定的依据档"这个意图显式化。

### ★ 测试补法：按**类别**扫（这是本次最重要的改动）

复查指出我"逐点修"。对应地，测试也改成**系统性组合**而不是再补几个样例：

| 新增用例 | 规模 | 作用 |
| --- | --- | --- |
| `rtWidthMix` 正向 | **160 组**（16 种前缀宽度 × 10 种否定写法） | 任何"只在某些宽度组合下错"的实现必然被覆盖 |
| `rtWidthMix` 反向 | **112 组**（16 种前缀 × 7 种真征象） | 防止"矫枉过正成一律不报" |
| `rtWidthMix` 复查样例 | 8 条 | 逐条钉住复查给的具体输入 |
| `rtDeptNegation` | 8 条 | 含混排与对照（真的胸闷仍须给心内科） |
| `triage-check.ps1` [5b]/[5c] | 10 + 4 条 | HTTP 层端到端 |

### ★ 顺带扫出的第 3 处实例（**恰好安全**，但把前提钉成测试）

按类别扫全仓后，`parseDsn` 也在同一个表达式里混用了两者：
`authority[(at + 1)..]` 的 `at` 来自 `lastIndexOf("@")`，是**字节**偏移。

我实测确认它**恰好是安全的** —— 因为它搜的分隔符（`/ @ :`）全是**单字节 ASCII**，
`x + 1` 又恰好是"跳过那个 1 字节分隔符"，整个解析**自洽地待在字节空间**里。
但这属于"**碰巧对**"：正确性依赖"分隔符一定是 1 字节"这个**没被写下来**的前提。

⇒ 处置：**不重写没坏的东西，但把它的前提写成测试** ——
`selftest` 新增 6 条 DSN 断言（用户名/密码/主机/库名含中文），
哪天有人把分隔符改成多字节、或某处改成字符下标，它会立刻变红。

| `src/schema.cj` | 新增 `previsit_session`（**第三类表**，见下） |

| `tests/previsit-check.ps1` | HTTP / SSE 端到端（含帧格式与越权） |

### ★★ 核心：把 brief §5.2 那条纪律**落成结构**

brief 把"必须分开处理"点名为**本节最容易做错的地方**，所以代码结构上就分开：

| | 走什么 | 为什么 |
| --- | --- | --- |
| **对话文本**（追问的话） | **SSE 流式** | 它就是自然语言。流错了患者看到半句话 —— **他只会再问一次，无害** |
| **业务值**（问诊单字段） | **普通 JSON，一次性** | 流错了客户端可能已把它写进病历草稿 —— **那是医疗记录污染** |

具体到实现，这体现为两个不共用的产出路径：
`previsitAssistantLines()` 产出**要流出去的句子**；
`PrevisitForm` 是**有类型、有校验的结构化值**，只在 `complete()` 为真时出现在响应里
（未完成时**连 `form` 字段都没有**，只给 `filled/total_slots` 进度）。

> 📌 还有一条不那么显眼但同样重要的：`POST .../answer` **刻意不用 SSE**。
> 它返回的"已填项数 / 是否完成"是**业务值** —— 流式会让客户端拿到中间态
> （"已完成 3/6" → "4/6"），而它可能已经据此更新了界面。

### ★ 新增的**第三类表**：`previsit_session`

加这张表时 `selftest` **第四次**报红（它就是这么设计的），并暴露我原来的分类是错的：

| 类别 | 表 | 数据访问范式 |
| --- | --- | --- |
| 号源/挂号域 | `schedule` `appointment` | 直接 SQL（ADR-0001 §4.3 **锁死**只准 `BookingRepo` 写） |
| 配套域 | `department` `doctor` `patient` `medical_record` | 内存 Store（整表替换刷盘） |
| 鉴权域 | `auth_user` `auth_token` `auth_login_attempt` | 直接 SQL |
| ★ **预问诊域** | `previsit_session` | 直接 SQL，**但不属号源域**（由 `PrevisitRepo` 独占） |

原来只有"业务表 6 + 鉴权表 3"两个数字，而 `previsit_session` **两边都不属** ——
硬塞进"业务表"会让那个数字失去含义。所以改成**四个人口都有的分项**，
并额外断言"四类互不重叠 + 并集 == ALL_TABLES"：
**加表时忘了归类会立刻变红，而不是悄悄混进某个数字里。**

同时钉住两条否定断言：
- ★ 预问诊表**不属号源域**（否则会被误当作可扣号的路径）；
- ★ 预问诊表**不属内存 Store 负责的表**（它是医疗数据，必须立刻持久化，不能进"整表替换"范式）。

### 诚实标注的边界

| # | 边界 | 说明 |
| --- | --- | --- |
| 1 | **追问文本是规则生成的，不是模型生成的** | 与分诊同一阻塞（Q6 合规）。接模型只需替换 `previsitAssistantLines()` 一个函数；会话状态机 / 流式帧 / 业务值校验**一行不用改** |
| 2 | **流式响应一旦开始写出，就无法再改为错误码** | 这是 HTTP 的固有限制，不是缺陷。所以"空主诉"这种情况的处理是**照常开流 + 用第 1 个问题去问**，而不是回 400。已把这个行为**钉成断言**（免得将来被误改成"先回 400"而破坏流式） |
| 3 | **SSE 由服务端分帧，不是真·增量生成** | 现在文本是一次生成完再逐句写出的（对患者是打字机效果）。真·逐 token 流式需要模型侧流式，属接模型时的事 |
| 4 | **`timeout(15000)` 中间件不会中断流式 handler** | 与 P1 记录的边界同源（同步 handler）。流式响应本来就可能超过 15s，这里没有额外保护 —— 如实记录 |

### 变异测试：本轮 "未发现" 的那次值得记下来

变异"`find` 去掉 `patient_id` 过滤"（会话隔离失效）**第一次跑时我的判定脚本报了"未被发现"**，
但实际输出里明明有 27 项 `[FAIL]`。原因是我用 PowerShell 匹配带 ANSI 颜色的输出、
且把 `[FAIL]` 计数写成了对 `$o`（而非解析后的文本）计数 —— **是我的判定脚本坏了，不是测试没抓到。**

改用**退出码**判定后重跑：变异被抓住。
再把变异改成"**合法查询、仅失去隔离**"（保持占位符数一致，避免变成 bind 错误）后：

    [FAIL] ★★ ② 别的患者读不到
    [FAIL] ★★ ③ 别的患者写不了
    [FAIL] ④ 篡改未生效
    [FAIL] ★★ ⑩ 采完后别的患者依然读不到

⇒ **4 项语义失败**，证明隔离断言真的在守。

> 📌 这一节本身也是个教训：**变异测试的"判定脚本"也要可信。**
> 我第一次的"未被发现"是假警报 —— 如果就此认为"测试没覆盖"，
> 会去改一个本来正确的测试。**看到"未被发现"时，先怀疑判定方式。**
