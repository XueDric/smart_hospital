## 2. ★ 并发压测：这是本增量最有价值的部分

### 为什么必须用独立进程

本仓库（框架 + 应用）**通篇没有 `spawn`**，仓颉 1.2.0 的多线程用法在本项目无先例。
而"并发"的真实形态本来就是**多个客户端同时打同一号源** ——
所以脚本起 N 个 **`curl.exe` 独立进程**，各自建独立 HTTP 连接。

这补上了 [ADR-0001](adr/ADR-0001-号源与挂号独立MySQL路径.md) 明确标注的验证边界：

| AC | 层级 | 证明什么 |
| --- | --- | --- |
| **AC-1**（P0 单测） | 数据库层 | 「过期 version 的 UPDATE 必返回 0 行」= 原子性**根因** |
| **AC-9**（P1 压测） | 端到端 | 「N 个真实并发请求打同一号源，**成功数恰好等于号源数**」 |

### 实测结果（三种工况全绿）

| 工况 | 请求 | 号源 | 成功 | 409 | 余量 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 供不应求 | 20 | 8 | **8** | 12 | 0 | ✅ 恰好卖光 |
| 高压 | 50 | 10 | **10** | 40 | 0 | ✅ 恰好卖光 |
| 供大于求 | 5 | 20 | **5** | 0 | 15 | ✅ 全成功、余量正确 |

断言含**余量守恒**：`remain_num + 有效挂号单 == total_num`（三种工况都成立）。

## 3. ★ 压测抓出的真缺陷（已修）

### 3.1 少卖：**乐观锁策略本身有问题**（rev.3 已改策略，不是加大重试）

> ⚠⚠ **本节结论已被 2026-10-07 第三方复查推翻并重修，保留原文以便对照"当时怎么误判的"。**
> 当时的处置是"把 `MAX_BOOKING_RETRY` 从 2 升到 3、HTTP 层给 6"，并**只验了 20抢8 / 50抢10
> 这类有余量的工况**。复查方用"**请求数 == 号源数**"这个最穷工况重测，发现**仍然少卖**
> （20→15、40→26，耗竭率 15%~50%），也就是说**当时的"已修复"是假的**——
> 旧文档 §3.1 那句「修复后：同样工况 → 恰好 8 个成功」只覆盖了宽松工况。
>
> **真正的根因**：`version = ?` 乐观锁在"每个请求都互相撞车"时把重试预算耗尽，
> 而**重试预算再多也治不好**——因为 N 个请求会反复读到同一个新 version、反复互撞。
> **正确处置**：去掉 version 前置条件，改为**一次成功的原子自减**
> （`remain_num > 0` 条件已足够保证不超卖）。实测：20/30/40/50 抢同数号源**全部卖光**。
>
> 详见 [ADR-0001 rev.3](adr/ADR-0001-号源与挂号独立MySQL路径.md)（含"为什么去掉 version 更正确"的论证）。
> 新增回归闸门：单测 **AC-10** + 更严格的分档压测（`请求数 == 号源数`）。

**现象**：20 并发抢 8 号，只卖出 **6** 个，`remain_num = 2`（剩两个号没人抢到）。

**性质**：失败方向是**少卖**而不是超卖 —— 安全方向，但**仍然是错的**
（有号却挂不上，患者会以为没号了）。

**根因**：`MAX_BOOKING_RETRY = 2`（共 3 次尝试）。20 个进程同时重读 version、
又同时失败，3 次预算不够。每次重试都要一次读+写往返，冲突窗口没被拉开。

**处置**：
- `MAX_BOOKING_RETRY` 2 → **3**（安全范围上限）；
- 新增 **`HTTP_BOOKING_RETRY = 6`** 作为 HTTP 层的重试预算（`book()` 的 `maxRetry` 已是具名可选参数）。

**修复后**：同样工况 → 恰好 8 个成功、余量 0。

> ⚠ **这不是"调大重试就完事"**：重试是有代价的（每次都是额外往返）。
> 真到重试也扛不住的量级，正确处置是 ADR §3 的**方案 C（悲观锁）或加排队**。
> 本 ADR §8 复审触发条件第 1 条就是为此写的（耗尽率 > 1% → 重估方案 C）。

### 3.2 退号响应自相矛盾

**现象**：退号成功返回 200，但 body 里 `status` 还是 `"booked"`。

**根因**：handler 用了**取消之前**读的那份快照（`appt`）回包。

**处置**：取消后**重读**再回（`Cancelled` 与 `SlotNotRestored` 两条路径都改了）。
自相矛盾的响应比不返回还糟 —— 客户端会以为没退成。

### 3.3 测试脚本自己写错了两处（比不写更糟）

| 坑 | 现象 | 性质 |
| --- | --- | --- |
| `Start-Process -ArgumentList` **拆坏含空格的参数** | `"X-Role: patient"` 到达 curl 变成 `"X-Role:"` → 每个请求都 401，压测显示"0 成功" | **假失败**：看起来像"服务端拒绝并发" |
| 断言不分工况 | "5 并发抢 20 号"（本就该剩 15）被无条件断言"必须卖光"→ 报 3 项失败 | **假失败**：服务端是对的，是断言写错 |

**处置**：header/body 全部走 curl **config 文件**（`-K`），命令行只剩无空格路径；
断言按 `$exhausted = ($Tokens -ge $ScheduleTotal)` **分两种工况**。

> 这两个坑值得单独记：**测试写错会让人去改对的代码。**
> （P0 也踩过同类：变异测试时测试静默崩溃、以及 `exec()` 返回值当自增 id 导致假通过。）

### 3.4 另外两个实测坑

- **curl config 里反斜杠是转义符**：`@C:\Users\...` 被读成 `C:Users...` → 路径必须写正斜杠。
- **PowerShell 的反引号转义在数组拼接里原样写入**：JSON 变成非法串 → `400 Invalid JSON`。
  处置：body 写独立文件，config 用 `data = "@文件"`。

## 3.5 ⚠ 本增量的**临时形态**（必须知道，别当成已完成）

### 4.1 鉴权是开发态的，不是令牌

| 项 | P1 现状 | 搬迁前／目标 |
| --- | --- | --- |
| 身份来源 | `X-Role` / `X-Patient-Id` 请求头 | 不透明令牌 + PBKDF2 三阶段加锁 |
| 开关 | 必须显式 `--dev-auth` | — |
| 审计 | 每请求打 `[DEV-AUTH]` 警告 | 全链路审计 |
| 生产保护 | `--prod` 与 `--dev-auth` 同传 → **拒绝启动** | — |

**为什么用命令行开关而不是环境变量**：本工具链的仓颉 std **没有 `getEnv`/`envVars`**
（框架 `config.cj:17-21` 逐字核对过），搬迁前也因此明说"不支持环境变量配置，只能走命令行"。
用环境变量会**静默永远不生效** —— 那比没有更糟（以为生产被保护了，其实没有）。

### 4.2 默认只绑 127.0.0.1

轻舟 `app.serve(port)` 默认 `bindAddr = "0.0.0.0"`（整个局域网可连），而本阶段是
**明文 HTTP + 开发态身份头**。所以 `serve` 默认**只绑本机**，联调再显式 `--bind 0.0.0.0`。

## 4. ★ 令牌鉴权（已上线，`--dev-auth` 降为可选联调开关）

### 4.1 口径

| 项 | 做法 |
| --- | --- |
| 口令 | **PBKDF2-HMAC-SHA256，100000 次迭代**，16 字节随机盐（照搬迁前口径） |
| 令牌 | **32 字节随机 → 64 位 hex**，落 MySQL `auth_token` |
| 会话模型 | **有状态**（服务端存 token → user），**不是无状态 JWT** ⇒ 停用账号/改口令能**立即踢下线** |
| 有效期 | 30 天，**滑动续期**，但用 `last_renew_at` **节流到每天最多写一次** |
| 回收 | 签发时顺手清过期令牌（搬迁前的"tokens 表只增不减"教训） |
| 防枚举 | 账号不存在时**照样跑一次完整 PBKDF2**（假材料），且与口令错误**返回同一个错误码** |
| 比较 | 口令摘要用**定时安全比较**，不在第一个不同字节返回 |

### 4.2 ★ 密码学是"验过"的，不是"抄过"的

`hospital-server.exe authtest` 用**三个公开测试向量**钉住 PBKDF2：

| 向量 | 来源 |
| --- | --- |
| `pbkdf2("passwd","salt",1,64)` | RFC 7914 §11 |
| `pbkdf2("Password","NaCl",80000,64)` | RFC 7914 §11 |
| `pbkdf2("password","saltSALT",100000,32)` | 与 .NET `Rfc2898DeriveBytes` 对拍（**正式参数档**） |

外加：非法参数（`iters<=0` / `dkLen<=0`）必须 **fail closed 返回空**，不得静默降级成 1 轮。

> `serve` 启动时**先跑 authtest 再连库** —— 否则连上库也只是在用错的哈希签发令牌。
> 另有独立子命令 `authtest`，不需要数据库。

### 4.3 ★ 防枚举：实测计时比值 **1.01 ~ 1.06**

搬迁前记过：未防护时"账号存在/不存在"的登录耗时差约 **13 倍**，登录接口本身就是个账号枚举器。
本项目实测（各 5 次）：

| 场景 | 平均耗时 |
| --- | --- |
| 账号存在但口令错 | 473.9 ms |
| 账号不存在 | 448.3 ms |
| **比值** | **1.06** ✅ |

对医院尤其要紧：**"谁在本院看过病"是最该保护的一类信息。**

### 4.4 接口

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | 无（换令牌） |
| POST | `/api/v1/auth/logout` | 需令牌（吊销当前令牌） |
| GET | `/api/v1/auth/me` | 需令牌 |
| POST | `/api/v1/admin/users` | 仅管理员（已存在 → **409**，不静默复用） |
| GET | `/api/v1/admin/users?login_name=` | 仅管理员（**只回非敏感字段**，绝不回盐/摘要） |
| POST | `/api/v1/admin/users/:id/password` | 仅管理员（★ **同时吊销该账号全部令牌**） |

### 4.5 ★ 引导问题：第一个管理员怎么来

`POST /admin/users` 需要管理员身份，而第一个管理员还不存在 —— 鸡生蛋。
所以引导入口**不经 HTTP**：

```powershell
.\build\hospital-server.exe create-admin <dsn> [登录名]
```

口令本机随机生成、**只打印一次**、不落盘；账号已存在则改口令（并吊销其全部令牌）。
它与"直接改 `auth_user` 表"等价，**不引入新的信任假设**（能改库的人本来就能改任何东西）。

### 4.6 `principalOf()` 与 `can()` 解耦 —— 换鉴权零业务改动

从开发态身份头切到令牌，**业务逻辑与权限矩阵一行未改**：唯一改点是 `principalOf()` 的实参。

解析优先级：
1. **`Authorization: Bearer <token>`** —— 正式路径（先看，避免"以为在用令牌其实在用头"）；
2. 开发态头 `X-Role`/`X-Patient-Id` —— **仅 `--dev-auth` 下**，每请求打警告；
3. 都没有 → **401，明确失败**（不静默放行）。

实测确认：**未开 `--dev-auth` 时，`X-Role: admin` 头被忽略并返回 401**。

### 4.7 与搬迁前服务端的差异（如实标注）

| 项 | 搬迁前 | 本侧 |
| --- | --- | --- |
| 令牌存储 | 内存 `s.tokens` + 整库刷盘 | **直接 SQL `auth_token`**（当时的两种范式，见 ADR-0001 §4.2；内存 Store 已于 rev.7 拆除） |
| 表名 | `tokens` | **`auth_token`**（避撞名：搬迁前的库里已占用 `tokens`） |
| 三阶段加锁 | 有（PBKDF2 移出全局锁） | **不需要** —— 无全局锁，PBKDF2 天然不在锁内 |
| 角色 | 原业务角色 | 患者/医生/管理员三端 |

> ⚠ 仍**未做**：登录限流/锁定、口令强度校验、令牌按设备管理、证书信任分发与轮换。
> 这些都不该在明文 HTTP 上宣称"已完成"。

## 5. ★ HTTPS（已上线）—— 填掉上一轮标注的最大安全缺口

### 5.1 用法

```powershell
# 1) 生成带 SAN 的自签证书（本机所有 IP + localhost + 127.0.0.1 + ::1 都写进 SAN）
cd server
.\new-tls-cert.ps1

# 2) 启动 HTTPS（用脚本产出的**纯 ASCII 运行副本**，原因见 §5.4）
.\build\hospital-server.exe serve <dsn> --port 8443 --tls-files "C:\ProgramData\smart-hospital\tls\tls.env"
```

`serve` 新增 `--tls-cert` / `--tls-key` / `--tls-files`。
**不给 TLS 参数则跑明文 HTTP，并明确打印警告**（令牌与口令会明文过网）。

### 5.2 ★ 绝不静默降级（四条已实测）

| 场景 | 行为 | 实测 |
| --- | --- | --- |
| 证书文件不存在 | FATAL 退出，**不回退明文** | ✅ exit=1 |
| 私钥文件不存在 | FATAL 退出 | ✅ exit=1 |
| PEM 内容非法 | FATAL 退出（框架抛 `Failed to parse PEM`） | ✅ exit=1 |
| 只给了 cert 或只给了 key | 直接拒绝（多半是命令行打漏） | ✅ exit=2 |

而且验证过：这些情况下**端口不会被误起成明文服务**。

> 为什么这条最重要：静默降级会让"HTTPS 没起来"变成一台**看起来正常的明文服务**——
> 客户端照样能用，没人会发现问题。

### 5.3 TLS 验证结果（`tests\tls-check.ps1`）

| 项 | 结果 |
| --- | --- |
| 证书有 SAN 且含 IP 条目 | ✅ 8 个条目（DNS=localhost + 7 个 IP） |
| TLS 1.2 握手 + **真校验**（链 + 主机名） | ✅ 协商 Tls12 |
| TLS 1.3 握手 + 真校验 | ✅ 协商 **Tls13** |
| TLS 1.0 / 1.1 被拒 | ✅（服务端侧，SSPI 失败） |
| 反向：不在 SAN 里的主机名/IP 必须不覆盖 | ✅ |
| 反向：用**不同的 CA** 验证必须失败 | ✅ |
| 明文打 TLS 端口必须失败 | ✅ 000 |
| HTTPS 下登录 + 带令牌调 `/auth/me` | ✅ 200 |

**不冒充的两点**（如实标注）：
- **TLS 1.0/1.1 的拒绝是"服务端拒绝"还是"客户端不肯发起"？** 本脚本用 .NET `SslProtocols.Tls`/`Tls11`
  显式发起，得到的是**服务端侧 SSPI 失败**，属于服务端拒绝；但要**绝对硬**的证据需
  `openssl s_client -tls1`，而**本机没有 openssl**，所以脚本把这一点写成了 INFO 而非静默通过。
- 验收依据仍是 `SOURCE-MANIFEST.sha256` + 测试结果。

### 5.4 ★ 为什么证书要放 `C:\ProgramData\smart-hospital\tls`

**根因：本工具链的仓颉运行时无法接受含非 ASCII 的 argv** ——
在 `main` 之前就抛 `IllegalArgumentException: Invalid unicode scalar value`，
连 usage 都打不出来（搬迁前的 API 踩坑记录 坑 6）。当时的仓库路径还叫「智能医院客户端」（含中文），
所以 `--tls-cert "...\智能医院客户端\server\certs\cert.pem"` **必然启动失败**（实测确认）。

> **后续更正（2026-10-17）**：仓库已改名为 `E:\harmonyOS\smart_hospital`（纯 ASCII），
> `--tls-cert` 直接传仓内路径**现在可用**；ASCII 运行副本的做法保留为「部署到含中文目录」及「私钥与源码树隔离」的兜底。

试过的两条"看起来能绕"的路，**实测都不行**（记下来省下次时间；前提是路径里确实有中文）：

| 尝试 | 结果 |
| --- | --- |
| `--tls-files <配置文件>`（路径写文件里） | ❌ **配置文件自己的路径**也在中文目录下 → 照样炸 |
| Windows 8.3 短名（`GetFile().ShortPath`） | ❌ 本卷**禁用了 8.3 名**，返回的还是长名 |

**可行解**：把证书/私钥复制到一棵**纯 ASCII 目录树**（`%ProgramData%\smart-hospital\tls`），
配置文件也放那里、内容里只有 ASCII 路径 ⇒ 命令行与文件内容**全 ASCII**。
`new-tls-cert.ps1` 会自动产出这份副本，并用 `icacls` 把该目录 ACL **收紧到
当前用户 + Administrators + SYSTEM**（私钥不外泄）。

`--tls-files` 这个参数因此**保留**（它把路径从命令行挪进文件，仍能隔离 shell 转义与长路径问题），只是**任何含中文的部署路径下必须指向 ASCII 路径**。

### 5.5 五个实测踩到的坑（都影响正确性，不是小事）

| # | 坑 | 现象 | 处置 |
| --- | --- | --- | --- |
| 1 | .NET Framework 的 RSA 是 `RSACng`，**没有** `ExportRSAPrivateKey()` | `new-tls-cert.ps1` 报「RSACng 不包含名为 ExportRSAPrivateKey 的方法」 | 按 RFC 8017 A.1.2 **手工构造 PKCS#1 DER**（含"INTEGER 最高位为 1 要补 0x00"） |
| 2 | **自签证书必须 `CA:TRUE`**，否则 Schannel 不认 | `curl --cacert cert.pem` 报 `schannel: error 0x00000010`（而 `curl -k` 是 200 ⇒ 握手本身没问题） | 生成时置 `BasicConstraints(CA:TRUE)`。**安全性没变差**：持有该私钥本就能签发任意证书 |
| 3 | `SslStream` 回调里拿到的证书对象**回调返回后失效** | 主体/指纹全空，`X509Chain.Build` 报「链上下文句柄无效」 | 回调里**立刻 `Export(Cert)`** 取出 DER 字节，之后用 DER 重建证书 |
| 4 | **IP SAN 是二进制**，不能按文本搜 | `Encoding.ASCII.GetString(san) -match '127\.0\.0\.1'` **永远不匹配**（会误判"证书没覆盖本机 IP"） | 按 ASN.1 解析 GeneralNames，tag `0x87` 取出字节转 `IPAddress` 再比 |
| 5 | `New-Object X509Certificate2(,$bytes)` 命中"按文件加载"重载 | 报「指定的路径或文件名太长」（把 DER 当路径了） | 显式 `[byte[]]` cast：`-ArgumentList @(, $derBytes)` |

## 6.5 ★ 第三方复查（2026-10-07）：3 严重 + 2 中等 + 若干轻微，全部已修

这一轮是**外部复查**驱动的修复，**发现了 3 个我自己没发现的严重缺陷**，
其中 2 个是"我以为已经修好了其实没有"。全部有回归闸门。

### 6.5.1 🔴 严重①：`client_token` 未按患者隔离（**跨患者数据泄露**）

| 项 | 内容 |
| --- | --- |
| 现象 | 患者 B 提交**患者 A 用过的** `client_token` → 命中 A 的单并**原样返回**：既不扣号，也不报错。B 拿到了 A 的挂号单内容，同时以为自己挂上了 |
| 根因 | `client_token` 是**客户端自己**生成的字符串（契约就是 `"booking-1"` 这类），而唯一索引与查询都是**全局**的 |
| 修法 | 唯一索引改 `(patient_id, client_token)`；查询同样带上 `patient_id` |
| 实测 | 修复后患者 B 提交同一 token → **拿到自己的单（`patient_id=2`）并真实扣号**（`seq_no=2`） |

**同一处还暴露了第二层**：退号后同 token 重挂 → 命中那张**已取消**的单 → 患者拿到
`cancelled` 却以为挂上了。修法：只把 `status <> 'cancelled'` 当幂等命中。

**第三层（修第二层时才发现）**：只在查询侧过滤 cancelled **不够** ——
唯一索引仍被那张老单占着，重挂 INSERT 直接撞唯一键 → **500**。
修法：**退号时把 `client_token` 置 NULL 释放**（MySQL 唯一索引允许多个 NULL）。
且必须补一步**存量数据归位**：迁移前就已取消的单，其 token 仍是原值 ——
漏了这步就只在"特定历史路径"上炸（实测复现）。

### 6.5.2 🔴 严重②：少卖在**最穷工况**仍复现（命中 ADR §8 复审阈值）

| 项 | 内容 |
| --- | --- |
| 现象 | **请求数 == 号源数**时仍少卖：**20→15~17、30→22~23、40→25~26**（耗竭率 15%~50%） |
| 关键 | 我之前只验了 `20抢8 / 50抢10` 这类**有余量**的工况 —— **恰好绕开了这个点** |
| 性质 | 失败方向是少卖（安全方向），但**有号挂不上**，患者会以为没号了 |
| 根因 | `version = ?` 乐观锁：N 个请求同时读同一 version，只有一个能成功，其余作废；重试又互撞，预算迅速耗尽。**加大重试治不好** |
| 修法 | 去掉 version 前置条件 → **一次成功的原子自减**（`remain_num > 0` 已足够防超卖） |
| 实测 | **20/30/40/50 抢同数号源 → 全部恰好卖光、余量 0、零少卖** |

> 这也是「**测试的工况选窄了，等于没测**」的教训：宽松工况下旧实现看起来完全正常。

### 6.5.3 🔴 严重③：`--tls-files` 会**静默降级成明文**

| 项 | 内容 |
| --- | --- |
| 现象 | 给一个**只有注释**（或键名大小写不符）的 `tls.env` → 解析出空 cert/key → `wantTls` 为 false → **静默按明文 HTTP 启动**（实测起在 8092 且 `/health` 返回 200） |
| 性质 | ★ **违反本文件 §5.2 自己承诺的"绝不静默降级"** —— 承诺与实现脱节比没有承诺更危险（运维会相信它） |
| 修法 | 引入 `tlsFilesGiven`：只要**表达了要 TLS**（给了三个 TLS 参数之一）而最终没凑齐 cert+key → **拒绝启动**；解析后立即校验 `cert=`/`key=` 是否存在 |

### 6.5.4 🟠 中等④：`cancel()` 幂等路径**吞掉运维告警**

| 项 | 内容 |
| --- | --- |
| 现象 | 第 1 次退号（`remain_num == total_num` 归还失败）→ `SlotNotRestored` + 告警（诚实）；**第 2 次（用户重试）→ `Cancelled`，告警消失** |
| 根因 | 幂等快路径无条件返回 `Cancelled`，而 `Cancelled` 的语义是"已取消**且号已归还**" |
| 修法 | 落库 `appointment.slot_restored`，幂等路径**按真实状态**回报 |
| 实测 | 第 2 次退号现在也返回 `slot_restored: false` + 告警 |

### 6.5.5 🟠 中等⑤：`accept` 清库守卫**把生产库名列入白名单**

| 项 | 内容 |
| --- | --- |
| 现象 | 原判据 `!db.contains("test") && db != "hospital"` —— 挡住了 `hospital_x`，却**恰好放行唯一的生产库名 `hospital`**，而 `accept` 会 DELETE **6 张表** |
| 性质 | 守卫**是反的**：最该拦的那个被放过 |
| 修法 | 只认库名含 `test` 的显式测试库；`hospital` 不再例外。并补 `create-db` 子命令方便建测试库 |

### 6.5.7 🔴🔴 **第二份**外部复查（2026-10-07 晚）：又是 1 严重 + 1 中等 + 漂移

**这一轮的严重缺陷是本轮最值得记的一条，因为它暴露的是我的"修法不彻底"，
而不是"没发现"。**

#### 🔴 严重⑥：并发退号会**永久丢号源** —— 少卖那个根因我只修了一半

| 项 | 内容 |
| --- | --- |
| 现象 | N 个人**同时退号**，只有极少数能真正归还 —— **其余号源永久消失**，需管理员手工重置。而**每个患者都收到"退号成功"的 200 响应** |
| 实测 | 我自测复现：**10 个号源、10 张单同时退 → 只归还 5 个，丢 5 个**（`remain_num=5`，应为 10）。复查给的更细的表显示 **3 人同时退就已经中招**（丢 1 个）—— **不是极端工况** |
| 根因 | ★ **同一个根因，出现在"镜像路径"上**：我修 `tryDeductSlot` 时去掉了 `version = ?` 前置条件，但 `releaseSlot` **仍然带着它**，而 `releaseSlotFor` **没有任何重试**（注释里却写着"重试代价可接受"——**代码里根本没有重试**，注释在撒谎） |
| 修法 | 与扣号**完全镜像**：去掉 version 前置条件。`remain_num < total_num` 与 `remain_num = remain_num + 1` 在同一条 UPDATE 内原子求值，InnoDB 行锁让并发 UPDATE **串行**执行 ⇒ N 个号源**全部归还**，且"不得超过放出量"的护栏仍在 |
| 实测（修复后） | **10/10、20/20 全部归还，零丢失**，`remain_num` 精确回到 N |
| 回归闸门 | 新增 **AC-11**（N 次归还全部成功 + 反向断言"满员时再归还必失败"，防超发）。**已做变异测试**：把 version 条件塞回去 → 当场 8 项 FAIL，证明它有牙齿 |

> 📌 **本轮最重要的一条教训**：**同一个根因会在镜像路径上重现。**
> 修"扣"的时候必须顺手核对"还" —— 两者用的是同一个错误模式
> （version 前置条件 + 无重试），我只改了其中一个。
> 现在 AC-10（扣）与 AC-11（还）**必须同时绿**，把这个核对固化了。
>
> 📌 第二条教训：**注释撒谎比没有注释更坏。** "重试代价可接受"这句暗示了一个
> 不存在的缓解措施，会让人跳过真正的失败路径。已改正，并在注释里写明"为什么不带 version"。

#### 🟠 中等⑥：`seq_no` 响应值与落库值不一致

| 项 | 内容 |
| --- | --- |
| 现象 | 退掉 `seq_no=1` 的单后再挂，库里落 `seq_no=2`，而 **HTTP 响应报 `seq_no=1`** |
| 根因 | 落库用 `nextSeqNo()`（`MAX(seq_no)+1`，**不回收**已用过的号），而响应回填用 `countBooked()`（统计**当前有效**单数）—— **两个口径根本不是一回事** |
| 修法 | 把真正写进库的那个 seq 经 `TxResult` 带出来回填；新写 `MAX+1` 是对的，错的是回填 |
| 回归闸门 | 新增 **AC-12**：直接读库比对"响应 == 落库"，并断言退号不回收序号 |

### 6.5.8 ✅ 本会话收尾两项（用户指定）：登录限流 + 内存 Store / AC-4 闭合

#### ① 登录限流 / 失败锁定

| 项 | 内容 |
| --- | --- |
| 为什么 | 没有限流时**在线爆破只要一个循环**（PBKDF2 只让离线爆破变贵），而且能把服务端 PBKDF2 当 **CPU 放大器**打（每次尝试烧 0.55s CPU） |
| 参数 | 5 次失败 / 15 分钟窗口 / 锁 15 分钟。**刻意不用永久锁定** —— 永久锁会让攻击者用"故意输错"对真实用户做拒绝服务 |
| 存储 | 新增表 `auth_login_attempt`，键是登录名的 **HMAC-SHA256**（固定 key）。★ **单独一张表**的理由：**账号不存在时也必须计入限流**（放在 `auth_user` 列上则"对不存在的登录名狂试"完全不受限，而那正是试用户名的手法） |
| ★ 防枚举 | 限流**不是** oracle。计数表与 `auth_user` **无外键** ⇒ "连续输错 5 次"对存在/不存在的名字**结果完全一样**。<br>实测：`admin` → `401,401,401,401,429`；`nobody-no-such-user` → `401,401,401,401,429`（**同一点切换**）。计时比值 1.03 |
| ★ 不放大 CPU | 锁定检查在 PBKDF2 **之前**。实测：解冻期失败 `t≈0.55s`，锁定期拒绝 `t≈0.02s`（已写成断言 `< 0.2s`，防将来有人把闸门挪到后面） |
| 一个我判断错后查清的点 | 转点是**第 5 次**变 429（不是我最初以为的第 6 次）。核对后确认**代码是对的**：第 1~5 次都是真实的口令尝试（都跑了 PBKDF2），第 5 次失败使计数达阈值 ⇒ **即刻**锁定。<br>**好处是没有为了限流而少给用户尝试机会。** 我改的是断言，不是代码 —— 不拿代码去迁就自己的猜测 |
| 清理 | 成功登录**清零**计数（否则"失败 4 次 + 成功 1 次"留着 4 次，下次错 1 次就被锁）；`pruneAttempts()` 清陈旧行（否则随机登录名能刷爆这张表 —— 搬迁前 tokens 表"只增不减"就是这个坑） |
| 错误码 | `AUTH_RATE_LIMITED` = **429** + `Retry-After` 头 |

新增 `LoginOutcome` 类替代 `?(Int64,String,Int64)`：登录现在有**三种**结局
（成功 / 凭据不对 / 被限流），元组 + Option 只能表达两种 —— 硬塞会把"被限流"伪装成
"凭据不对"，客户端就拿不到"等多久再来"。

#### ② 内存 Store 落地 + AC-4 从"结构性"升级为"真跑一次刷盘"

P0 把 AC-4 的完整回归挂到 P1（写在本 ADR 的"验证边界"里），这次还掉了。

  · `mem_store.cj`：配套域（`department`/`doctor`/`patient`/`medical_record`）的内存 Store，
    照搬迁前 `store.cj` + `writeDbToMysql` 的**本质**：**一个事务内整体替换清单里的表**；
  · `sql_recorder.cj`：实现 `DbBackend` 的**录制装饰器**，把实际发出的 SQL 全记下来。

**AC-4 现在是四层断言**（逐层加强，只做前两层是**弱**的）：

| 层 | 验什么 | 为什么必须有 |
| --- | --- | --- |
| ① 机制 | `MEM_TABLES ∩ BOOKING_DOMAIN_TABLES = ∅` | 根因层：遍历源里就没有号源域 |
| ② **SQL 痕迹** | 刷盘发出的**任何一条** SQL 里都不出现 `schedule`/`appointment` | ★ "**根本没碰**"比"碰了但值没变"强 |
| ③ 逐值比对 | 从 `information_schema` 取**全列**，刷盘前后逐行逐列比对 | 只比 `remain_num` 之类少数列是弱的（刷盘可能改了 `version`/`created_at`） |
| ④ 反向 | 刷盘**确实**改了它该管的 4 张表 | 防"因为什么都没做"而**假绿** |

> ★★ **第 ② 层的价值有一份硬证据**：做变异测试时让刷盘**只读**一下 `schedule`
> （`SELECT COUNT(*)`，**不改任何值**）—— 结果 **② FAIL 而 ③ 仍然 PASS**。
> 这正是"若只做逐值比对就会漏检"的实证。**变异测试做了两道**：
> 把 `TABLE_SCHEDULE` 混进 `MEM_TABLES` → ① 层 4 项 FAIL；
> 让刷盘顺手读 schedule → ② 层 FAIL。

⚠ 仍如实标注的差异：本 Store 用**整表替换**（简化），搬迁前是**脏行裁剪**。
两边都不碰号源域 ⇒ AC-4 不变量成立；且整表替换是**更强**的写放大，
连它都不波及号源域，脏行裁剪版更不会。性能差异不在 AC-4 范围。

### 6.5.9 🔴🔴 **第三份**外部复查（2026-10-07 深夜）：限流可被**一个字符**绕过

#### 🔴 严重⑨：登录限流按**登录名字符串**记，而账号查找 TC 不敏感

| 项 | 内容 |
| --- | --- |
| 现象 | 我实测复现：先把 `admin` 锁死（5 次错口令）→ 再用**正确口令**试，`Admin` / `aDmIn` / `admin␣␣` **全部 200 拿到令牌**。数据库里当时躺着**两份**计数（`fail_count=5` 与 `fail_count=1`） |
| 根因 | 计数键是登录名**原文**哈希，而账号查找走 `utf8mb4_general_ci` + `PAD SPACE`（`'Admin' = login_name` → 1，`'admin ' = login_name` → 1）。**两套口径不一致 ⇒ 换个写法就换一份新预算** |
| 危害（按形态算清楚） | · 字母登录名（`admin`）：大小写变体上限 `2^n − 1` 份预算（`admin` = **31 份** = 155 次/15 分钟）<br>· **尾空格变体**：任意长 ⇒ **无限份**<br>· ★ **纯数字登录名（手机号）没有字母**，大小写变体为 0，但**尾空格照样给无限份预算**（`13800000001` / `13800000001␣` …） |
| 修法 | 库与哈希**共用同一个归一值**：`normalizeLoginName = trimAscii + toAsciiLower`，并在 `findUser` / `createUser` / `login` / `loginNameHash` **全部**先归一。归一只在仓储层做**一次**（只有一处定义，不再有两套口径） |
| 实测（修复后） | `admin` 锁死后：`Admin` / `aDmIn` / `ADMIN` / `admin␣␣` / `␣␣admin` / `\tadmin` / `Admin␣` **7 种写法全部 429**，库里只剩 **1 份**计数。反向也验了：**未锁定时**这些写法全部 **200**（归一只影响计数口径，不改变"能登录"） |

> ⚠ 为什么用 `toAsciiLower` 而不是 locale 感知的 `toLower`：登录名是 ASCII（手机号/工号/字母）。
> locale 感知的转换会引入"同一字符串在不同机器上归一成不同结果"（土耳其语 I 问题那一类），
> 而**归一口径必须跨机器一致** —— 否则限流又能被绕过（换台机器就是新副本）。
> **宁可少归一，也不要"不一致地"归一。**

回归闸门：`rate-limit-check.ps1` 新增第 [3] 节（7 种变体 + 计数行数必须为 1）与第 [9] 节（归一不破坏正常登录）。

#### 🟠 注释谎报：把"可被 DoS"说成了"攻击者最多拖慢自己"

我原先在 `auth_repo.cj` 写着"有限窗口下，攻击者最多拖慢自己，用户等一会儿即可自愈"。
**这句是错的** —— 锁定记在**账号**上，所以知道某人登录名的攻击者**可以故意输错 5 次锁死那个真实用户**
（实测：锁定期内正确口令同样 429）。

已如实改写为：「可被用于对**特定账号**做 15 分钟量级的拒绝服务」，并说明为什么仍然选账号级锁定
（不锁则在线爆破不受限，泄露的是病历；有限窗口让受害者无需人工解锁即可自愈；
彻底消除要按 IP 限流或加验证码，属 P2+）。**不假装没有这个代价。**

#### 🔴 严重⑩：`auth-check.ps1` **不再可重复**、也不再顺序无关

| 项 | 内容 |
| --- | --- |
| 现象 | 复查实测：第 1 次 `25 PASS / 0 FAIL`，**紧接着第 2 次 `13 PASS / 12 FAIL`，登录全部 429** |

#### ① 口令强度校验 —— 关键是"在哪一层强制"

| 项 | 内容 |
| --- | --- |
| 规则（4 条） | ① ≥ 8 位；② 同时含字母与数字；③ 不在常见弱口令表；④ 不等于登录名、也不是"登录名+前后缀" |
| **刻意不要求特殊字符** | 强制特殊字符会把用户推向 `Password1!` 这类**可预测**写法（NIST 明确不建议），收益低、代价是用户改用便签 |
| ★ **强制点在仓储层**（本项最关键的决策） | 设置口令的入口有**三个**：`POST /admin/users`（建号）、`POST /admin/users/:id/password`（重置）、`create-admin`（CLI 引导）。放 HTTP 层 ⇒ **CLI 那条路会漏**，将来再加入口还会漏。放仓储层 ⇒ 只有**一个必经点**，谁都无法绕过（`createUser` 与 `setPassword` 都调 `checkPasswordStrength`）。<br>📌 这正是前几轮反复吃的教训："同一件事有两处实现，迟早漏一处" |
| 顺带修的顺序缺陷 | 原 `setPassword` 是"UPDATE 之后再 revokeAllTokens"，**不检查 UPDATE 是否影响了一行**。现在先确认账号存在（不存在则 404），并且**先校验强度、再落库+吊销** —— 否则弱口令请求会把用户**踢下线**（攻击者拿管理员令牌发一次弱口令请求即可 DoS） |
| 400 而不是 500 | 新增 `UserFacingError` 类型：仓储层用它表达"这是请求不对"，handler 映射成 **400 VALIDATION_FAILED** 并保留原因。<br>⚠ 刻意**不**用"按消息字符串 contains 匹配"—— 改一个字就静默失效，正是本项目反复踩的"两处口径"坑 |
| 实测 | 5 种弱口令全部 400（含"只有数字"`12345678`、常见弱口令 `password`）；强口令通过；**弱口令被拒后用户未被踢下线**（200）；不存在账号 → 404 |

   （"退号释放幂等键"），所以按 token 删匹配不到，每次都残留 ⇒ 条数随运行次数增长。
   已改为按 `(patient_id, schedule_id)` 清，并把断言从"列表长度 == 1"改成
   **"我刚挂的那张在不在" + "条数 == 库中有效单数"**（前者会把别的用例的数据误判成本用例缺陷）。

### 6.5.11 🔴 **第四份**外部复查（2026-10-07）：`create-admin` 约 8.6% 失败

#### 🔴 真缺陷①：口令生成器**不满足自己定的强度规则**

| 项 | 内容 |
| --- | --- |
| 现象 | `create-admin` 约 **8%** 概率直接失败，且失败信息是**堆栈**而不是其它地方统一的 `❌` 清晰提示 |
| 实测（我复现） | 70 次失败 **6** 次 = **8.6%**；理论值 `(21/26)^12 = 7.71%` —— 与复查给的数完全吻合 |
| 根因 | `CODE_ALPHABET` = **21 字母 + 5 数字**（共 26），而 `randCode(12)` 是"独立均匀取 12 个"，**不保证成分** ⇒ 约 7.7% 概率生成"全字母"口令 ⇒ 被本项目**自己**的强度规则②（必须含字母与数字）拒 ⇒ 抛 `UserFacingError`。<br>而 `createAdmin` 的 `try/catch` **只包了建库那段**，于是异常直冒到顶层 |
| ★ 影响面 | `create-admin` 是**唯一的引导入口**（第一个管理员 + 口令找回），约 1/12 概率直接崩 |
| 修法（两条一起） | ① `randCode` **强制成分**：先放 1 个随机字母 + 1 个随机数字，其余位均匀随机，再整体 **Fisher–Yates 洗牌**（不洗牌的话"首位必字母、次位必数字"就成了可预测结构，等于少了几位熵）；<br>② `createAdmin` 把"生成 + 建号"**整体**包进 try/catch，并在失败时**重试一次**（引导入口失败一次代价很高），仍失败则给 `❌ + 处置`，**不冒堆栈** |
| 实测（修复后） | **70/70 成功、0 堆栈**；200 个口令逐位置统计数字占比 **17.5%~28%**（无位置被钉在 0%/100%，证明洗牌生效）；整体数字占比 **22.4%**，与理论期望 **24.4%** 吻合；70/70 无重复 |
| 回归闸门 | `p1-extra-check.ps1` 第 **[5]** 节：40 次 CLI 端到端（原缺陷下期望失败 ≈3 次，足以可靠变红）+ 4 条断言（全成功 / 无堆栈 / 成分齐 / 洗牌生效） |

> ★★ **为什么这个缺陷值得单独记**：它恰好**证明了"强度校验放仓储层"的决策是对的** ——
> 校验确实打到了 CLI 这条路，正是当初论证要防的漏点。只是**生成器没跟上自己定的规则**。
>
> 📌 **教训（新的缺陷类别）**：**"生成器"与"校验器"必须处在同一个契约下。**
> 加校验规则时必须回头问一句：**"我们自己的生成器/默认值/夹具满足这条规则吗？"**
> 这与前几轮"修一处忘同类位置"是同一类病，但更隐蔽 —— 因为它表现为
> **随机失败**（8%，跑一次很可能不复现），而不是稳定报错。
>
> 📌 复查另外**专门验证了数据安全**并确认干净：`checkPasswordStrength` 在**任何写库之前**执行，
> 所以失败**不产生部分状态、旧口令不被破坏**（复现失败后用失败前那次成功的口令登录仍 200）。
> 这一点我认同并保留 —— 它正是"先校验、再落库+吊销"那个顺序修复的价值。

#### 🟠 真缺陷②（**我自己引入的回归**）：补弱口令表时**漏掉了原有的 `admin123`**

复查指出原表漏了"常见词 + 数字"这一整类（实测 `password1` / `password123` 都能通过）。
我补了 40 余条变体 —— 但**重写清单时把原本就有的 `admin123` 漏掉了**，
是测试用例当场抓出来的（那条期望 400 却拿到 **201**）。

已补回，并加齐同类短数字变体（`test123` / `qwerty12` / `abcdef12` / `aa123456` /
`admin12345` / `root1234` / `test123456` / `hospital2026` 等），实测**全部 400**。

> 📌 教训：**改写"清单/白名单"时最容易漏的就是"原本已有的项"。**
> 这次是测试抓到的；如果没有那条用例，就会是一个"补了 10 条却丢了 1 条"的净退化。

#### 同类隐患排查（复查没要求，我自己做了）

按"生成器 × 校验器"这个新类别，逐个查了其余 CLI 子命令有没有同类问题
（"自身产物被自身规则拒"或"异常未捕获直冒堆栈"）：

| 子命令 | try | 可能抛异常的调用 | 结论 |
| --- | --- | --- | --- |
| `selftest` | 0 | 0 | ok（纯本地断言） |
| `check-db` | 1 | 3 | ok |
| `accept` | 1 | 2 | ok |
| `create-db` | 2 | 0 | ok（新增 `--admin-dsn`，见 P3-HANDOFF §五之四） |
| `create-admin` | 2 | 5 | ✅ 本轮修好 |
| `serve` | 1 | 0 | ok |

**结论**：`create-admin` 是唯一的"**生成自己的输入、再用自己的规则校验它**"的子命令，
所以这个缺陷类别目前只此一处。已记入本文档，供下次加 CLI 子命令时对照。

### 6.5.12 ★ 顺手解决的工程问题：仓库自管 devdb

复查过程中"补测试库"卡在权限上（本项目账号**没有 CREATE DATABASE**，root 口令未知）。

| # | 缺陷 | 性质 |
