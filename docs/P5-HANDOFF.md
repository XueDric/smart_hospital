# P5 · RAG 知识库 —— 交付说明

> **范围**（brief §5.5 + §2.1 第 4 条）：**零向量库轻量 RAG**
> ① 文档落库与切块；② 向量存 MySQL JSON + **纯仓颉余弦**；
> ③ 向量不可用时**回落关键词检索**；④ 管理端 CRUD；⑤ 接进分诊的**增强层**。
>
> **状态：✅ 全部完成**（本页从"进行中的记录"更新为**交付说明**）。

## ★★ 一、开工前核实到的一个**关键事实**（它决定了整个做法）

**DeepSeek 没有 embeddings 端点**。实测：

```
POST https://api.deepseek.com/embeddings      -> 404
POST https://api.deepseek.com/v1/embeddings   -> 404
```

⇒ 项目当前**拿不到 embedding 服务**。而 brief §5.5 **已经预判了这种情况**：

> **降级**：向量模型不可用时回落关键词检索（与参考系统一致）

⇒ 所以 P5 建成**两层、可自证**：

| 层 | 依赖外部服务 | 状态 |
| --- | --- | --- |
| **关键词检索** | ❌ 不依赖 | ✅ **默认路径，永远可用，有真实测试** |
| **向量检索** | ✅ 需要 embedding 端点 | ✅ 已实现（余弦/序列化/排序都有测试）；接上端点即启用 |

★ **两层都如实标注 `source`**（`"keyword"` / `"vector"`）。
⚠ 绝不把关键词结果说成向量结果 —— 那是本仓反复点名的"看起来更好"的谎，
而且它会**掩盖"embedding 从没接上"**（第十份复查刚抓过一模一样的形态）。

## 二、交付清单 ✅

### 2.1 表（`schema.cj`，`KB_SCHEMA_DDL`，2 张；表集 12 → **14**）

| 表 | 作用 | 关键设计 |
| --- | --- | --- |
| `kb_doc` | 文档（**人维护的单位**） | `title` **唯一键**：知识库最容易出的问题是同一主题写了两份互相矛盾的文档，而检索会把两份都召回 ⇒ 模型看到矛盾内容。让"重名"在写入那一刻失败。`enabled` 而非删除：停用后历史检索仍可解释 |
| `kb_chunk` | 切块（**检索的单位**） | `embedding` 存 **JSON 数组**、**允许 NULL**（关键词路不需要向量 —— 这正是"零向量库"的关键）；唯一键 `(doc_id, seq)` ⇒ **重新切块 upsert，不留旧块幽灵行** |

⚠ **为什么两张表而不是一张**：切块策略会变（窗口/重叠），而**改策略不该动文档**。

### 2.2 核心算法（`domain_kb.cj` —— 无 DB、无网络 ⇒ 每个函数都能纯逻辑测试）

`kbVectorToJson` / `kbVectorFromJson`

### 2.3 仓储（`kb_repo.cj`）
文档 CRUD + **重切 upsert（旧块必消失）** + 两条检索路 + 向量写入 + 规模统计

  GET/POST/GET:id/PUT:id/DELETE:id  /api/v1/admin/kb/docs

### 2.5 ★ RAG 接进分诊（`ai_triage.cj` + `http_app.cj`）
`aiRagContext(hits)` → 片段进 Prompt 的「参考资料」段；`triageRagHits()` 取片段。

'### 2.6 ★ 看板知识库块（`dashboard.cj`）

`GET /admin/dashboard` 新增 `knowledge_base` 块：`docs` / `docs_enabled` / `chunks` /
`chunks_embedded` / `embedding_coverage_pct` / `scan_limit` / **`scan_limit_reached`** / `note`。

★ **为什么必须放在看板上**（而不是"知识库自己有 stats 接口就够"）：
`GET /admin/kb/stats` 只有**知道要去看**的人才会调；而看板的用途是**看清全局**。
知识库是分诊说明文案的来源，其规模与向量覆盖率决定"RAG 增强还能不能更强"
⇒ 放在看板上，运维例行巡检就会看到"覆盖率长期 0%"，
不必等到有人抱怨"模型说的和院内须知不一致"。

★ `scan_limit_reached` 是**布尔结论**：块数是否已超过检索上限。
超了之后**后面的块静默检索不到**（本仓最忌的形态）⇒ 看板上**一眼可见**，
不让人自己去比 `chunks` 与 5000。

⚠ **独立容错**：用看板自带的 `count1`（内部 catch），**不是** `kb_repo.cj` 的 `kbCount1`
（后者是裸查询，表缺失会直接抛）。看板恰恰是"系统出问题时给人看的那一页"，
它自己 500 会让人以为**整个系统**坏了。
📌 顺带记一条坑：**同名/近名的两个取数助手，容错语义可能完全不同** ——
不能按名字像就挑。

## 三、RAG 接入的三条硬约束（都是**结构性**的，不是"注意一下"）

### ① 片段是**不可信输入** ⇒ 必须过同一道安全层
片段来自 `kb_doc.body`，由**本院人员**维护，比模型编的可信；
但「可信来源」≠「可信格式」—— 里面可能有 Markdown、超长段落，
也可能被误粘进一段医疗建议。
⇒ 片段**逐条过 `aiSanitizeNote`**（只取首行、去 Markdown、命中用药/诊断词**整条丢**）。
📌 判据：**清理的依据是「这段文本会不会原样给患者看」，不是「它从哪来」。**
✅ 由 `AC-KB-5 ③④` 钉住（含用药的片段被丢、好坏混排时好的留下）。

### ② 必须有界
50 条 × 400 字 = 2 万字，直接拼进 Prompt 会顶掉「患者主诉」的注意力位置、
把 token 成本乘几倍而收益递减。
⇒ `AI_RAG_TOTAL_CHARS = 600`（**按字符**，不是字节）。
✅ 由 `AC-KB-5 ⑤` 钉住。

### ③ ★★ 模型仍然**一个字节都改不了** `options`
⚠ 这一条在接入 RAG 之后**更重要**了：知识库文档里很可能写着
「高血压请挂心内科」之类的句子 —— 若模型能据此改推荐，就等于
**知识库内容可以绕过 P2 的硬性验证层**（推荐一个**没号的**科室，
患者照做就挂不上号）。
⇒ Prompt 里**明确写「不要去哪个科室以系统判定为准」**；
且 `ai_triage.cj` 里依然**没有**对 `v.options` 的任何赋值。
✅ 由 `AC-KB-5 ⑥⑧` 钉住。

**另**：`ragHits` 为空 ⇒ Prompt **完全不变**（不加空的「参考资料：」段 ——
那会诱导模型**自己编**参考资料）。由 `AC-KB-5 ⑦` 钉住。

## 四、★ 一条硬性上限，必须知道（复查要求写进文档）

**`KB_SCAN_LIMIT = 5000`**：一次检索最多扫描 5000 个块（按 `c.id` 升序）。
**超过 5000 块时，后面的块不会被检索到。**

⚠ 这是本仓最忌的"静默失效"形态，所以做了两件让它**可观测**的事：
1. 检索响应带 `scanned`（调用方自己就能发现 `scanned == 5000`）；
2. `stats()` 回报 `scan_limit` / **`scan_limit_reached`** / `scan_limit_note`
   —— 直接给出**布尔结论**，不让人自己去比。

⚠ 5000 怎么来的：brief §5.5 说「单院区知识库几千 chunk 完全够用；上万 chunk
才需要降维/分片」。**5000 正好落在这个区间的上沿** ⇒ 到了该分片的时候，
`scanned` 会顶到 5000 提醒你。
📌 一个**刚好等于设计容量**的上限，比一个"很大所以看起来碰不到"的上限有用。

## 五、★★ 合规（已写进 `docs/Q6-合规决策记录.md`）

知识库文档由**本院人员**维护（**文档本身不出站**），
但**检索命中的片段会随 Prompt 出站给第三方模型** ⇒ **知识库里不得放患者个人信息**。

⚠ 这条**无法用代码完整保证**（文档是自由文本）⇒ 三层处置：
1. 管理端写入时**机制性拒绝**明显的个人信息形态（18 位数字／**17 位 + X**／11 位手机号）；
2. 表注释与接口文档写明；
3. Q6 记录里**如实列为「仍需人工把关」**（姓名识别做不到 —— 中文姓名无法可靠区分于普通词）。
📌 **不假装"代码保证了合规"**：能挡的挡住，挡不住的说清。

## 六、本轮踩到并修掉的真问题（都写进代码注释）

🔴 **① `kbLooksLikePersonalInfo` 漏判「17 位 + X」身份证**（复查抓到）
   循环只累加 `0-9` ⇒ 末位 X 的身份证数字段只有 17 位 ⇒ 不触发 `maxRun >= 18`
   ⇒ **放行**。实测：纯 18 位数字 → 400 拒绝，而「17 位 + X」→ **201 放行**。
   ⚠ 这条尤其要紧：Q6 把"拒绝个人信息形态"**列为一条合规缓解手段**，
   而合规手段**漏掉最常见写法**比没有更糟 —— 它会让人以为"已经挡住了"。
   ⇒ 加 `kbHasIdTailX()`（独立判形状，不把 X 计入数字段长度），大小写都覆盖。
   📌 判据：**声称「已挡住」的东西，必须挡住常见写法**。
   ✅ `AC-KB-4 ③` 加了 4 条（大写 X / 小写 x / 16 位+X 不误杀 / 17 位纯数字不误杀）。

🔴 **② `aiRagContext` 超界（611 > 600）** —— 分隔符没计入预算
   只按 `piece` 长度扣预算，而实际写入还有条目间的 `"\n"` 与开头的 `"· "`
   ⇒ 累加式超界，**条目越多超得越多**（少量条目时看不出来）。
   📌 **算"还能放多少"时要把所有将要写入的字节都算上** ——
   只算"正文"而漏掉分隔符/前缀，是累加式起界最典型的错法。
   ✅ `AC-KB-5 ⑤` 钉住（现在精确 600 ≤ 600）。

🔴 **③ `base-check` 的清理前缀只修了一半**（复查抓到，**三份证据**）
   我加了 `BASET`/`BASEDEL` 却**漏了第 5 节的 `RESP950`** ⇒ 那行永远清不掉：
   - 第一次跑 `base-check`：48/0
   - **再跑一次同一库**：47/1
   - `base-check` → `triage-check`：23/1，失败项「★ 反向：有号后能推荐呼吸内科」
     —— **读起来完全像产品缺陷**
   根因链：`RESP950` 逃过清理 ⇒ 残留的「呼吸内科」（无排班）与 `triage-check` 的
   **固定名字**夹具在 `UNIQUE(department.name)` 上撞车 ⇒ 它的 INSERT 静默失败。
   ⇒ 三条修法（都做了，因为"记得加前缀"本身不可靠）：
   1. **前缀只在一处定义**（`$CleanPrefixes` 拼出 SQL），不再散落字面量；
   2. ★ **结尾自检残留为 0**（照 `create-db-check.ps1` 的做法）——
      同类问题会在**源头**暴露，而不是伪装成产品缺陷去坑下一个脚本；
   3. **前置条件失败即中止**：原来科室没建出来仍继续建"孤儿医生 + 排班"
      （实测残留里就有 `dept=810033` 的孤儿医生）。
      📌 判据：**前置条件不成立时，后续步骤不是"也会失败"，而是"会留下垃圾"。**
   ✅ 实测：`base-check` 连跑 **2** 次均 **49/49**；`base-check → triage-check` 混跑 **2** 轮全绿。

🟠 **④ `selftest` 漏看 `KB_SCHEMA_DDL`**（表集断言 5 项失败，而表**实际建出来了**）
   ⇒ 新增 `allSchemaDdl()` 作为**唯一答案**，自检只认它。
   📌 **「有哪些」只能有一处答案**。

🟠 **⑤ `AC-KB-4 ⑨` 只在首次运行成立**（`accept` 381 → 380）
   ⑨ 断言"库里无向量"，而 ⑩ 会写入向量 ⇒ **重跑即假红**。

## 七、★ 本阶段新增的三条纪律（待并入 README 踩坑表）

| # | 纪律 | 为什么 |
| --- | --- | --- |
| AI | ★★ **「降级路径」必须是可测的默认路径，不是备用方案** | 若把关键词做成"很少走的兜底"，它就**永远不会被测到** ⇒ 真需要它时才发现它坏了。⇒ 关键词设为**默认路径**（无外部依赖 ⇒ CI 永远能测），向量作为**需配置才启用**的增强 |
| AJ | ★★ **两条路的分数不可比时，就不要混排** | 关键词分是"覆盖比例"、向量分是"余弦"，量纲不同 ⇒ 混排等于**用不可比的数排序**。正确做法是**二选一**（由"有没有 embedding"决定），并如实标注 `source` |
| AK | **切块最容易错的不是"切得难看"，而是"悄悄丢内容"** | 丢内容在检索时表现为"某些问题永远查不到"，**极难从结果上发现** ⇒ 必须用"各块按顺序覆盖全文"这种**结构性断言**钉住 |
| AL | ★★ **能被静默触发的上限，必须有一个显式的「已触顶」信号** | `KB_SCAN_LIMIT` 触顶后超出的块**静默检索不到** ⇒ 只回报总块数不够（看到 6000 未必联想到只扫 5000），必须直接给布尔结论 |
| AM | ★ **测试脚本要自检「本脚本的残留为 0」** | 清理漏一个前缀 ⇒ 残留跨轮累积 ⇒ 伪装成**别的脚本的产品缺陷**（本阶段实证坑了 `triage-check`，害我排查两轮） |

## 八、仓颉/工具链层面的坑（本阶段新增）

| 坑 | 说明 |
| --- | --- |
| `Array<T>` **不支持 `+`** | 合并两个数组必须 `ArrayList<T>` + `.toArray()`。实测报 `invalid binary operator '+' on type 'Struct-Array<Struct-String>'` |
| `package` 声明必须在 **import 之前** | 我把 `import` 插到 `package` 前 ⇒ `expected declaration, found keyword 'package'`。本仓约定：`package` 写在文件头注释**之后**、所有 `import` **之前** |
| 含 `"` 的中文串**不能**直接写 ASCII 引号 | 会**提前终止字符串**。用 `「」`。本阶段因它编译失败 **4** 次 |
| `trimAscii` **首尾都去** | 切块需要保留尾部换行（换行是断点）⇒ 自己写 `kbTrimLeftAscii` |
| **不要用 PowerShell `Replace` 改 `.cj`** | 本阶段它造成了：静默失败（以为改了实际没改）、**4 次留下裸引号**（`'/*`、行尾 `'`）、**误删 rune 字面量收尾引号**（破坏 `domain_base.cj`/`triage_redflag.cj`，已从 HEAD 恢复）、把 `schema.cj` 弄成两文件拼接。⇒ **一律用 `edit` 工具**，改完**核对目标确实变了** |
| 改完 `.ps1` 必须补 **BOM** | `edit` 工具会去掉它 ⇒ PS 5.1 按 ANSI 读中文 ⇒ 满屏假语法错 |
| 改完文本要核对**行尾** | 本阶段**第三次**踩：`schema.cj` 显示 841 行变化而真实只有 34 行。⇒ 提交前用 `git diff --ignore-cr-at-eol --numstat` 复核 |
