### 2.1 P0-1 鸿蒙构建与**运行**证据（✅，本轮从"能构建"推进到"能装能跑"）

1. 仓库内没有可用 hvigor 入口：`hvigor/hvigor-wrapper.js` 是 **0 字节**（与 DevEco 新建模板同源，本就设计成由 IDE 重新生成），且仓库无 `hvigorw`。

## 三、让"智能"这条线真的调得动、说得清

### 3.1 默认开箱即用：`builtin:demo`（评审"默认一次模型都不调"的直接回应）

**不变量**：`server/src/ai_settings.cj` 的 `ai.key_ref` 只存**引用**（`env:` / `file:` / `builtin:`），库里永不出现裸密钥——这条没有为了分数破掉。

**做法**：新增第 4 种引用形式 `builtin:demo`。`server/src/ai_builtin.cj` 持有密钥本体与默认 endpoint/model（`https://api.deepseek.com/chat/completions` / `deepseek-chat`）；`ai_settings.cj` 的默认值改为 `ai.enabled=1` + `builtin:demo`，于是**全新库装完即可真调**。`keyRefBuiltinName()` 用**整串白名单比对**（不做前缀切片，避免 `builtin:sk-xxx` 绕过）。

> ⚠ **必须轮换**：该密钥随源码与二进制分发。`ai_builtin.cj` 头部已写明"发布前必须轮换"，`docs/Q6-合规决策记录.md` 同步登记了"演示默认开、生产必须换 key 或置 0"的决策（§6）。

**验收**：`server/tests/ai-live-check.ps1` —— **25 项全 PASS**，含 `data.probe.ok=true / http_status=200 / elapsed_ms≈654`、`source=model`、`ai_note` 为真实模型输出、`triage_stat` 出现 `source=model` 行、看板 `model_calls=2`、响应中不出现 `sk-…` 指纹。

### 3.2 规则引擎两条可复现缺陷 + 同义词（✅ 三条全修）

### 3.3 出站调用：重试 + 全链路上限 + TLS 信任锚（✅）

- **重试**：`AI_CALL_MAX_ATTEMPTS = 2`、退避 200 ms；可重试 = 网络异常(`httpStatus==0`)/429/5xx 且**请求确实发出去过**（`AiCallResult.attempted`）；401/400/解析失败不重试（重试无意义，只会放大账单）。
- **"无 connectTimeout"的诚实处理**：扫 `stdx.net.http.cjo` 符号表确认该版本**没有** `connectTimeout`（`connectTimeout` 命中 0 次）。于是改为 `spawn` + `Future.get(timeout)` 的**墙钟硬上限**（含 DNS/connect/读写），超时降级到规则并写明"模型调用超过 Ns 全链路上限"。注释里写清：`Future` 超时不取消 TCP，僵尸线程受 `ai.max_concurrent` 约束。
- **★ TLS 真因（评审与文档都没提的新发现）**：`POST /admin/ai/models/:id/test` 报
  `TLS handshake failed (client): certificate verify failed (134), TLS alert unknown CA(F)`，
  而 `curl.exe`（Schannel）与 .NET 访问同一 endpoint 都是 200 ⇒ 不是网络、不是密钥：**仓颉 stdx 走 OpenSSL，不读 Windows 证书存储**。
  处置：新增 [`server/export-ca-bundle.ps1`](../server/export-ca-bundle.ps1)（从 `LocalMachine\Root` + `LocalMachine\CA` + `CurrentUser\Root` 去重导出 PEM，76 张证），运行时 `SSL_CERT_FILE` 指向它；`tools/package-release.ps1` 生成的 `start-dev.cmd` 会**自动导一次**再设环境变量。分发包**不携带 PEM**（可能含企业内网根证书，绝不随包分发），只带导出脚本。

### 3.4 看板不再说谎（✅ P2-7）

`server/src/dashboard.cj` 原 `triage.put("source", JsonString("rules"))` 把每条都写成 `rules`，而统计又在数 `countBySource("rules")` ⇒ 看板永远自证"AI 没被调用"。现在改为按 `SELECT source, COUNT(*) … GROUP BY source` 推导 `model`/`rules`/`mixed`/`none`，并新增 `by_source` 明细；管理台把它渲染成「来源 模型/规则/混合」。实测：`triage.source = "mixed"`、`by_source = [rules 105, model 19, model:invalid 2]`、`total_calls = 126`。

### 3.5 模型种子与"存量库覆盖"陷阱（✅ 另修两处）

1. 默认播种指向 DeepSeek（对话），**向量行单独指向百练 `text-embedding-v3`**（DeepSeek 无 `/embeddings`，硬指过去只会 404）。
2. `ai.enabled` 默认从 `0` 改 `1` 后，`aiModelSeedDefaults()` 的"存量库迁移"分支被全新库误命中（判据只看 endpoint/model 非空）⇒ 只播 1 行。修法：`ai_settings.cj` 新增 `hasRow()`（**直查库、绕过缓存**），判据改为"非空 **且** 库里真的有这两行"。

## 六、合规口径变更（必须与代码一致）

原 `docs/Q6-合规决策记录.md` 的决策是"`ai.enabled` 默认 `0`，Q6 获批前生产保持 0"。本轮为了让评审/答辩能看到真实模型调用，把**默认值改为 `1` + `builtin:demo`**。这不是"把合规换成分数"，而是把风险**显式化并限定范围**：

- 只影响**演示/开发**：`builtin:demo` 是演示密钥，随源码分发，**发布前必须轮换**（`server/src/ai_builtin.cj` 头部已写死这句话）。
- ★ **有效期是代码行为**（2026-10-18 补）：`AI_BUILTIN_DEMO_VALID_UNTIL = 2026-12-31`，到期后
  `aiResolveKey()` 拒绝、`aiKeyRefProblem()` 给出到期日与换法、分诊降级到规则；由
  `acceptance_ai_call.cj` 的 ⑧ 段 8 条纯逻辑断言守着（`accept` 786 → **794**）。
  负责人决定保留这把 key 作实验室/评审演示用 —— 保留的风险因此被装进"到期即失效"里，
  但**窗口期内被拿走仍是可能的**，所以余额要小、窗口结束要吊销。
- ★ **换自己的密钥是一条命令**：`.\tools\set-ai-key.ps1 -ApiKey sk-… -AdminPw <口令>`
  —— 写 `server\ai-key.txt`（已 gitignore）→ 改 `ai.key_ref=file:<绝对路径>` → 调模型自检。
  **生产上线清单**：把 `ai.key_ref` 换成 `env:…` 或 `file:…`、轮换密钥、按 Q6 结论决定
  `ai.enabled` 是否为 `0`；`docs/Q6-合规决策记录.md` 已同步这三点。
- 依赖链没变：出站仍是 `OPENSSL`（需 `SSL_CERT_FILE`），失败仍降级到规则，响应里仍不落患者标识。

> 📌 这轮的五条教训（都是"改对了局部、错了整体"的形态）：
> ① **放宽窗口/阈值 ≠ 更准**——判据维度不够时，放大窗口只会把"没看见"变成"看错"；
> ② **给配置项加默认值会连带改一大批断言的语义**（见附录 A 的"一处假红"与 §3.5 的种子陷阱）；

> ④ **覆盖写优于"先删后写"**——多步非原子操作之间的失败窗口，正是身份串号的来源；
> ⑤ **注释里的 `/*` 是代码**——块注释可嵌套的语言里，一句"`shared_prefs/*.xml`"就能让整个文件不编译。
