# 智慧医院智能导诊就诊系统 · 项目说明

> **一句话**：患者输入一句主诉 → AI 多步推理取证 → 推荐科室与医生 → **校验真实有号** → 一键挂号 → 医生接诊 → 生成七段式电子病历，全程落库、可追溯、可观测。
>
> 本文是**面向验收的项目说明**（背景、需求、功能模块、创新点、应用价值）。
> 技术实现见 [系统设计.md](系统设计.md)，架构决策见 [adr/](adr/)，提交材料索引见 [README.md](README.md)。

---

## 1. 项目背景

**业务背景**：门诊是医院里最拥堵的一环。患者说不清症状 → 挂错科 → 反复退号重挂；医生在诊室里再问一遍已经问过的病史；病历质量完全依赖医生当场的记忆与手速；院方则拿不到"分诊准不准、号源用没用完、AI 到底帮了多少忙"这类数据。

**行业现状**：头部三甲已上线智慧医院，但实现方案普遍偏重——`FastAPI + LangChain + Redis + 向量数据库 + Vue3` 一套下来，一个单院区要维护五六个中间件。中小医院与校医院没有对应运维能力，导致这类系统"做得起、养不起"。

**本项目的技术背景**：团队具备**仓颉（Cangjie）+ 轻舟（QingZhou）**能力。仓颉是华为自研的国产化语言；**轻舟是仓颉生态的 Koa 风格 Web 框架，由本团队自研并 MIT 开源**（路由/静态错误体可注入、数据库断链自愈与探活、MySQL 参数化绑定等框架级能力均为本团队实现，证据见 [轻舟说明](轻舟说明.md)）。因此本作品同时具备**两层产出**：框架侧的设计与实现，以及跑在该框架上的完整门诊业务闭环——既验证了仓颉在真实业务（并发、事务、流式、AI 编排）上的工程可用性，也是一份可直接交付的信创改造参考实现。

**为什么是"读一个参考系统 + 重写"**：项目启动时以某开源智慧医院方案为能力基线（19 个路由模块 / 21 张业务表 / 约 80 个 REST / 三端角色），逐条判断"哪些能力本仓库已有、哪些要新写、哪些是仓颉侧做不到的"，再按 P0–P5 六个阶段落地。**逐条映射与取舍**落在本文的功能清单与 [adr/](adr/) 的架构决策里：参考系统用「号源表行锁 + 内存排队」保证不超卖，本仓库换成「号源表原子自减 + 挂号唯一键幂等」；参考系统把病历与看板都放内存，本仓库全部直接 SQL（读写一致由事务隔离保证）。

## 2. 需求分析

### 2.1 角色与核心场景

| 角色 | 核心场景 | 关键诉求 |
| --- | --- | --- |
| **患者** | 说不清该挂哪个科 → 填一句主诉 → 拿到带**真实可约号源**的科室/医生推荐 → 补全预问诊 → 挂号 → 看就诊进度与病历 | 推荐必须可执行（不能推一个没号的科室）；挂号不能重复、不能超卖；界面要能说清"现在到哪一步了" |
| **医生** | 看今日接诊队列 → 到院/叫号/接诊 → 录入七段式病历 → 提交锁定 | 队列顺序稳定；病历草稿不丢、一旦定稿不可改（医疗数据不可篡改）；既往病历随手可查 |
| **管理员** | 维护科室/医生/排班号源；重置账号密码；配置 AI 能力中心与知识库 | 改配置**不重启**；密钥**不落库**；看板只出聚合不出明细 |

### 2.2 功能需求（编号可追溯）

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| FR-1 | 主诉 → AI 推荐科室/医生，且**推荐里只能出现当前有号的科室** | `POST /api/v1/triage` + 校验层（`server/src/triage.cj`）+ 验收用例 `acceptance_triage.cj` |
| FR-2 | 危急征象必须先于 AI 结论命中（词表 + 否定 + 共现） | `server/src/triage_redflag.cj` + `triage-check.ps1` |
| FR-3 | 预问诊多轮采集，**流式**回显（SSE） | `server/src/previsit.cj` + `previsit-check.ps1` |
| FR-4 | 挂号：幂等（同 `client_token` 不重复建单）、并发不超卖、退号归还号源 | `domain_booking.cj` + `stress-booking.ps1`（20/30/40/50 进程抢同数号源） |
| FR-5 | 接诊队列状态机：到院/候诊/接诊中/完成/取消/**爽约（`no_show`）** 共 7 态，非法跃迁一律拒（`booked`/`arrived`/`waiting`/`visiting` 均可转 `no_show`） | `domain_emr.cj:visitTransitionAllowed` + `visit-timeline-check.ps1` |
| FR-6 | 七段式电子病历：草稿 → **提交锁定**，锁定后不可改；修订历史可查可对比 | `domain_emr.cj` + `emr-check.ps1` / `revision-check.ps1` |
| FR-7 | 运营看板：科室/挂号趋势/号源使用率/分诊命中/预问诊完成率/病历进度/AI 概览 | `dashboard.cj` + 管理台页面 |
| FR-8 | AI 能力中心：模型配置、Prompt 模板、密钥引用、工具开关**全部落库、改完即生效** | `ai_settings.cj` / `ai_prompt.cj` + `ai-model-check.ps1` |
| FR-9 | 零向量库知识库：文档切块 + 关键词检索（默认路）+ 向量路（配 embedding 即启用），片段可进分诊但**改不了推荐** | `domain_kb.cj` / `kb_repo.cj` + `kb-check.ps1` |
| FR-10 | 三端权限：患者/医生/管理员各自只能做自己的事 | `http_app.cj` 角色守卫 + `auth-check.ps1` / `base-check.ps1` |

### 2.3 非功能需求

| 维度 | 要求 | 实现 |
| --- | --- | --- |
| **安全** | 口令不可逆存储；令牌不透明；**AI 密钥不落库**；管理动作按角色隔离；不泄露驱动/堆栈细节 | PBKDF2-HMAC-SHA256 × 100000 + 16B salt；64-hex 不透明令牌；密钥只存 `env:`/`file:` 引用（裸密钥机制性拒收）；`/health` 失败只给固定短句 |
| **并发** | 抢号不能超卖，退号不能丢号 | 参数化原子 `UPDATE … WHERE remain_num > 0` + 唯一键 + 同事务 INSERT |
| **可用** | AI 挂了业务不能挂；数据库闪断不能全站 500 到重启 | 三态降级（`rules` / `model` / `model:invalid`）；DB 断链自愈 + `/health` 探库（503） |
| **可运维** | 改 AI 配置不重启；升级不加手工步骤 | 配置落库 + 缓存失效；自动建表 + 编号迁移（幂等） |
| **合规** | 明确"发什么出站、默认关不关、谁能打开" | [Q6-合规决策记录.md](Q6-合规决策记录.md) |
| **可验证** | 单元/验收/契约/压测/全量 live 门禁 | `selftest` 51 + `authtest` 17 + `triagetest` 150 + `accept` 821 断言 + `final-verify` 18 项门禁 + 契约门禁（24 Schema / 67 样例） |

### 2.4 范围边界（本期**不做**）

自助注册 / 改密、支付与医保结算、多院区与多租户、短信/推送、离线队列（**挂号与 AI 调用必须在线直连**，排队等于超卖）、医生排班的图形化编辑器。理由：前四项要么依赖外部通道与资质（支付/医保、短信服务商、多租户隔离），要么会破坏「挂号只认服务端权威」这条不变量（离线队列必然超卖）；排班图形化编辑器属纯效率功能，命令行与管理台已能覆盖。

## 4. 创新点

> **只写能被现场指认的**：每条都要能指到一行代码、一条命令或一个数字；指不到的是技术栈标签，不是创新点。
> 所以下面只有 5 条，另附 2 条**边界**——做不到的部分写清楚，比藏着更能站住。

### 4.1 五条核心

**① 模型只负责"怎么说"，结论和号源永远由规则与数据库给**

医疗导诊里"模型编一个科室"是安全事故，不是体验问题。常见做法是"让模型吐 JSON 再校验"，本项目把边界**前移**：模型调用发生在**规则已经定完科室、并复查过真实号源之后**，模型拿不到"改结论"的权力，只能把结论转写成患者能读的一两句话。

- 可指认：`server/src/triage.cj:102-104`（`options` 永远由规则 + 数据库决定）；`server/src/ai_triage.cj:163` `aiEnhanceTriage` 的入参是**已定**的 `TriageVerdict`；模型失败 / 超时 / 输出不合规一律 `source=rules` 并写 `degrade_reason`。
- 边界：只做结构校验与"号源可约性复查"，**没做**语义层的幻觉检测。

**② 危急征象用"三段式否定窗口"，而不是"含否定词就不报"**

红牌误报与漏报是这套系统里唯一可能致命的判定。朴素做法（"胸痛前面有『没有』就不报"）会漏掉三种真实写法：**"无法缓解的胸痛"、"无明显诱因突发胸痛"、"没胃口而且胸痛"**——它们恰好是否定词与危象共存。

- 可指认：`server/src/triage_redflag.cj:119` `RED_FLAG_NEGATION_WINDOW = 8`、`:133` `RED_FLAG_NEGATION_GAP_MAX = 6`、`:136` `GAP_SHORT = 1`、`:143` 阻断词表（`而`/`且`/`但`/`却`/`诱因`/`原因`）；`triagetest` 150 条里这三句是**必须报红**的断言。
- 边界：词表法的固有上限——未登录表达靠模型兜底与人工申诉，**不承诺零漏报**。

**③ AI 能力中心：模型、提示词、开关都能改，且全链路零重启**

"AI"最容易变成硬编码 prompt + 写死模型。本项目把模型行、提示词、开关做成三张表 + 内存缓存，**写库即失效**（TTL 5 s 兜多实例），改完下一次请求就生效；分诊的提示词槽位是**真接线**，不是只读展示。

- 可指认：`server/src/ai_settings.cj:620-629`（读缓存 / 写清缓存 / TTL 5 s）；`server/src/ai_prompt.cj:78`、`:94`、`:113`（第 4 个槽位 `triage`）；`server/src/ai_triage.cj:303`、`:357`（取模板 → 渲染成实际 prompt）；`PUT /api/v1/admin/ai/prompts/triage` 后下一次分诊即用新模板（命令与返回见 `docs/验收实跑-2026-10-21.md`）。
- 边界：工具开关（tool-calling）是**预留闸门**——参数页能改，但生产路径没有派发器。

**④ 单实例零中间件：一种数据访问范式替代五个中间件**

同类作品常靠"Redis + 向量库 + 消息队列 + 网关"堆能力。本项目 17 张表全走**直接 SQL + 事务**：抢号靠 `UPDATE … remain_num > 0` 原子扣减、流式问诊用框架路由手写 SSE、数据库断链自愈而不重启进程。少一层中间件就少一类线上故障面。

- 可指认：`server/src/domain_booking.cj`（原子扣减 + 幂等令牌 + 归还三态）；`server/src/http_app.cj:2280`（`/api/v1/previsit/stream` 流式）；`server/third_party/qingzhou/src/db_mysql.cj:351`、`:360`（断链识别与重连）。
- 边界：单进程单连接。要横向扩容得先解决连接与缓存一致性，本仓库不承诺 scale-out。

**⑤ 把"能跑"做成"别人能复算"：门禁化的交付纪律**

参赛作品的测试数字普遍不可复算。本项目把可复算性做成基础设施：**821 条断言**、18 项 live 门禁、契约 24 Schema + 67 样例双门禁、三层 CI（文档卫生 / 分发包 76 个文件逐字节对源码 / 真编译 + 三件套）、交付快照机器校验。

- 可指认：`docs/验收实跑-2026-10-21.md`（命令、退出码、输出原文、环境指纹）；`.github/workflows/repo-hygiene.yml`（三个 job）；`tools/check-snapshot.ps1`；`server/tests/doc-counts.ps1`（25 条数字对账）。
- 边界：客户端只有 10 条纯 JVM 契约测试，鸿蒙侧 Hypium 未搭（需要 `ohosTest` 脚手架与 `ohpm` 依赖）——这是真实短板，不粉饰。

### 4.2 两条诚实边界

| 议题 | 现状 | 为什么这样写 |
| --- | --- | --- |
| 向量检索 | `kbCosine` / `searchVector` 已实现且有单测（`server/src/domain_kb.cj:19` 起、`acceptance_kb.cj:145-175`），但**生产只走关键词**；DeepSeek 无 `/embeddings` 端点（实测 404） | 准确说法是"关键词检索已在生产链路，向量路是已验证但未接入的备选"，不是"已做 RAG" |
| 国产化栈 | 仓颉跑通并发抢号、SSE、事务、AI 编排、静态托管与管理台 | 这是**选型验证**，不是语言创新；真正有价值的是为绕开语言/标准库缺失做的三处取舍（`server/src/ai_prompt.cj` 的 `match` 常量改 `if` 链、`server/src/triage_redflag.cj` 的 `Array<Rune>` 索引窗口、`server/src/ai_call.cj` 的墙钟超时） |

### 4.3 这五条的共同点

医疗场景有两条硬约束——**模型输出不可信**、**每个数字要能被追责**。上面 5 条都是把这两条约束落成代码与门禁的结果：前三条管"模型不能越权"，后两条管"系统能被别人独立复算"。

## 5. 应用价值

**对患者**：把"该挂哪个科"从经验判断变成**可执行推荐**——推荐里每个科室都能当场约到号，不白跑一趟；就诊进度（已挂号 → 已到院 → 候诊 → 接诊中 → 完成）在端上可见。

**对医生**：病历从"事后补"变"当场成稿"，七段式结构化 + 定稿锁定，既往病历按就诊时间一键可查，减少重复问诊与漏项。

**对医院管理者**：拿到分诊命中率、号源使用率、预问诊完成率这些**可动决策的数据**；AI 能力可开关、可换模型、可审计，不需要停机。

**对信创改造**：整套系统在国产语言（仓颉）与**我们自研的国产框架（轻舟）**上跑通了一条完整的医疗业务闭环，可作为同行业系统迁移的**参考实现**——"框架能改成什么样"与"业务该怎么写"两层都有落点；踩过的坑（字节/字符、`NO_BACKSLASH_ESCAPES`、断链重连）也都写进了 ADR、交接文档与上游 `CHANGELOG`。

**可复用资产**（与业务无关，可直接搬到别的仓颉项目）：

| 资产 | 位置 |
| --- | --- |
| Koa 风格中间件 + Trie 路由 + SSE/chunked 出站流式 + 静态/gzip/Range/ETag（**本团队实现，含路由/静态错误体可注入**） | `server/third_party/qingzhou/` |
| 数据库抽象 + 参数化绑定 + 事务 + **断链自愈 + 探活**（**本团队实现的框架层能力**） | `server/third_party/qingzhou/src/db*.cj` |
| 统一信封 + 错误码表 + 角色守卫 + 请求体上限统一封装 | `server/src/http_common.cj` |
| 契约门禁（导出机 + Schema + 逐字节比对） | `contract/`、`server/tests/contract-check.ps1` |
| AI 编排纪律（三态降级 / 校验层 / 密钥引用不落库） | `server/src/ai_*.cj` |
| 全量 live 门禁（一条命令 18 次运行 / 17 个脚本，`health-check` 在 dev/prod 各一次） | `server/tests/final-verify.ps1` |
