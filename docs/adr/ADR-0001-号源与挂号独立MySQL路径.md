### ★ rev.3 的核心：为什么去掉了乐观锁

rev.1/rev.2 用的是「`version` 乐观锁 + 重试」。**实测证明它在最穷工况（请求数 ≈ 号源数）
下严重少卖**：

| 工况 | rev.2（乐观锁） | rev.3（原子自减） |
| --- | --- | --- |
| 20 并发抢 20 号 | 只卖出 **15~17** | **20** ✅ |
| 30 并发抢 30 号 | 只卖出 **22~23** | **30** ✅ |
| 40 并发抢 40 号 | 只卖出 **25~26** | **40** ✅ |
| 50 并发抢 50 号 | （未测） | **50** ✅ |

原因：N 个请求同时读到同一个 `version`，只有一个能成功，其余作废；
重试时它们又读到同一个新 `version`、再次互撞 —— 重试预算迅速耗尽。
**这也正是 §8 第 1 条复审触发条件被命中的情形**（耗竭率实测高达 50%，远超 1% 阈值）。

**为什么去掉 `version` 更正确而不是更冒险**：防超卖真正依赖的两件事
（`remain_num = remain_num - 1` 与 `remain_num > 0`）在**同一条 UPDATE 内**由 InnoDB 原子求值，
不存在"检查-后-写"的跨语句窗口。乐观锁解决的恰是跨语句场景，这里**不适用** ——
它只贡献了"并发请求互相作废"。`version` 列保留并继续 +1，改为服务**管理端并发编辑**
（防覆盖别人的排班改动）。

### ★★ rev.6 的核心：`medical_record` 为什么必须移出内存 Store

P4 落地电子病历时发现：**病历被划错了类**（rev.1 起一直在"配套域/内存 Store"里）。
两条理由，都是硬的：

#### 理由 ① 本仓**自己**已经为同类数据判过一次（P2 的先例）

P2 引入 `previsit_session` 时**特意**把它排除在内存 Store 之外，当时的原话是
（见 `docs/P2-HANDOFF.md` §「新增的第三类表」与 `previsit_schema` 注释）：

> ★ 预问诊表**不属内存 Store 负责的表**（**它是医疗数据，必须立刻持久化**，
>   不能进"整表替换"范式）

而 `medical_record` 装的是**诊断与处理意见** —— 比预问诊问诊单**更**典型的医疗数据。
同一类数据两套处置，正是本项目反复点名的病（"同一语义两处口径"）。

#### 理由 ② 内存 Store 在**生产路径上从未刷盘**（已核实）

这是更硬的一条。`flushToMysql()` 的全部调用点：

```
acceptance.cj:483   ← 只有测试
```

`main.cj` 与 `http_app.cj` **完全没有引用 `MemStore`**。
⇒ 若病历走内存 Store，那么"医生写病历"这个动作的实际效果是：
**只写进程内存，永不落库**（服务一停即丢）。

> 📌 对科室/医生这类"可重新配置"的数据，这个缺口是**待补的工程债**
>   （配置丢了能重建）；
>   对病历，它是**数据丢失**（诊断与处理意见重建不出来）。两者不是一个量级。

#### 因此 rev.6 的处置

| 项 | rev.5 | rev.6 |
| --- | --- | --- |
| `MEM_TABLES` | 4 张（含 `medical_record`） | **3 张**（科室/医生/患者） |
| 病历写入 | 内存 + 整表替换刷盘 | **直接 SQL**（`MedicalRecordRepo` 独占） |
| 病历的删除风险 | 一次刷盘 `DELETE FROM medical_record` 全表重写 | 逐条 upsert，**不存在整表删除** |
| 断言 | — | `!MEM_TABLES.contains(TABLE_MEDICAL_RECORD)`（selftest 两条） |

⚠ **明确没做的事**（诚实边界，免得被读成"配套域也搬走了"）：
`department` / `doctor` / `patient` **仍在内存 Store 里**。
它们同样"生产不刷盘"，但处置它们属**另一项决策**
（是给 `serve` 接上刷盘、还是也改直接 SQL），本轮**没有**顺手改 ——
把一件没论证的事混进来比留着它更糟。已写进 `docs/P4-HANDOFF.md` 的未做清单。

### ★★★ rev.7 的核心：内存 Store 为什么被**整体拆除**

起因是 P4 收尾时核对"配套域（`department`/`doctor`/`patient`）在生产路径上不刷盘"
这个缺口 —— 打算按 rev.6 的手法给它接上刷盘。**但核实的结论比"缺口"彻底得多**：

| 核实项 | 实测结果 |
| --- | --- |
| `MemStore` 的**生产**实例化点 | **零处**（唯一实例在 `acceptance.cj:469`） |
| `loadAll()` 的**生产**调用点 | **零处** |
| `flushToMysql()` 的**生产**调用点 | **零处** |
| `MemStore` 有"往内存里写"的入口方法吗 | **没有** —— 只有 `loadAll` / `flushToMysql` / 两个查询函数 |
| 生产代码对这三张表的**写**（INSERT/UPDATE/DELETE） | **零处**（唯一的 `DELETE` 在 `mem_store.cj` 自己的刷盘里） |
| 生产代码对这三张表的**读** | 11 行（看板 3 个计数、分诊 2 处科室名查询） |
| 有"管理端建科室/医生"的端点吗 | **没有** |

⇒ 结论：**这条范式在生产上从未接线**。那三张表实际是**只读参考数据**（靠人工 SQL 灌入），
而 `README` 却把它描述成"内存 Store 范式" —— **文档比实现更先进**；
并且 P4 的看板还会把"上次刷盘的快照"当成现状报出去（**它根本没错，因为从来没有刷过**）。

#### 三条修法候选与选择

| 方案 | 做法 | 为什么没选 / 选了 |
| --- | --- | --- |
| A | 补全：给 `MemStore` 加写入口 + `serve` 里 `loadAll` + **定时刷盘** | 引入本项目迄今没有的**后台定时器**，且仍有"两次刷盘之间崩溃丢改动"的窗口。**这不是修洞，是"真的把配套域建起来"**——工作量与风险都远超一个补丁该有的样子 |
| B | **拆掉**：删 `mem_store.cj` / `sql_recorder.cj`，三张表改直接 SQL | ★ **选了它**。生产行为**几乎不变**（它们本就只被读），却消掉"两种范式并存"的复杂度与"文档比实现先进"的误导 |
| C | 只改看板标注 + 写进未做清单，代码不动 | 最小改动、零删除，但那份 ~490 行**未接线代码会继续存在并继续误导读者** |

#### 为什么"拆"是**更保守**的选择，而不是更大胆的

- **没有功能被删掉**：这三张表本来就只被读，拆掉内存 Store 后**读法不变**（还是 SQL）。
  真正被删的是**一条从未走过的代码路径**。
- **"不接线的东西"不是中立的**：它让 README 与实现不一致、让 AC-4 去验证一个
  生产上不存在的机制、让后来者（包括我自己）以为数据流是那样走的。**这是负资产。**
- **保留了重建的余地**：若将来真需要内存缓存（例如 §8 触发条件里的水平扩展），
  那时**有明确的需求与验收标准**再建，比现在留一条半成品更好。

#### 一个必须写清的区分：**消失的是"范式"，不是"表"**

`department` / `doctor` / `patient` **仍然在库里、仍在 `ALL_TABLES` 里、仍被人读**。
它们只是不再经内存 Store。所以 `selftest` 的分类里：
- ❌ **不是**删掉那一项（我第一版就那么干的，结果求和 = 9 而 `ALL_TABLES.size` = 12 —— **而那条断言恰好把它抓住了**）；
- ✅ 而是给它**新的归属**：**基础数据域**（直接 SQL 读；⚠ **目前没有写入端点**，靠人工 SQL 维护）。

> 📌 教训：**删一个概念时，先问"挂在它下面的实体去哪"。**
> 把实体一起删掉 = 数据丢失；连分类一起删掉 = 断言数不上账。
> 正确做法是**重新归类，并写明新纪律**。

#### 那 `sql_recorder.cj` 为什么也删

它是 `DbBackend` 的录制装饰器（录下实际发出的 SQL），**唯一用途是 AC-4 的
"刷盘 SQL 里从未出现 `schedule`"** 那条断言。没有刷盘了 ⇒ 它没有对象可录。
📌 一个**只为一个不存在的机制服务的测试工具**，留着就是"假象的一部分"。

#### AC-4 如何处理（不是简单删掉）

AC-4 是"内存 Store 刷盘**不波及**号源域"。没有刷盘了 ⇒ 它守的对象消失了。
但它里面**真正要保证的事**仍在：**没有第二条路径能碰号源域**。⇒ 重写为
「数据访问范式**唯一化**」，四层结构保留（逐层加强），对象换掉：

  ① 分类：每张业务表都归属一个**域**（无孤儿表）；
  ② ★★ 号源域的表**只准 `BookingRepo` 写**，且域清单与表集**不脱节**；
  ③ ★ 表名与搬迁前内存 Store **零交集**（**从旧 AC-4 保留**：搬迁前若同库运行会争表）；
  ④ ★★ **反向**：号源域确实**有**数据（否则③是"空比空"的假绿）。

⚠ 并且**刻意不写**"没有内存 Store"这类运行期断言：
按踩坑表 M 条「断言"没有 X"的前提是 X 真的**存在**」—— 那些名字已经不存在了，
硬写一个字符串比较是**空洞**的（只是在比自己的字面量）。
⇒ 这条交给**编译器**：引用 `MEM_TABLES` / `MemStore` 会直接**编译失败**。
**编译期保证比任何运行期断言都硬**，所以这里写明"不写那种断言"以及**为什么**。

#### 顺带修掉的一处"钉数字"式断言


AC-4 里原有一句 `check("① 内存 Store 负责 4 张表", MEM_TABLES.size == 4)` ——
rev.6 一改就**必然变红**。这暴露了它是"**钉数字**"而不是"钉不变量"：
真正要守的是"刷盘只碰 `MEM_TABLES` 里的表、且号源域不在其中"。
⇒ 已改为从 `MEM_TABLES` 派生（`selftest` 的 `memTables` 同样改为派生）。
📌 这是本项目的反复教训：**断言要钉不变量，不要钉数字**。

## 1. 背景（Context）

### 1.1 搬迁前服务端的持久化范式

搬迁前的服务端，持久化范式是：

> **全量载入内存 + 全局锁 + 每次提交整体替换各表**
> —— 证据：搬迁前的 `mysql_store.cj:30-37`（"一次提交要整体替换 7 张表"）、
> 其 `docs/` 与 `README.md` 未决 #12 / S-14。

该范式对**早期那类小体量业务**是合适的：数据量小（千人档）、读多写少、单实例、业务不要求毫秒级扣减。

### 1.2 挂号场景提出的新要求

参考系统（`smart-hospital-project-brief.md` §2.3）给出两条必须照搬的机制：

1. **防超卖**：排班表 `version` 乐观锁 + 扣减带 `remain_num > 0` 条件；
2. **顺延不串号**：挂号单保存 `visit_date` **就诊日快照**。

第 2 条与持久化路径无关，照做即可。**第 1 条是本次决策的全部压力来源。**

### 1.3 为什么不能把排班表塞进 `PersistedState`

若把 `schedule` 放进现有内存 Store，会**同时**继承三个代价：

| # | 代价 | 依据 |
| --- | --- | --- |
| 1 | **整表替换写放大** —— 每次挂号重写整个排班/订单表 | `mysql_store.cj:30-37` |
| 2 | **`s.lock` 跨一次网络事务持有** —— 全部挂号串行化，且与整库刷盘争锁 | 搬迁前 S-14：「这把锁是**跨一次网络事务**持有的」 |
| 3 | **并发扣减被完全串行化** —— 乐观锁的意义被抹掉 | 同上 |

并且搬迁前 README 未决 #12 已明确记载：

> **「跨实例共享同一份数据仍然不成立：内存 Store 是每进程一份、没有失效通知」**

**结论**：号源是**唯一**不能走内存 Store 的域。

## 2. 决策（Decision）

### 2.1 一句话

> **号源 / 挂号单独成域，不进 `PersistedState`，由 MySQL 权威；
> 扣减用参数化原子 `UPDATE` + `version` 乐观锁 + `remain_num > 0` 条件，
> 与挂号单 INSERT 同处一个 `withTransaction`。**

### 2.2 具体做法

```cangjie
// ★ rev.3：**一次成功**的原子自减 —— 不带 version 条件。
//   防超卖只依赖两件事，且都在同一条 UPDATE 内由 InnoDB 原子求值：
//     · remain_num = remain_num - 1  （原子自减，不丢更新）
//     · remain_num > 0               （永不减成负数）
// 利用 DbBackend.exec(sql, params) 的**受影响行数**返回值（搬迁前 db.cj:100-105）。
let n = db.exec(
  "UPDATE schedule SET remain_num = remain_num - 1, version = version + 1 " +
  "WHERE id = ? AND remain_num > 0 AND enabled = 1",
  [DbInt(sid)])

if (n == 1) {
  // 抢到号 → 写挂号单（同事务）
} else {
  // n == 0 ⇒ **号真的放完了**。不重试（重试只会再拿 0 行）
}
```

> ⚠ **rev.1/rev.2 这里写的是** `AND version = ?` 乐观锁 + 失败重试。
> 实测它在"请求数 ≈ 号源数"时少卖 **15%~50%**（见顶部 rev.3 说明），已废弃该条件。
> `version` 仍递增，用途改为**管理端并发编辑**的防覆盖，不再是扣号前置条件。

**四个不可动摇的细节**：

| # | 细节 | 理由 |
| --- | --- | --- |
| ① | `remain_num = remain_num - 1` 走**参数化 SQL 文本**，不用 `UpdateQuery.set()` | `set` **只接受值、不接受列表达式**（搬迁前 `dbquery.cj:492-556`）；需要列表达式时必须手写 SQL（`dbquery.cj:89`） |
| ② | 判定成败**只看 `exec` 返回的受影响行数 `n`**，不先 `SELECT` 再 `UPDATE` | 先读后写会把原子操作拆成竞态窗口（TOCTOU） |
| ③ | `UPDATE` 与挂号单 `INSERT` **同一个 `withTransaction`** | 否则会出现"扣了号没挂号单"或反之 |
| ④ | 幂等键 **按患者隔离**（`patient_id + client_token` 唯一索引），且**退号时释放**（置 NULL） | rev.2 只用全局 `client_token` ⇒ **跨患者泄露**（实测：患者 B 用 A 的 token 会拿到 A 的单且不扣号）；且已取消的单占着 token 会导致重挂 **500** |

### 2.3 为什么新表不会被整体替换波及

`writeDbToMysql(s, cur)` 只遍历 `Snapshot.entities` 里的表（搬迁前 `mysql_store.cj:1097`）。
**新表不进 `PersistedState` ⇒ 整体替换不会碰它 ⇒ 无双写冲突。**

> ⚠️ 此推论**基于 `mysql_store.cj` 的替换语义阅读得出，属推断**（`smart-hospital-project-brief.md`
> §附录C 推断 2 原话：**「建议落地即写测试钉住」**）。
> **验收条件 AC-4 就是钉住它的回归测试** —— 见 §5。

## 3. 备选方案与否决理由（Alternatives）

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| **A. 塞进内存 Store**（照旧范式） | `schedule` 进 `PersistedState`，扣减在 `s.lock` 内改内存 | ❌ 三个代价全中（§1.3）；且与参考系统的乐观锁设计**正面冲突** |
| **B. 号源独立域 + Redis 预扣** | Redis 原子 `DECR` + 异步落库 | ❌ 决策 #3 已定**单院区单实例**，**不需要 Redis**；引入 Redis 等于新增一个必须运维的有状态组件，收益不成立 |
| **C. MySQL 悲观锁**（`SELECT ... FOR UPDATE`） | 行锁串行化 | 🟡 **可行但不选**：单院区量级下与乐观锁性能差距很小，但悲观锁会**长时间持有行锁**，与 `withTransaction` 一起更容易在热点号源上排队。乐观锁在"冲突少"的挂号场景更合适，且与参考系统口径一致 |
| **D. 本项目选定：独立域 + 乐观锁原子 UPDATE** | §2.2 | ✅ **采用** |

> 备注：方案 C 是我们**保留的后手** —— 若 Q5（日门诊量 / 号源放出峰值并发）实测显示
> 乐观锁重试率过高，可局部改为 `SELECT ... FOR UPDATE`，**不影响本 ADR 的其余部分**。

## 4. 后果（Consequences）

### 4.1 正面

- 挂号扣减是**单条原子 SQL**，并发安全由数据库保证，不依赖应用层锁；
- 整库刷盘（`writeDbToMysql`）**不会**因为挂号而重写排班表 —— 写放大被切断；
- `s.lock` **不参与**挂号路径，挂号不再与其它业务的刷盘争锁；
- 单院区单实例部署下无需 Redis。

#### 4.3.1 ⚠ 口径修订（2026-10-07 复查）：把「域」拆成两层

> ### ★ AC-4 现在做到了什么（四层，逐层加强）
>
> `mem_store.cj` 落地了配套域的内存 Store（照搬迁前 `store.cj` + `writeDbToMysql` 的本质：
> **一个事务内整体替换清单里的表**），于是 AC-4 可以真跑一次刷盘。四层断言：
>
> | 层 | 验什么 | 为什么必须有这一层 |
> | --- | --- | --- |
> | ① 机制 | `MEM_TABLES ∩ BOOKING_DOMAIN_TABLES = ∅`，且 schedule/appointment 不在 Store 清单里 | 根因层：刷盘的**遍历源**里就没有号源域 |
> | ② **SQL 痕迹** | 用 `SqlRecorder` 把刷盘实际发出的 SQL 全录下来，断言 `schedule`/`appointment` **从未出现在任何一条语句里** | ★ 这是"**根本没碰**"，比"碰了但值没变"强。**实测证据**：故意让刷盘只**读**一下 schedule（不改值）→ 本层 FAIL 而逐值比对仍 PASS —— 恰好证明少了这层就漏检 |
> | ③ 逐值比对 | 从 `information_schema` 取**全列**，刷盘前后逐行逐列比对 | 防"SQL 里没提但通过别的路径改了"；只比 `remain_num` 之类少数列是**弱**的 |
> | ④ 反向 | 刷盘**确实**改了它该管的 4 张表（行数 > 0、数据落库） | 防"因为什么都没做"而**假绿** —— 这正是本项目反复踩到的"永远绿色的假保证" |
>
> **变异测试**（两道，都实测过）：
>   · 把 `TABLE_SCHEDULE` 混进 `MEM_TABLES` → ① 层 4 项 FAIL；
>   · 让刷盘顺手 `SELECT COUNT(*) FROM schedule` → ② 层 FAIL。
>
> ⚠ 仍如实标注的差异：本 Store 的刷盘是**整表替换**（简化），搬迁前是**脏行裁剪**。
> 两边都不碰号源域 ⇒ AC-4 的不变量成立；且整表替换是**更强**的写放大，
> 连它都不波及号源域，脏行裁剪版更不会。性能差异不在 AC-4 范围。
>
> **AC-7 的由来**：这是 2026-10-07 复查发现并修掉的**真缺陷**。原 `cancel()` 返回
> `tx.cancelDone && tx.released`，当 `releaseSlotFor` 失败（如管理员重置过号源使
> `remain_num == total_num`）时，事务**已提交** —— 单子取消了、号没还回，却对外报 `false`，
> 调用方会误以为"取消失败"从而重复重试或误导用户。已改为三态 `CancelOutcome`
> （`Cancelled` / `SlotNotRestored` / `NotFound`），并补 AC-7 钉住。
>
> **测试有效性已用变异测试证明**：把 `AND version = ?` 中性化为 `AND (version = ? OR 1 = 1)`
> 后（保留参数个数），AC-1 当场报 3 条 `[FAIL]`；恢复后重新全绿。
> 首次尝试变异时因参数个数不匹配导致 `bindSql` 抛异常、测试**静默中断**，
> 这促使我们给测试加了 `section()` 异常兜底 —— **失败必须被说出来，不能靠崩溃表达。**
>

> AC-1/2/3/5/6/7/8 已实测通过，AC-4 的剩余部分有明确的 P1 归属与理由，故本 ADR 维持 **Accepted**。

### 5.1 ⚠ 验收依据：**源码哈希 + 测试**，不是产物哈希

2026-10-07 实测确认：**cjc 的产物不逐字节可复现** —— 同一份源码连续两次构建，
`hospital-server.exe` 的 SHA256 不同（行为一致，属编译器正常现象：内嵌时间戳/路径/布局差异）。

| 对象 | 连续两次构建是否一致 |
| --- | --- |
| `hospital-server.exe` 的 SHA256 | ❌ **不同** |
| `build/SOURCE-MANIFEST.sha256` 的 SHA256（当时 43 个源文件；现在是轻舟框架 38 + 业务 33 = **71**） | ✅ **相同** |

**因此：产物哈希不能当验收依据**，可复现的锚点是
**`build/SOURCE-MANIFEST.sha256`（记录每个参与编译源文件的 SHA256 + cjc 版本 + stdx 路径 + 驱动产物哈希）
配合测试结果**。`build.ps1` 每次构建都会重写该清单，口径与框架副本的 `MANIFEST.sha256` 一致。

## 6. 调参项（Tuning Knobs · 带安全范围）

| 参数 | 含义 | 安全范围 | 说明 |
| --- | --- | --- | --- |
| `MAX_BOOKING_RETRY` | **瞬时错误**（死锁/锁等待超时）的重试次数 | **1 – 3**（默认 **3**） | ⚠ rev.3 起**不再用于 version 冲突**（扣号已无 version 前置条件，正常争抢一次成功）。它只管 InnoDB 瞬时异常；命中率若显著上升，说明该加排队/换方案 C |
| `HTTP_BOOKING_RETRY` | HTTP 层传入的同一预算 | **6**（默认） | ⚠ rev.3 说明：**它原先是为"抗乐观锁冲突"设的，现已失去存在意义**——正常路径不再需要重试。保留是为了兼容调用签名；**实际生效值受 `MAX_BOOKING_RETRY` 语义约束**（只对瞬时错误生效） |
| 幂等键口径 | `(patient_id, client_token)` 唯一 | — | **按患者隔离** + **退号置 NULL 释放**（rev.3）。这是幂等的**唯一**保证（先查 + 唯一索引兜底 + 捕获冲突回读），rev.4 起不再有登记表 |
| ~~幂等窗口~~ | ~~`booking_idem` 清理窗口~~ | — | **rev.4 已删除**（该表不再存在）。若将来引入"无天然唯一键"的写操作需重新设计，并重开 ADR |
| 号源放出上限 | 单排班 `remain_num` 上限 | 建议 **≤ 200** | 超过则单行成为热点行，需按 Q5 实测决定是否分段 |
| 事务超时 | `withTransaction` 允许时长 | **≤ 3s** | 事务内**禁止**调用外部模型/HTTP —— 见下 |

🚫 **铁律**：`withTransaction` 内**绝不允许**出站网络调用（AI 模型/HTTP）。
搬迁前已立此纪律（`h_ai.cj` 的 `aiAgentLoop`：锁外调模型 → 锁内跑 1 个工具 → 锁外回灌）。
挂号事务里同理 —— **不允许"调 AI 判断该挂哪个科"再扣号**。

## 8. 复审触发条件

出现以下任一情况时，本 ADR **必须复审**：

1. ~~实测挂号峰值并发使 `MAX_BOOKING_RETRY` 耗尽率 > 1% → 重估方案 C~~
   → ★ **本条已被命中并处置（rev.3）**：实测最穷工况（请求数≈号源数）少卖 15%~50%，
   远超 1% 阈值。处置**不是**加重量次数，而是**去掉 version 乐观锁前置条件**（见顶部 rev.3）。
   实测修复后 20/30/40/50 并发抢同数号源**全部卖光、零少卖**。
   若**再**出现瞬时错误重试耗尽（`MAX_BOOKING_RETRY`），仍按本条走：加排队或改方案 C。
2. 需要**跨域事务**（挂号与病历/支付同时原子）→ 双范式方案本身破产，需重新设计；
3. 引入**第二个号源写入方**（如 HIS 对接）→ "同一条 UPDATE 内原子判定"的假设仍成立，
   但 `remain_num` 的**语义**要重新定义（谁有权改号源）；**必须复审**；
4. 需要**水平扩展**（突破决策 #3 单实例）→ 内存 Store 与直接 SQL 的边界要重新划；
5. 本侧需要**第 4 张**走直接 SQL 的表 → 必须回到 §4.3 重新论证并扩写范围锁死清单；
6. 幂等键口径再变（如需要保留"哪个 token 建的"历史）→ rev.3 用"退号置 NULL"换取了
   token 复用，**代价是不再保留 token 历史**；若将来要审计这条，需重新设计（见 §6）。
