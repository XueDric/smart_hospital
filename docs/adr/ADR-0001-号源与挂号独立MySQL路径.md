## 1. 背景（Context）

### 1.1 搬迁前服务端的持久化范式

搬迁前的服务端持久化范式是**全量载入内存 + 全局锁 + 每次提交整体替换各表** —— 证据是搬迁前的 `mysql_store.cj:30-37`（"一次提交要整体替换 7 张表"）与其 `docs/` 与 `README.md` 未决 #12 / S-14。该范式对**早期那类小体量业务**是合适的：数据量小（千人档）、读多写少、单实例、业务不要求毫秒级扣减。

### 1.2 挂号场景提出的新要求

参考系统给出两条必须对齐的机制：

1. **防超卖**：排班表 `version` 乐观锁 + 扣减带 `remain_num > 0` 条件；
2. **顺延不串号**：挂号单保存 `visit_date` **就诊日快照**。

第 2 条与持久化路径无关，照做即可。**第 1 条是本决策的全部压力来源。**

### 1.3 为什么不能把排班表塞进 `PersistedState`

若把 `schedule` 放进现有内存 Store，会**同时**继承三个代价：

| # | 代价 | 依据 |
| --- | --- | --- |
| 1 | **整表替换写放大** —— 每次挂号重写整个排班/订单表 | `mysql_store.cj:30-37` |
| 2 | **`s.lock` 跨一次网络事务持有** —— 全部挂号串行化，且与整库刷盘争锁 | 搬迁前 S-14：「这把锁是**跨一次网络事务**持有的」 |
| 3 | **并发扣减被完全串行化** —— 乐观锁的意义被抹掉 | 同上 |

并且搬迁前 README 未决 #12 已明确记载「**跨实例共享同一份数据仍然不成立：内存 Store 是每进程一份、没有失效通知**」。

**结论**：号源不能走内存 Store —— 它是唯一需要并发扣减的域。

## 2. 决策（Decision）

### 2.1 一句话

> **号源 / 挂号单独成域，不进 `PersistedState`，由 MySQL 权威；扣减用参数化原子 `UPDATE` + `remain_num > 0` 条件，与挂号单 INSERT 同处一个 `withTransaction`。**

### 2.2 具体做法

```cangjie
// ★ 一次成功的原子自减 —— 不带 version 条件。
//   防超卖只依赖两件事，且都在同一条 UPDATE 内由 InnoDB 原子求值：
//     · remain_num = remain_num - 1  （原子自减，不丢更新）
//     · remain_num > 0               （永不减成负数）
// 利用 DbBackend.exec(sql, params) 的**受影响行数**返回值（搬迁前 db.cj:100-105）。
let n = db.exec(
  "UPDATE schedule SET remain_num = remain_num - 1, version = version + 1 " +
  "WHERE id = ? AND remain_num > 0 AND enabled = 1",
  [DbInt(sid)])

if (n == 1) {
  // 抢到号 → 写挂号单（同事务）
} else {
  // n == 0 ⇒ **号真的放完了**。不重试（重试只会再拿 0 行）
}
```

**四个不可动摇的细节**：

| # | 细节 | 理由 |
| --- | --- | --- |
| ① | `remain_num = remain_num - 1` 走**参数化 SQL 文本**，不用 `UpdateQuery.set()` | `set` **只接受值、不接受列表达式**（搬迁前 `dbquery.cj:492-556`）；需要列表达式时必须手写 SQL（`dbquery.cj:89`） |
| ② | 判定成败**只看 `exec` 返回的受影响行数 `n`**，不先 `SELECT` 再 `UPDATE` | 先读后写会把原子操作拆成竞态窗口（TOCTOU） |
| ③ | `UPDATE` 与挂号单 `INSERT` **同一个 `withTransaction`** | 否则会出现"扣了号没挂号单"或反之 |
| ④ | 幂等键 **按患者隔离**（`patient_id + client_token` 唯一索引），且**退号时释放**（置 NULL） | 只用全局 `client_token` ⇒ **跨患者泄露**（实测：患者 B 用 A 的 token 会拿到 A 的单且不扣号）；且已取消的单占着 token 会导致重挂 **500** |

#### 为什么扣号不设 `version` 前置条件

`version` 乐观锁 + 重试在最穷工况（请求数 ≈ 号源数）下**严重少卖**：

| 工况 | 乐观锁（`AND version = ?` + 重试） | 原子自减（本决策） |
| --- | --- | --- |
| 20 并发抢 20 号 | 只卖出 **15~17** | **20** ✅ |
| 30 并发抢 30 号 | 只卖出 **22~23** | **30** ✅ |
| 40 并发抢 40 号 | 只卖出 **25~26** | **40** ✅ |
| 50 并发抢 50 号 | （未测） | **50** ✅ |

原因：N 个请求同时读到同一个 `version`，只有一个能成功，其余作废；重试时它们又读到同一个新 `version`、再次互撞 —— 重试预算迅速耗尽（耗竭率实测高达 50%）。

**这是正确性上的改进，不是冒险**：防超卖真正依赖的两件事（`remain_num = remain_num - 1` 与 `remain_num > 0`）在**同一条 UPDATE 内**由 InnoDB 原子求值，不存在"检查-后-写"的跨语句窗口；乐观锁解决的恰是跨语句场景，这里**不适用** —— 它只贡献了"并发请求互相作废"。`version` 列保留并继续 +1，用于**管理端并发编辑**（防覆盖别人的排班改动）。

### 2.3 为什么新表不会被整体替换波及

`writeDbToMysql(s, cur)` 只遍历 `Snapshot.entities` 里的表（搬迁前 `mysql_store.cj:1097`）。**新表不进 `PersistedState` ⇒ 整体替换不会碰它 ⇒ 无双写冲突。** 此推论**基于 `mysql_store.cj` 的替换语义阅读得出，属推断**；**验收条件 AC-4 就是钉住它的回归测试** —— 见 §5。

### 2.4 全域数据访问范式：直接 SQL 唯一化

服务端**只有一种数据访问范式：直接 SQL**。全部 17 张表按域划分：

| 域 | 表 | 一致性手段 | 写入口 |
| --- | --- | --- | --- |
| **号源域** | `schedule`、`appointment` | 原子自减 + `withTransaction` + 唯一索引 | `BookingRepo` 独占 |
| **基础数据域** | `department`、`doctor`、`patient` | 条件 UPDATE / 唯一索引 | 管理端端点（`patient` 无写入端点） |
| **病历域** | `medical_record` | 逐条 upsert | `MedicalRecordRepo` 独占 |
| **鉴权域 / 预问诊域 / AI 配置域 / 统计域** | 其余表 | 条件 UPDATE / 唯一索引 | 各自 Repo |

**为什么病历与号源/挂号同属"直接 SQL"却不是同一类**：两者共享"MySQL 权威"，但理由不同 —— 号源/挂号是因为**并发正确性**（内存 Store 三个代价全中，见 §1.3），病历是因为**持久性**（诊断与处理意见不能只活在进程内存里）；所以 `selftest` 里它们仍是**两个不同的类**（`BOOKING_DOMAIN_TABLES` vs 病历域）—— 分类的意义是让**纪律**可见，合并就看不到了。

**为什么不再保留内存 Store 范式**：它从未在**生产路径**上接线 —— `MemStore` 的生产实例化点、`loadAll()`/`flushToMysql()` 的生产调用点都是**零**，也没有"往内存里写"的入口方法；生产代码对 `department`/`doctor`/`patient` 三张表的写为零、读为 11 行（看板 3 个计数、分诊 2 处科室名查询），这三张表在业务侧是**只读参考数据**，维护走管理端端点或人工 SQL（见 §4.2）。一条从未走过的路径会让文档与实现不一致、让验收去验证一个生产上不存在的机制、让读者以为数据流是那样走的 —— **这是负资产**，因此整体拆除。

**消失的是"范式"，不是"表"**：`department`/`doctor`/`patient` **仍然在库里、仍在 `ALL_TABLES` 里、仍被人读**，只是不再经内存 Store；`selftest` 给它们的归属是**基础数据域**（直接 SQL 读）。

> 📌 教训：**删一个概念时，先问"挂在它下面的实体去哪"。** 把实体一起删掉 = 数据丢失；连分类一起删掉 = 断言数不上账（求和 = 9 而 `ALL_TABLES.size` = 12，那条断言恰好把它抓住了）。正确做法是**重新归类，并写明新纪律**。

## 3. 备选方案与否决理由（Alternatives）

| 方案 | 做法 | 否决理由 |
| --- | --- | --- |
| **A. 塞进内存 Store**（照旧范式） | `schedule` 进 `PersistedState`，扣减在 `s.lock` 内改内存 | ❌ 三个代价全中（§1.3）；且与参考系统的乐观锁设计**正面冲突** |
| **B. 号源独立域 + Redis 预扣** | Redis 原子 `DECR` + 异步落库 | ❌ 决策 #3 已定**单院区单实例**，**不需要 Redis**；引入 Redis 等于新增一个必须运维的有状态组件，收益不成立 |
| **C. MySQL 悲观锁**（`SELECT ... FOR UPDATE`） | 行锁串行化 | 🟡 **可行但不选**：单院区量级下与乐观锁性能差距很小，但悲观锁会**长时间持有行锁**，与 `withTransaction` 一起更容易在热点号源上排队。乐观锁在"冲突少"的挂号场景更合适，且与参考系统口径一致 |
| **D. 本项目选定：独立域 + 原子 UPDATE** | §2.2 | ✅ **采用** |

> 方案 C 是**保留的后手** —— 若 Q5（日门诊量 / 号源放出峰值并发）实测显示瞬时错误重试耗尽率过高，可局部改为 `SELECT ... FOR UPDATE`，**不影响本 ADR 的其余部分**。

## 4. 后果（Consequences）

### 4.1 正面

- 挂号扣减是**单条原子 SQL**，并发安全由数据库保证，不依赖应用层锁；
- 整库刷盘（`writeDbToMysql`）**不会**因为挂号而重写排班表 —— 写放大被切断；
- `s.lock` **不参与**挂号路径，挂号不再与其它业务的刷盘争锁；
- 单院区单实例部署下无需 Redis。

### 4.2 负面 —— 架构债与现状

架构债已还清：服务端只剩一种数据访问范式（见 §2.4），域的分类按**纪律**划分、不按"用哪种范式"划分；两套范式并存时的三项代价随之消失 —— 不必再判断某个域该走哪条路（只有一条路）、"新人上手成本"下降（只有一套代码）、跨域事务变得可行（都在 MySQL 里，可同事务）。

**边界**：

- 跨域事务**能力已具备、尚未使用** —— 挂号与病历仍是各自独立的写，不要误读成"已经这么做"；
- `department`/`doctor` 有管理端写入端点（`server/src/http_base.cj` 的 `/api/v1/admin/departments`、`/api/v1/admin/doctors`，GET/POST/PUT/DELETE）；
- `patient` **没有**写入端点，靠人工 SQL 维护。

### 4.3 风险控制（把范围关进笼子）

| 控制 | 做法 |
| --- | --- |
| **范围锁死** | `BookingRepo` 的直接 SQL **写入**仅限其拥有的 **2 张表**：`schedule` / `appointment`。新增表必须再开 ADR |
| **测试钉住** | AC-4 四层断言 + `selftest` 断言"表集里无 `idem` 命名表" |
| **文档标注** | `server/src/` 中走直接 SQL 的文件，文件头注释必须指向本 ADR |
| **写路径纪律** | Code review 检查项：号源域的写入只出现在 `BookingRepo`；跨域写必须显式放进 `withTransaction` |

#### 4.3.1 直接 SQL 的写入范围

域与表的归属见 §2.4。本 ADR 的约束精确为：**由 `BookingRepo` 执行的直接 SQL 写只准落在这 2 张表上**（`isBookingOwnedTable()` 是可执行的判定）。新增第 3 张由 `BookingRepo` 写的表，仍必须先开新 ADR —— 范围锁死的强度不因其他域也走直接 SQL 而变化。

#### 4.3.2 表名与搬迁前内存 Store 的撞名纪律

搬迁前的内存 Store 自己有一张 **`idem`** 表（搬迁前 `mysql_store.cj:892` 的 `PersistedState.idem`；DDL 同名，该文件 §309-311 明说「表名与 `store.cj` 的逻辑表名**一一同名**」）。搬迁前完整表名集合是：

`departments` `members` `plans` `tasks` `invite_links` `tokens` `idem` `meta` `meta_str` `schema_version`

**纪律：本侧所有表名必须与这 10 个零交集**（例：`auth_token` 不叫 `tokens`）。否则搬迁前内存 Store 的整库刷盘（`replaceBatched("idem", …)`）会与本侧的表**争同一张表**。该纪律由 `selftest` 与 AC-4 的双重断言钉住（改名若回退，两条断言当场变红），且比对范围是**本侧全部业务表**与那侧**全部**表名 —— 只比号源域两张表会漏掉非号源域的撞名。

## 5. 验收条件（Acceptance Criteria · 可测试）

| # | 验收条件 | 测试方式 | 状态 |
| --- | --- | --- | --- |
| **AC-1** | 同一号源的两个并发扣减，**恰好一个**成功（`n=1`），另一个 `n=0` | 单测：对同一 `work_date` 连发两次 `UPDATE … remain_num > 0`，断言 `n` 序列为 `[1, 0]` | ✅ **PASS** |
| **AC-2** | `remain_num = 0` 时扣减必然失败（`n=0`），**绝不出现负数** | 单测：置 `remain_num=0` 后扣减，断言 `n=0` 且库中仍为 0 | ✅ **PASS** |
| **AC-3** | 同一 `client_token` 重复提交，**只产生一张挂号单** | 单测：同 token 连续两次 `book()`，断言第二次返回既有单、`COUNT(*)=1` | ✅ **PASS** |
| **AC-4** | ★ **数据访问范式唯一化**：①每张业务表归属唯一域，无孤儿表；②号源域的表只准 `BookingRepo` 写，域清单与表集不脱节；③表名与搬迁前内存 Store 零交集；④号源域确实**有**数据（否则③是"空比空"的假绿） | `acceptance.cj` 四层断言 + `selftest` 表集分类 | ✅ **PASS** |
| **AC-5** | 挂号失败（`n=0`）时**不留下部分状态**（无挂号单、号源数不变） | 单测：制造冲突后断言两表均未变 | ✅ **PASS** |
| **AC-6** | `visit_date` **就诊日快照**：顺延排班后，已挂号单的 `visit_date` 不变 | 单测：挂号 → 改 `schedule.work_date` → 断言挂号单 `visit_date` 仍是原值 | ✅ **PASS** |
| **AC-7** | ★ 退号：**取消成功必须如实上报** —— 归还失败时不得谎报"取消失败" | 单测：制造 `remain_num == total_num` 后 `cancel()`，断言返回 `SlotNotRestored` **且**挂号单确已 `cancelled` | ✅ **PASS** |
| **AC-8** | （不适用）本设计不含幂等登记表；幂等的覆盖在 **AC-3**（同 token 重复提交） | — | — |
| **AC-9** | ★ **多进程真并发**下「成功数 == 号源数」且余量守恒 | `tests\stress-booking.ps1`：N 个**独立进程**打同一号源 | ✅ **PASS**（20/30/40/50 四档全部恰好卖光） |
| **AC-10** | ★ **最穷工况（请求数 == 号源数）不少卖** | 单测：连续 N 次 `tryDeductSlot`，断言 N 次全成功、余量归零 | ✅ **PASS** |

**实测记录**（全部在仓库自管 devdb 上重跑）：

| 套件 | 结果 |
| --- | --- |
| `hospital-server.exe selftest` | ✅ **51 项** |
| `hospital-server.exe authtest` | ✅ **17 项**（含 3 个公开测试向量） |
| `hospital-server.exe accept <dsn>` | ✅ **821 项 / 失败 0** |
| `tests\stress-booking.ps1` | ✅ **20/30/40/50 并发抢同数号源 → 全部恰好卖光、零 409、零少卖** |

> **AC-1 / AC-9 的验证边界（不冒充）**：本仓库通篇没有 `spawn`（仓颉侧无线程用法），所以验证拆成两层、**都不冒充多线程** —— **AC-1**（单元级）断言"每次扣减都恰好消耗一个单位号源、永不为负"这条**数据库层不变量**；**AC-9**（端到端）由 `tests\stress-booking.ps1` 起 **N 个独立 `curl.exe` 进程**打同一号源，断言"成功数 == 号源数"，这才是"真并发"的形态。
> **AC-4 的断言全部从表集常量派生，不写死数字** —— 断言要钉不变量，不要钉数字；也不写"没有内存 Store"这类运行期断言：那些名字已经不存在，硬写一个字符串比较是**空洞**的（只是在比自己的字面量）。这条交给**编译器**：引用已不存在的符号会直接编译失败，**编译期保证比任何运行期断言都硬**。
> **AC-7 的由来**：`cancel()` 的返回语义决定调用方行为。`releaseSlotFor` 失败时（如管理员重置过号源使 `remain_num == total_num`）事务**已提交** —— 单子取消了、号没还回；若对外报 `false`，调用方会误以为"取消失败"从而重复重试或误导用户。因此 `cancel()` 返回三态 `CancelOutcome`（`Cancelled` / `SlotNotRestored` / `NotFound`），由 AC-7 钉住。
> 验收套件的 `section()` 带异常兜底：绑定参数不匹配之类的失败必须被**报出来**，不能靠崩溃中途静默 —— **失败必须被说出来，不能靠崩溃表达。**

### 5.1 验收依据：**源码哈希 + 测试**，不是产物哈希

实测确认：**cjc 的产物不逐字节可复现** —— 同一份源码连续两次构建，`hospital-server.exe` 的 SHA256 不同（行为一致，属编译器正常现象：内嵌时间戳/路径/布局差异）。

| 对象 | 连续两次构建是否一致 |
| --- | --- |
| `hospital-server.exe` 的 SHA256 | ❌ **不同** |
| `build/SOURCE-MANIFEST.sha256` 的 SHA256（轻舟框架 38 + 业务 38 = **76** 个源文件） | ✅ **相同** |

**因此：产物哈希不能当验收依据**，可复现的锚点是**`build/SOURCE-MANIFEST.sha256`（记录每个参与编译源文件的 SHA256 + cjc 版本 + stdx 路径 + 驱动产物哈希）配合测试结果**；`build.ps1` 每次构建都会重写该清单，口径与框架副本的 `MANIFEST.sha256` 一致。

## 6. 调参项（Tuning Knobs · 带安全范围）

| 参数 | 含义 | 安全范围 | 说明 |
| --- | --- | --- | --- |
| `MAX_BOOKING_RETRY` | **瞬时错误**（死锁/锁等待超时）的重试次数 | **1 – 3**（默认 **3**） | 不用于 version 冲突（扣号已无 version 前置条件，正常争抢一次成功）。它只管 InnoDB 瞬时异常；命中率若显著上升，说明该加排队/换方案 C |
| `HTTP_BOOKING_RETRY` | HTTP 层传入的同一预算 | **6**（默认） | 正常路径不需要重试，保留是为了兼容调用签名；**实际生效值受 `MAX_BOOKING_RETRY` 语义约束**（只对瞬时错误生效） |
| 幂等键口径 | `(patient_id, client_token)` 唯一 | — | **按患者隔离** + **退号置 NULL 释放**。这是幂等的**唯一**保证（先查 + 唯一索引兜底 + 捕获冲突回读），不设独立登记表 |
| 号源放出上限 | 单排班 `remain_num` 上限 | 建议 **≤ 200** | 超过则单行成为热点行，需按 Q5 实测决定是否分段 |
| 事务超时 | `withTransaction` 允许时长 | **≤ 3s** | 事务内**禁止**调用外部模型/HTTP —— 见下 |

🚫 **铁律**：`withTransaction` 内**绝不允许**出站网络调用（AI 模型/HTTP）。搬迁前已立此纪律（`h_ai.cj` 的 `aiAgentLoop`：锁外调模型 → 锁内跑 1 个工具 → 锁外回灌）；挂号事务里同理 —— **不允许"调 AI 判断该挂哪个科"再扣号**。

## 8. 复审触发条件

出现以下任一情况时，本 ADR **必须复审**：

1. 实测挂号峰值并发使瞬时错误重试耗尽率 > 1% → 重估方案 C（悲观锁），或加排队；
2. 需要把**跨域事务**（挂号与病历/支付同时原子）作为常规路径 → 需重新划定域边界与 `BookingRepo` 独占写的约束；
3. 引入**第二个号源写入方**（如 HIS 对接）→ "同一条 UPDATE 内原子判定"的假设仍成立，但 `remain_num` 的**语义**要重新定义（谁有权改号源）；**必须复审**；
4. 需要**水平扩展**（突破决策 #3 单实例）→ 需重新评估是否引入缓存，并重新划分一致性边界；
5. `BookingRepo` 需要写**第 3 张**表 → 必须回到 §4.3 重新论证并扩写范围锁死清单；
6. 幂等键口径再变（如需要保留"哪个 token 建的"历史）→ 现有做法用"退号置 NULL"换取 token 复用，**代价是不再保留 token 历史**；若将来要审计这条，需重新设计（见 §6）。
