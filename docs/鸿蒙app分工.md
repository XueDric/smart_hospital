


# 三人团队鸿蒙端分工方案

## 一、项目背景速览

本方案对应的是一套基于 **FastAPI + LangChain + ReAct Agent** 的智慧医院智能导诊就诊系统，服务端由外部团队负责。现有前端采用 **Vue 3 + Element Plus**，主题为医疗青绿色（`#00a9a7`），功能覆盖：

- **患者端**：智能分诊、预问诊、预约挂号、我的就诊
- **医生端**：门诊接诊、电子病历
- **管理端**：基础数据、AI 能力中心、运营看板

鸿蒙端需要从零使用 **ArkTS + ArkUI** 原生重写。这意味着无法直接复用 Vue 的 UI 代码，但可以复用接口协议和业务逻辑设计。

## 二、角色定义

基于“三个鸿蒙开发 + 一人兼设计”的约束，推荐以下角色划分：

| 角色 | 核心定位 | 是否兼设计 |
| --- | --- | --- |
| A | 鸿蒙开发：基础架构 + 患者端 | 否 |
| B | 鸿蒙开发：医生端 + 管理端 | 否 |
| C | 鸿蒙开发：公共模块 + 鸿蒙/安卓界面设计 | 是 |

C 的双重职责是整个方案中最关键的约束。建议将 C 的设计工作时间控制在 **40% 以内**，其余 **60%** 投入公共模块开发，避免设计任务挤压开发进度。

## 三、详细分工

### A：基础架构 + 患者端

#### 基础架构职责

- 搭建 DevEco Studio 多模块工程骨架，按照 `entry`（壳工程）+ `common-core`（公共层）+ `feature-*`（功能模块）的分层结构初始化项目。
- 封装网络层：
  - 统一 HTTP 请求客户端。
  - Bearer Token 注入。
  - SSE 流式解析。预问诊的流式打字机输出依赖 SSE。
- 搭建统一路由注册表，各 `feature` 模块向 `common-core` 中的 Router 注册页面。
- 与外部服务端团队对接接口协议，输出接口对接文档供 B、C 参考。

#### 患者端开发职责

- **智能分诊页面**：输入主诉，展示推荐科室、医生、置信度、危急等级和推理步骤。
- **智能预问诊页面**：多轮对话采集病情，SSE 流式输出，约第 5 轮生成预问诊摘要。
- **预约挂号页面**：按科室、医生、日期筛选号源，支持乐观锁扣号和取消归还。
- **我的就诊 / 医疗档案 / 医疗公告页面**。

建议页面数：**6-8 个**。

### B：医生端 + 管理端

#### 医生端开发职责

- **门诊接诊页面**：查看本人挂号队列，开始、结束或取消接诊。
- **电子病历页面**：采用七段式结构，包括主诉、现病史、既往史、过敏史、体格检查、诊断、处理意见；支持草稿保存和提交锁定。

#### 管理端开发职责

- **基础数据管理**：用户、科室、医生、排班号源、患者档案、症状标签库。
- **AI 能力中心**：Prompt 管理、知识库维护。
- **运营看板**：关键指标可视化展示。

#### 辅助职责

- 与 A 共同维护接口对接，负责医生端和管理端的接口联调。
- 负责应用打包、签名配置、华为 AGC 平台相关操作。

建议页面数：**8-10 个**。

### C：公共模块 + 界面设计（双职责）

#### 设计职责（约 40% 精力）

##### 鸿蒙端设计

- 制定医疗青绿主题的鸿蒙设计规范：
  - 建立颜色资源体系。
  - 遵循鸿蒙色彩引用规范，禁止硬编码色值。
  - 配置浅色和深色双模式。
- 统一尺寸规范：
  - 全局采用 `vp` 单位。
  - 遵循 `8vp` 基线网格。
  - 可点击控件热区最小为 `40vp × 40vp`。
- 字体体系：
  - 手机端基准为 `16fp`。
  - 使用鸿蒙动态字阶。
- 设计核心页面视觉稿：登录、首页、智能分诊（对话式界面）、预约挂号。

##### 安卓端设计

- 复用同一套视觉语言，但遵循 **Material Design 3** 规范调整组件样式。
- 重点适配差异点：鸿蒙的 `RelativeContainer` 相对定位粒度比 Android 更粗，布局方案需要分别设计。
- 输出双端设计标注文档，统一交付给 A 和 B 作为开发依据。

##### 设计工具建议

- 使用 DevEco Studio 的预览器 + Inspector 双向预览验证鸿蒙端设计效果，支持代码编辑器、UI 界面和组件树三者联动。
- 设计稿工具不限，Figma / Sketch 均可，但必须输出包含 `vp/fp` 标注的规范文档。

#### 公共模块开发职责（约 60% 精力）

- **公共 UI 组件库**：基于设计规范封装基础组件，如按钮、输入框、卡片、列表项、标签等，放在 `common-core` 中供 A、B 复用。
- **状态管理**：统一使用 ArkTS 状态管理 V2 版本，包括 `@Local`、`@Param`、`@Event`、`@Provider/@Consumer`，避免 V1/V2 混用。
- **数据持久化层**：封装偏好存储、文件存储等能力。
- **主题切换**：实现深色/浅色模式切换逻辑。
- **登录态管理**：Token 刷新、登录拦截等。

## 四、协作机制

### 1. 模块边界与接口约定

按照“依赖单向：`app → feature → common-core`，业务模块之间禁止互相 `import`”的原则组织工程结构。

A 和 B 各自的功能模块通过 `common-core` 中的路由和网络层通信，不直接互相依赖。

### 2. 接口对接节奏

- **第一周**：A 完成网络层封装，与外部服务端团队确认全部接口协议。
- **第二周起**：A、B 并行开发，C 完成设计规范 + 公共组件初版。
- **联调阶段**：按模块独立联调，A 负责患者端接口，B 负责医生端和管理端接口。

### 3. 设计交付节奏

C 的设计工作建议前置：

- **第 1 周**：完成设计规范，包括色彩、字体、间距、组件基础样式。
- **第 2 周**：完成核心页面高保真设计稿。
- **第 3 周起**：边开发公共组件，边迭代细节设计。

### 4. 可复用的现成资源

华为开发者联盟提供了医疗健康类 HarmonyOS 模板，包含健康数据可视化、预约挂号等场景的现成组件，可以直接参考或复用，大幅减少从零设计的工作量。

此外，现有的 Vue 3 前端已经完成了交互设计和业务逻辑梳理。鸿蒙端可以直接参照 Vue 端的页面结构和交互流程进行 ArkTS 重写。C 的设计工作更多是在视觉层做鸿蒙原生适配，而非从零开始设计交互。

## 五、关键风险与应对

### 1. C 的设计任务挤压开发进度

**应对**：设计规范在第一周集中输出后冻结，后续设计调整走轻量迭代。C 的公共组件开发可以和 A 的网络层封装并行推进。

### 2. 鸿蒙与安卓设计差异导致返工

**应对**：C 在设计阶段就明确双端差异点，包括布局系统、导航模式、字体渲染等，并在规范文档中分别标注，避免 A、B 按错误规范开发。

### 3. 与外部服务端联调阻塞

**应对**：A 在第一周优先完成网络层封装和 Mock 数据方案。即使服务端接口未就绪，前端也能使用 Mock 数据独立开发，接口就绪后只需替换 BaseURL。
