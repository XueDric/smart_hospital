## 三、仓颉语言侧的三个真实陷阱（回答「仓颉和 Go/Rust 差在哪」用）

> 这一节是评估报告第 ④ 条要的「集中可讲的理解深度」：材料本来散在代码注释里，
> 现在集中成两分钟的答问弹药。**每一句都能指到行号**。

### 陷阱 1：`match` 里用 `String` 常量当 case ⇒ 变成 catch-all

```cangjie
match (name) {
    case PROMPT_DEPT => ...        // ✗ 这里的 PROMPT_DEPT 被当成「绑定变量」，不是常量
    case _ => ...
}
```

- **现象**：`promptDefaultBody(PREVISIT)` 一直返回 **dept 的模板**，四个槽位拿到同一个默认体。
- **为什么**：case 位置上的标识符被当成**模式绑定**（catch-all），按值比较根本没发生 —— 编译器不报错。
- **我们怎么绕**：`server/src/ai_prompt.cj:133-181` 刻意写成 `if (name == PROMPT_DEPT) … if (name == PROMPT_PREVISIT) …`，并把这段踩坑写进注释（`:133-149`），防止后人「美化」成 `match`。

### 陷阱 2：没有 `array.window()`，字符串按「字符」而不是「字节」切

- **要解决的问题**：红牌分诊的**否定窗口** —— 命中词前面 8 个字符内出现「没有/不/无」就作废，但**不能跨分句**、中间隔着「而/但/诱因」也不算。
- **坑**：仓颉标准库没有 `windows(n)`；`String` 的 `size` 是字节长度，中文一个字 3 字节，直接 `size - 8` 会把窗口算成 2.7 个汉字。
- **我们怎么绕**：先把查询转成 `Array<Rune>`（按**码位**而非字节），自己写索引回看 + 分句边界 + 阻断词三段判定，窗口常量全放在文件头（`server/src/triage_redflag.cj:113-143`：`RED_FLAG_NEGATION_WINDOW = 8`、`RED_FLAG_NEGATION_GAP_MAX = 6`、`RED_FLAG_NEGATION_GAP_SHORT = 1`、`RED_FLAG_NEGATION_BLOCKERS`）；`triagetest` 150 项里有专门的反例（「一直头晕」「没有胸口疼」「无法缓解的胸痛」必须报红牌）。

### 陷阱 3：stdx 的 HTTP 与 TLS —— 缺 `connectTimeout`，且不读 Windows 证书存储

- **缺超时**：`stdx.net.http` 的 `Client` 只有 `readTimeout`/`writeTimeout`，**没有 `connectTimeout`**（在 `stdx` 符号表里 grep `connectTimeout` 命中 0）。于是「连不上」这件事没有独立时限。
  绕法：把调用丢进 `spawn` 的 worker，主线程 `Future.get(Duration.second * deadline)` 到点就**如实降级**，并在注释里写清「超时不取消 TCP」这个残留（`server/src/ai_call.cj:333-367`）。
  ——这也是我们被评审扣过的那条的正面回答：**不是没做超时，是框架没给分阶段超时，我们用墙钟兜住并要求自己诚实标注**。
- **TLS 不读系统证书**：仓颉 stdx 的 HTTPS 走 **OpenSSL**，只认 `SSL_CERT_FILE`/`SSL_CERT_DIR`，不读 Windows「受信任的根证书」⇒ 真实模型调用报 `TLS handshake failed (client): certificate verify failed (134)`，而同一台机器 `curl` 一切正常。
  绕法：`server/export-ca-bundle.ps1` 把本机根证书 + 中间 CA 导出成 `server/ca-bundle.pem`，启动前 `$env:SSL_CERT_FILE=<该文件>`。这是**运维动作**（只读证书存储、只写一个文件），已写进 [DEPLOYMENT](DEPLOYMENT.md) 与演示步骤 0。

### 一句话总结（可直接背）

> 仓颉的坑集中在「**标准库还不够厚**」和「**默认不报错**」：`match` 常量被当绑定、没有 `window`、没有 `connectTimeout`、TLS 不认系统证书 —— 前两个靠**读符号表 + 写反例**，后两个靠**墙钟兜底 + 显式环境变量**。

## 四、12 个高概率追问

| # | 追问 | 回答口径 |
|---|---|---|
| 1 | **AI 会不会瞎推荐科室？** | 会提议，不会决定。模型只产出科室名，服务端必须用真实号源库存校验；不通过就降级为"备选号源 + 说明"。演示里那句「本院暂未开诊「消化内科」」就是校验结果。 |
| 2 | **模型挂了怎么办？** | 降级到规则分诊（`source=rules` + `degrade_reason`），用户端不报错。出站最多 2 次尝试（429/5xx/网络异常，退避 200 ms）+ **全链路墙钟上限**（默认 30 s，框架给不出 `connectTimeout`，我们用 `Future.get` 兜住并要求注释诚实标注「超时不取消 TCP」）。 |
| 3 | **怎么证明 AI 真被调用了？** | `ai-live-check.ps1` 26 项断言 + `triage_stat.source` 分布 + 看板 `by_source`。原实现把 `source` 写死 `rules`，我们删了这行——**系统不能自证没调 AI**。 |
| 4 | **密钥怎么管的？** | 库里只存引用（`env:` / `file:` / `builtin:demo`），永不存裸密钥。`builtin:demo` 随源码分发，但带**有效期**（`AI_BUILTIN_DEMO_VALID_UNTIL = 2026-12-31`）：到期后 `aiResolveKey()` 直接拒绝、理由里写明到期日与换法，分诊降级到规则 —— 这是**代码行为**，有 8 条验收断言（`accept` ⑧ 段）盯着，不是文档承诺。评委若想用自己的 key：`tools\set-ai-key.ps1 -ApiKey … -AdminPw …`，一条命令写完并自检；生产用 `env:` 注入 + 吊销轮换。 |
| 5 | **为什么把默认值从关闭改成开启？** | 评审原话是"默认零模型调用"。我们改成"演示默认开、生产必须换 key 或置 0"，并把这条决策写进 `docs/Q6-合规决策记录.md`——不是偷偷改默认值。 |
