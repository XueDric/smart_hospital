# 向量检索状态说明（含答辩口径与启用路径）

> 本文回答评审第 3 条："把向量检索状态讲清楚并补验证"。
> 结论先行：**当前默认能力是关键词检索；向量路的代码与测试已就绪，但未接线到生产调用链，且没有可用的 embedding 服务因而无法端到端演示。** 以下把它拆成"已有什么 / 缺什么 / 怎么补"，并给出一句话答辩口径。

## 一、现在的真实状态（一句话版）

分诊的 RAG 检索**只走关键词路**：`server/src/http_app.cj:1038` 的 `triageRagHits()` 调 `kb.searchKeyword(complaint, topN: KB_SEARCH_TOP_N)`，命中块的 `source` 恒为 `keyword`；危急征象（`red_flag`）时直接返回空（不给模型参考资料）。

**所以缺的不是检索算法，而是"谁来生成向量 + 何时走向量路"这两处接线。**

## 三、为什么没接（诚实原因）

1. **默认对话模型 DeepSeek 没有 `/embeddings` 端点**：`/embeddings` 与 `/v1/embeddings` 实测均 404。种子数据里**向量行单独指向百炼** `text-embedding-v3`（`ai_model.cj` 的 `AI_MODEL_SEED_EMBEDDING_*`），两者故意不同源——但也因此需要一个百炼（或其它）key 才能真正跑。
2. **向量行没有可用密钥**：`ai.key_ref` 是全局引用，内置 `builtin:demo` 的 DeepSeek key 只能发往 `api.deepseek.com`（由 `ai_builtin.cj` 的 host 白名单硬拦），不能用它去调百炼。
3. **不想做"假向量"**：`acceptance_kb.cj` 里的 `[1.0, 2.0, 3.0]` 只是形状与排序的单元测试，用它冒充"向量检索已跑通"是自欺。宁可写清"未接线"。

## 四、答辩口径（可以直接念）

> 我们的 RAG 是**关键词检索 + 余弦向量检索双实现**，当前默认走关键词：因为默认对话模型 DeepSeek 没有 embeddings 端点，而向量行需要的百炼 key 不在演示环境里。向量路的仓储、余弦打分、覆盖率指标与来源标注都已完成并有单元测试，缺的只是"生成向量"的任务接线。给它一个支持 embedding 的服务（百炼 / 自建 bge-m3 / Ollama），改 `ai_model` 的向量行 + 跑 `kb-embed`，检索的 `source` 就会从 `keyword` 变成 `vector`，前端与契约不用动。

## 五、怎么补（三条路，按代价排序）

| 路径 | 步骤 | 代价 | 能否离线 |
| --- | --- | --- | --- |
| A. 百炼 `text-embedding-v3`（已内置该行） | ① `tools/set-ai-key.ps1 -ApiKey <百炼key>` 写 `file:` 引用（向量行的 `key_ref` 单独指它）② 跑一次生成任务（见 §六）③ 重新分诊，检查 `used_kb` 与看板覆盖率 | 最低（模型行不用改） | 否 |
| B. 自建 bge-m3 / Ollama embedding | ① `ai_model` 向量行 base_url 改本机 ② 注意 `ai_model.cj` 目前**强制 https**，本机 http 需先放开"仅 loopback 允许 http"（改动点：`ai_model.cj:268` 的 `startsWithAscii(..., "https://")` 判断）③ 同上生成 + 验证 | 中（要改一处校验 + 拉模型） | 是 |
| C. 离线预计算向量随包分发 | 训练/生成侧离线算好向量，写成 SQL 种子；运行时只做余弦 | 高（数据要跟文档同步） | 是 |
