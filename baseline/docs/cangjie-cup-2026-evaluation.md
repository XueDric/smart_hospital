## 一、结论

**技术底座远高于赛道平均线，但"提交物"严重不完整 —— 现在这样交，会被材料关扣掉一大截分。**

一句话：**这是一个"做得比说得多的项目"，吃亏全在包装。**

| 评分项（官方百分制） | 分值 | 本次估计 | 主要依据 |
|---|---|---|---|
| 系统完整性与运行稳定性 | 25 | **19–21** | 50 条路由 / 22 个页面 / 5 类角色，实测 7 套测试全绿；扣分：客户端 HAP 未签名、公网未部署 |

## 三、逐项对照

### A. 系统完整性与运行稳定性（25 分 → 估 19–21）

赛道要求：*"较完整的用户角色、业务场景、功能模块和数据流程，主要功能之间能够协同运行，并具备必要的异常处理、安全保障和运行维护能力。"*

**已具备（可取证）：**

| 要求 | 实现证据 |
|---|---|
| 完整用户角色 | 5 档身份：会长 / 副会长 / 部长 / 成员 / **运维（`ops`，独立于会长，只能 CLI 创建）**；`Store` 登录态 + 令牌 |
| 完整业务场景 | 组织与成员、任务流转、课题树、招募链接、审批、后台运维，共 **50 条路由**（`main.cj:746-900`：业务 39 + 运维 1 + AI 6 + 页面 2 + 关停 1，另 `/join/{token}` 落地页） |
| 功能协同运行 | 课题进度由整棵子树的任务聚合；任务挂部门课题有部门一致性校验；审批列表带 AI 风险分档；运维台**读**直连 MySQL、**写**转 club-server（唯一写入者） |
| 异常处理 | `errors.cj` 全量错误码 → HTTP 状态 + 中文文案，**未列出的码一律 500 且不暴露内部细节**（`errors.cj:30`） |
| 安全保障 | PBKDF2-HMAC-SHA256 口令、令牌过期与回收、登录失败锁定与**递增退避**、登录时序侧信道消除（N-16）、权限判定单一入口、CSP、落地页 HTML 转义、私钥不入库 |
| 运行维护 | 运维台 `/club` 页：概览 / 名录 / 任务 / 课题 / 招募链接 / **审计日志** / **一键备份**（从 MySQL 导出 JSON 快照）；`retire-ops` 优雅退役；`/admin/shutdown` 仅回环可调 |

**扣分项：**

1. **客户端交付物不可安装**：`build-profile.json5:3` 为 `"signingConfigs": []`，产物是 `entry-default-unsigned.hap` → **评委拿到手装不进任何设备**（详见 §四-P0-2）。
2. **公网未部署**：`HANDOFF.md:441`、`deploy-windows-verify.md:92` 均记"待服务器信息"。**没有在线体验地址**，评委没法一键验证。
3. 客户端分页缺陷（真实可见故障）：任务列表写死 `{page:1,size:50}` 而界面硬编码"第 1 / 1 页"（`TaskListPage.ets:56`），超过 50 条的任务不可达；会长移交只取前 50 人（`ManagePage.ets:1181`）。
4. 日历对账会**清空事件标题与描述**：`CalendarSync.ets:335` 以 `''` 覆盖，而 `POST /tasks/lookup` 其实返回了 `title`（服务端 `h_task.cj:804-808`）—— 数据在手边却丢了。
5. 死代码：`SplashPage.ets` / `PendingWaitPage.ets` 未登记路由、无引用（`main_pages.json` 无此二项）。

### B. 架构设计与工程质量（25 分 → 估 17–19）

赛道要求：*"复杂智能软件系统中的架构设计能力、工程实现能力和全生命周期开发规范。"*

**已具备：**

| 维度 | 证据 |
|---|---|
| 分层清晰 | `server/src` 35 文件按职责分层：handler（`h_*`）/ 领域（`store*`、`perms`、`auth`）/ 基础设施（`mysql_store`、`limits`、`timex`、`ids`、`audit`）/ 视图（`views`、`jsonw`）/ AI（`ai_*`、`h_ai`）/ 运维台（`src/ops`）；README 有逐文件职责表 |
| 权限收敛 | **全项目唯一权限判定点 `can(member, action, target)`**（`perms.cj`，403 行），明文纪律"禁止在每个 handler 里手写 if" |
| 数据一致性 | 落盘**单事务**整体替换，全参数化 SQL（`mysql_store.cj:1088-1271`）；快照在锁内、写盘在锁外；MySQL 会话强制 `SET NAMES utf8mb4`（修掉"一个 emoji 让后续写入持续 500"的 P0） |
| 依赖治理 | 轻舟框架**内置快照 + `MANIFEST.sha256` 每次构建校验**（`build.ps1`），`PROVENANCE.md` 记上游 commit 与供应链核对；MariaDB 驱动带 `LICENSE` + `UPSTREAM_COMMIT` |
| 全生命周期规范 | Conventional Commits、**218 次提交 / 10 位贡献者 / 多特性分支**（满足"须包含版本控制历史"）；`docs/code-review.md` **六轮评审**（一 24 条 + 二 9 + 三 4 + 四 6 + 五 4 + 六 3）逐条闭环 |
| 上游反哺 | 给轻舟提的改进清单被上游 v0.12.0 CHANGELOG **直接引用条目号**（A-1…A-5、A-7、B-1、B-2 共 8 条）—— 强证据表明是真懂框架而非浅用 |

**扣分项（重要）：**

1. **没有"系统设计文档"** —— 这是赛道明文要求的独立材料项，也是 25 分项的评分依据。仓库有 27 份文档、10,849 行，`api-design.md` 更是 109 KB 的接口权威，但**全仓检索"总体架构 / 数据流转 / 模块划分 / 架构图"，除竞赛原文引用外零命中**。总体架构、模块划分、数据流转、关键技术实现**没有一份文档系统讲清**（只在 README 的目录结构表和 HANDOFF 里零散提及）。**这是当前投入产出比最高的一个缺口。**
2. **架构决策无 ADR**：MySQL 迁移、ArkTS vs 仓颉客户端、RBAC 适配层等重大取舍散落在评估/交接文档里，没有可追溯的决策记录（`club-server-mysql-assessment.md` 已很接近，但只覆盖一个决策）。
3. **零张架构图** —— 全仓检索图片/图表资产（`*.png/jpg/svg/drawio/puml/mmd`），除 `assets/` 与客户端 `resources/base/media` 的界面素材外**没有任何架构图、时序图、ER 图**。答辩时"画不出来"比"写不出来"更伤。
4. **无 CI/CD**：无 `.github/workflows`，7 套测试全靠人工"每次改动都要跑"。竞赛明确考察"全生命周期开发规范"，CI 缺失是显性扣分点，且补齐成本很低。
4. **无数据库 schema 版本管理**：建表用 `CREATE TABLE IF NOT EXISTS`，**不会补列**。本次实测：对 9 月的旧 `club_test` 库跑单测 → `SqlException: Unknown column 'payload'`（`mysql_store.cj` → `tests.cj:2796`）；换**全新库**即 **629/0 全绿**。说明"从零部署"没问题，但**无法演进已有库**。
5. 锁纪律遗留：`storeSave` 持 `s.lock` 的同时取 `save_lock`，且该锁现在**跨一次网络事务**持有（README 自记 S-14，未改）。
6. 文档与代码矛盾（会被评委抓）：`llm-backend-guide.md:13` 称"服务端 `server/src` 下尚无任何 AI 代码"，而该目录实有 **8 个 `ai_*.cj` + `h_ai.cj`**（3,000+ 行）；`llm-ops-guide.md:157` 承诺的审计行 `ai_tool_propose` 全仓不存在（实际是 `ai_tool` / `ai_tool_confirm`）。

### C. 智能技术应用深度（20 分 → 估 11–14）

赛道原文警句：*"仅调用通用模型实现简单问答、仅在现有软件中增加独立 AI 聊天功能……不属于大赛重点鼓励的方向。"*

**服务端做得相当扎实（这是被低估的强项）：**

- **6 条 AI 路由**（`main.cj:754-772`）：`task-suggest` / `notice-draft` / `retrospective` / `ask` / `agent` / `agent/confirm`，另有邀请风控挂在 `GET /members/pending`。
- **真智能体工具循环**：≤ 4 轮、整请求共享 20 s 预算；锁外调模型 → 锁内跑 1 个工具 → 锁外回灌（`h_ai.cj:1274`、`1359-1378`）；静态工具白名单 5 只读 + 1 写（`ai_tools.cj:54-75`）。
- **写操作"实质性落库"**：模型只产**提议**不执行 → 服务端**自算 diff** → 令牌绑 actor + 5 min + 一次性 → 用户确认 → 执行时**重跑 `can()` 抗 TOCTOU** → 复用与 HTTP handler 同一份 `taskStatusApply` 落库（`h_ai.cj:1329-1352`、`1451-1502`；`ai_tools.cj:378-393`、`421`、`428`）。**这正是官方要的"实质性功能设计"，而不是聊天。**
- **模型输出强校验**：`extractJson` → `aiNormalize` 剔 null → `JsonSchema`；负责人必须在服务端候选集内；时间形状不合规即丢键；风险只接受 `low/medium/high` 且无 reasons 不采信。
- **降级契约**：读接口失败一律 `200 + data.source ∈ {model, fallback}`，**永不 5xx**；写操作反过来必须显式报错。
- **工程化闸门**：成员级滑动窗口 20/60 s + 单调时钟 + 零出站退额；并发降级；请求体 64 K 自拒；响应 256 K 上限 + **修掉框架"短读当 EOF"截断** + 关自动重定向（fail-closed）；密钥只走文件路径；审计只记元信息。

**扣分项（致命）：**

1. **客户端 AI 在运行版 App 里根本进不去。** 唯一调用 AI 的页面是 `AskPage.ets:75`，而 `AskPage` **全仓没有任何入口** —— 无 `pushTo('pages/AskPage')`，`main_pages.json:14` 只登记了路由，`ProfilePage` 的 `entryRow` 只有"待分配审批""管理"两条（`:274`、`:284`）。**评委点开 App 找不到 AI。**
2. **只接了 1/4 个接口。** `AiApi.ets:95-121` 封装 4 个接口（且**不含 `agent` / `agent/confirm`**），其中 `taskSuggest` / `noticeDraft` / `retrospective` **零调用点**。
3. **唯一在界面上可见的智能是"待审批风险角标"**（`PendingApprovalPage.ets:134`、`273-274`、`304-309`），确实端到端可用——但**服务端那套最亮的"提议→确认→落库"写链路，界面上完全不可见**。
4. **无 LLM 之外的智能**：全仓 `embeddings` / `TF-IDF` / 余弦 / 分类器 / 视觉 **零命中**；风险分档是纯阈值，缺省负责人是"在途最少 + id 小优先"（无按期率）。
5. 文档承诺未兑现：`api-design.md:1970` 承诺兜底含"历史按期率最高"，未实现（`ai_schema.cj:67-69` 自认候选行无该信号）；`llm-client-spec.md:23` 自认 §14 验收清单与 U7/U12 未做（核实为真）。
6. **真实模型联调无法复核**：`ai-real.ps1` 存在但需自备密钥；仓库内**无留痕证据**（无请求/响应日志、无截图）。给评委看的就是"请相信我们调通过"。

> **判断**：若只看代码，这一项配得上 15–16 分；若按"实机演示 8–10 分钟 + 随机功能测试"的决赛方式，**评委在 App 里摸不到 AI 写链路**，大概率落在 11–12 分。**把已有的写链路搬上界面，是性价比最高的一处提分（服务端零改动）。**

### D. 创新性与应用价值（15 分 → 估 8–10）

**加分面：**

- **选题真实**：社团管理是真问题（"社团里有哪些人 / 每件事由谁负责"），有"内部试用 2 周"的落地计划，不是造需求。
- **设计克制且有主张**（这类"反直觉但正确"的决策最能体现设计能力）：
  - 首页是「我的任务」而非组织架构图；
  - **"同一事实只存一份"**：删掉 `Department.lead_id`、课题不设 status、逾期不设状态；
  - **"能从事实推导的就不存"**：逾期由 `due_at` 算，课题进度由整棵子树聚合；
  - **"绝不级联删除"**：删课题子节点上提、任务软删除；
  - **服务端权威**：`updated_at`、逾期、分组、`is_overdue` 全部服务端生成。
- **职责分离的运维身份**：新增 `ops` 档（= 会长减「移交会长」），**不可由 API 分配**，只能 CLI 创建 → 审计里 actor 与会长分得清清楚楚。这是真实生产系统的思路。
- **工程创新**：`ai_transport.cj` 自实现出站传输层以修掉框架"短读当 EOF"截断；`spike/` 下三个最小复现（`llm-http` / `llm-truncation` / `semaphore`）带 `FINDINGS.md` 与 `evidence/run.log` —— **先做技术验证再落功能**，方法论成熟。

**扣分面：**

1. **选题同质化**：校园管理信息系统在开放命题赛道里是红海，评委容易产生审美疲劳；缺少一句让人记住的"技术主张"。
2. **创新点没有被提炼**：上述设计原则散落在 README 末尾的表格里，**没有一份"项目说明文档"把创新点与应用价值讲成故事**。评委没时间自己挖。
3. **应用价值缺量化**：无用户数、无试用数据、无效率对比（哪怕"录入 100 人从 X 分钟降到 Y 分钟"）。

#### 补充 ①：`--ai-ca` 的平台结论 —— 已用实测回答（评估反馈里提出的问题）

反馈问「**Linux 上是否也需要 `--ai-ca`，从没验证过**」。这个质疑是对的，但答案和我一度以为的相反：

**我曾凭推理把文档改成「与 OS 无关、两个平台都要自备 CA」** —— 理由是原文说的
「OpenSSL 不读系统证书库」听起来与平台无关。**这是未实测的过度推理，随后被实测推翻。**

| 平台 | `CertificateVerifyMode.Default` | 要 `--ai-ca` 吗 |
|---|---|---|
| **Windows** | ❌ 必然 `unknown CA(134)`（`spike R5` 实测） | **必须给** |
| **Linux** | ✅ **会读系统信任库** —— `api.deepseek.com` / `baidu` / `github` / `bing` **四个公网站点全部握手通过** | **不需要**（但本服务仍要求给，见下） |

⚠ **但 `aiValidate` 一律要求 `--ai-ca`**（为了在 Windows 上早失败、说清原因）
⇒ **Linux 上也要给，内容直接用系统那份即可**：`--ai-ca /etc/ssl/certs/ca-certificates.crt`。
这条已直接写进 `disabledReason`，Linux 用户照做就行。

**结论：原文的平台归属（Windows）本来就是对的**，只有它给的理由不够精确。
完整记录与教训见 `API-NOTES.md` **坑 46**（平台差异必须实测，不能从「理由听上去通用」推出来）。

## 七、答辩预案（决赛 5 分钟陈述 + 8–10 分钟实机 + 8–10 分钟问答）

评审专家会做的事：**代码定位、架构说明、异常场景测试、非预设输入测试**。建议预演：

1. **非预设输入**：任务标题传 10 万字符（`limits.cj` 会拒）、emoji 姓名（utf8mb4 已修，有回归断言）、`due_at` 传数值而非字符串（**这是已知未修缺陷 S-4：类型不对会被静默忽略**，被问到要坦承并说明修法）。
2. **异常场景**：断 MySQL 起服务（**故意起不来**，避免空库覆盖真实数据——这是有意的设计决策，讲出来是加分项）；关掉 AI 端点看降级（读接口 `200 + source=fallback`，写操作显式报错）。
3. **架构说明**：重点讲 `can()` 单一权限判定点、落盘单事务、快照锁内/写盘锁外、运维身份与会长的职责分离。
4. **必答题**：为什么客户端用 ArkTS 而不是仓颉 UI？（诚实回答：技术栈决策 + 仓颉侧承担全部服务端，仍是"核心模块用仓颉"）
5. **风险题**：多实例共写同一库不支持（路线 B 已知代价，README 已如实记录）—— 如实说明比掩饰好。

> 章程第 8 节明确：专家有权通过**成员问答**核验真实性与团队贡献。
> 请确保**每位队员都能讲清自己负责模块的核心代码**，不要出现"只有一个人能答辩"的结构。
