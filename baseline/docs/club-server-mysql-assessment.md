## 二、现状量化（实测数字）

| 项 | 数值 |
| --- | --- |
| `server/src/*.cj` 总行数 | **10,083 行**（23 个文件） |
| 其中数据层 `store.cj` | **1,422 行** |
| 业务 handler（`h_*.cj`，8 个文件） | **3,285 行** |
| 单测 `tests.cj` | **1,985 行**（507 条断言） |
| **表** | **7 张**：`departments` / `members` / `plans` / `tasks` / `invite_links` / `tokens` / `idem` |
| **对内存 Store 的耦合** | `s.lock.lock()` **51 处** · `s.<表>` 直接访问 **218 处** · `storeSave/storeSnapshot/flushPending` **77 处** |
| `store.cj` 内的辅助函数 | **64 个**（其中一半是 to/fromJson 序列化，另一半是派生查询） |
| 现有测试面 | 单测 507 · 冒烟 434 · TLS 22 · 契约 33（**全部对着内存 Store 的文件语义写的**） |

现有数据层的**关键语义**（迁移必须逐条保住，否则会出现"看起来一样、其实不一样"）：

1. **整库原子落盘**：先写 `db.json.tmp` → 备份 `db.json.bak` → rename 覆盖；因此**跨表一致**
   （不会出现"任务存了、索引没存"）。
2. **`200 ⇒ 已落盘`**：响应是在落盘之后才发出的（`snapshotFlush` 挂在请求链末端、`ctx.commit()` 之前）。
3. **提交序号守卫**（`seq`/`saved_seq`）：并发写盘收敛到最新快照，旧快照不会覆盖新快照。
4. **快照在锁内、写盘在锁外**：`storeSave` 只在锁内取快照，磁盘 IO 挪到锁外串行。
5. **派生量全部由服务端算**：`is_overdue` / `overdue_days` / 课题树递归聚合与深度 /
   任务时间桶分组（今天/本周/逾期/阻塞…）/ 部门范围 / 权限 —— 都建立在**内存结构**上。
6. `storeSaveNow` 只给单线程入口（`init-admin` / 单测）用。

## 三、迁移要动的面

> ⚠ **本节是 2026-09-19 的评估口径，已被 2026-09-20 的落地超越** —— 实际走的是路线 B
> （内存 `Store` 一行未动，只换持久化层），所以"1,422 行重写 / 218 处改写 / 507 条测试要么重写要么作废"
> 都**没有发生**（见顶部结论更新）。

不是"换一个存储实现"，而是**替换整个数据访问范式**：

| 要动的地方 | 量级 |
| --- | --- |
| `store.cj` 的 7 张表读写 | 全部改成 SQL（**1,422 行重写**） |
| **218 处** `s.<表>` 直接访问 | 全部改（`s.members.get(id)` → `SELECT ... WHERE id=?` 之类的语义等价改写） |
| **51 处** `s.lock.lock()` | 从"全局互斥锁"改成"每请求连接/事务"模型 —— handler 骨架要重排 |
| **77 处** `storeSave/storeSnapshot/flushPending` | 整套"快照 + 序号守卫 + 链尾刷盘"中间件作废，改由 DB 承担持久化 |
| **64 个**派生辅助函数 | 要么下沉成 SQL（重写、易漂移），要么改成"按需加载"（那就要重做分页/懒加载） |
| `tests.cj` **1,985 行 / 507 条** | 绝大多数直接构造 `Store` 断言内存行为 → **要么重写、要么作废** |
| 冒烟 434 / 契约 33 条 | 语义不该变，但跑之前要先有 MySQL |

## 四、能力缺口：框架的 `DbBackend` 太薄

框架 v0.7 的抽象层只有这些（`third_party/qingzhou/src/db.cj`）：

```cangjie
public func query(sql: String): DbResultSet        // 结果集
public func exec(sql: String): Int64               // 影响行数
public func ensureTable(name, columns): Unit       // CREATE TABLE IF NOT EXISTS
public func close(): Unit
// DbResultSet 只有 rowCount() / cell(i,j) / row(i)，且**所有列值统一字符串化**
```

它自己文档里也写明「SQL 只写**最小公共子集**（`SELECT *` / `WHERE` 等值 / `INSERT VALUES` /
`DELETE WHERE` / `ORDER BY`）」。而我们需要的：

| 我们需要 | `DbBackend` 现在 |
| --- | --- |
| 事务（改成员+改任务+写审计要一起成功） | ❌ 没有事务接口 |
| 参数化查询（防注入） | ❌ **只有字符串拼 SQL**（见 §五） |
| 类型化取值（Int64 / bool / 时间） | ❌ 全字符串化，要自己 parse |
| JOIN / 聚合 / 递归（课题树、部门统计） | ❌ 文档明确只保证最小子集 |
| 迁移/建库脚本、索引、外键 | ❌ 只有 `ensureTable(name, columns)` 字符串 |

**结论**：`DbBackend` 可以作**连接与最小执行**的地基，但真要做 club-server 的数据层，
上面还得自己补一层 DAO（事务 + 参数化 + 类型映射 + 查询构造）。**这不是"换个 backend"的事。**

## 五、⚠ 安全：框架的 MySQL 路径是**字符串拼 SQL**

框架自己的代码就是这么写的（`third_party/qingzhou/src/store.cj:116`）：

```cangjie
let rs = db.query("SELECT * FROM users WHERE username = '${username}'")
```

`MySqlBackend.query/exec` 也是把整条 SQL 字符串交给 `conn.prepareStatement(sql)` ——
**没有占位符参数**。

而 club-server 的入参里**大量是用户可控字符串**：成员姓名、任务标题/描述/阻塞原因、
**名录搜索关键词 `q=`**、部门名、课题名、注册口令、招募 token……

→ 如果照这个模式把 `s.members` 之类的内存查询直接改写成拼 SQL，
**会立刻引入 SQL 注入**（`q=' OR '1'='1` 之类）。

**所以迁移的一项硬前提是：先补参数化查询能力**（`std.database.sql` 本身支持
`prepareStatement` + 参数绑定，框架只是没暴露；需要给 `DbBackend` 加
`query(sql, params)` / `exec(sql, params)`，或者我们在 club-server 侧自己包一层）。
**这条不做，就别迁。**

## 六、收益 vs 代价

**潜在收益**（都只在特定条件下才兑现）：

| 收益 | 何时才有意义 |
| --- | --- |
| 多实例同时写同一份数据 | 需要水平扩展时（现在单实例足够） |
| 摆脱"整库重写"的线性 IO（现状约 3× 文件大小的 IO/次写） | 库涨到十几 MB 以上（现在 **0.5 MB**） |
| 库不再必须放得下内存 | 数据量远超千人社团 |
| 借助 DB 做备份/复制/查询 | 运维侧需求 |

**确定的代价**：

1. **部署退化**：club-server 现在**零数据库依赖**（拷 exe + 4 DLL + 一个目录就能跑，部署包里
   连 Node 都不需要）。迁完必须有一台可达的 MySQL —— 对一个"社团内部试用 2 周"的工具是明显的
   负担（本次给队友连后台的 MySQL 就踩了 DHCP、防火墙、账号三道）。
2. **测试面几乎全废**：507 条单测大量直接构造 `Store`（`tests.cj` 1,985 行）。
   按本项目"每条修复都要有会因回退而变红的断言"的纪律，这笔账很大。
3. **派生逻辑重写风险**：`is_overdue` / 课题树递归 / 时间桶分组 / 部门范围判定
   —— 任何一处语义漂移都会变成"客户端看到的数字不对"，而这类 bug 很难测。
4. **并发模型重排**：现在 51 处 `s.lock` 是"一把大锁最省心"；换 DB 后要决定事务边界、
   连接池、死锁重试策略 —— 引入的是新一类问题。
5. **工期**：对一支以学生为主、AI 辅助、目标是"两周试用"的队伍，这是**周级**而不是天级的改动，
   而且要重跑并重写大量测试。

## 七、三条可选路线

| 路线 | 做法 | 代价 | 何时选 |
| --- | --- | --- | --- |
| **A. 全量 DAO 重写** | 7 张表全 SQL 化，handler 全面改写，加事务/参数化/DAO 层 | 最大（周级，测试几乎重写） | 真要长期演进成"正经后端"时 |
| **B. 写穿缓存（最小中间态）** | 保留内存 Store 与全部派生逻辑不动；**只把"落盘"从"重写 db.json"换成"写 MySQL"**（启动时从 DB 全量载入内存） | 中等（只动持久化层 + 建表/迁移脚本）；**但拿不到水平扩展**（多实例内存会不一致，除非再加失效通知） | 想先验证"MySQL 能不能稳定顶上"时；也是**推荐的第一步** |
| **C. 只迁高churn表** | 把 `tokens` / `idem` 这类低关联、高churn的表挪进 DB，核心业务仍在内存 | 小 | 想缓解"令牌表越滚越大、每次整库重写都要背上它"时（其实**动作 3 的令牌回收已经缓解了**） |

## 八、与"队友共用数据"的关系（重要）

用户此前的目标是"**队友不必各自装数据库**"。要澄清：

- 客户端（App）**只跟 club-server 说话**，从不连数据库；
- 所以**只要一台 club-server 在跑**，所有队友的客户端看到的就是**同一份数据**——
  这已经天然满足"共用"，**不需要 MySQL**；
- MySQL 只在"**每个队友各跑一个 club-server，但要让它们共享同一份数据**"时才变得必要 ——
  而那正是 §七 路线 B/A 要解决的事。

**换句话说：如果目标只是联调共用数据，现在的架构已经够了；MySQL 是为"多写者/多实例"准备的。**

## 九、建议

> ⚠ **以下是 2026-09-19 的建议原文**。2026-09-20 的落地按 ①②③ 的顺序做了 ①②③（含用
> 六套测试确认没退化），**唯一没做的是第 3 条里的"保留 `db.json` 作回退路径"** ——
> 用户明确要求不采用文件存储。第 4 条（同步部署面）已做。

1. **本轮不迁。** 依据是项目自己定的阈值：`db.json > 20 MB` 或日均写数千次
   （`docs/capacity-baseline.md` §5）。现在 0.5 MB（1000 成员 + 1000 任务）。
2. **若确实要推进**，按顺序：
   - ① 先给 `DbBackend` 补**参数化查询**（`query(sql, params)` / `exec(sql, params)`）——
     这是安全前提，不做就别开始（§五）；
   - ② 再走**路线 B**：只替换持久化层（`storeSave` / `storeLoad` → MySQL 的建表 + 全量载入 + 增删改），
     内存模型与全部派生逻辑**一行不动**，测试面因此基本可控；
   - ③ 用 `bench.ps1` + 现有六套测试确认没退化，再做路线 A 的增量替换（一次一张表）。
3. **迁移脚本与双写**：真要动数据时，写一个 `db.json → MySQL` 的一次性导入（含校验：
   行数、关键字段、派生量抽查），并保留 `db.json` 作为回退路径至少一个版本。
4. **别忘部署面**：迁完 club-server 就有了 MySQL 硬依赖，部署文档
   （`docs/local-deploy.md` / `deploy-windows-verify.md`）要同步改，否则"拷 exe 就能跑"
   这条最省事的路径会失效。
