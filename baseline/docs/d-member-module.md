### 2.2 分工文档「必须记住的坑」四条

| # | 坑 | 状态 | 客户端做法 |
| --- | --- | --- | --- |
| 1 | **编辑姓名权限受限** → 403 `FORBIDDEN_ROLE` | ✅ | 没权限**直接不渲染按钮**，不靠报错兜底；`can()` 统一判定（含同权保护与"部长限本部门"） |
| 2 | **最后一个会长不能移出** → 409 `FORBIDDEN_LAST_PRESIDENT` | ✅ | 进详情页时用 `GET /members?role=president&status=active` 拉会长列表 → `isLastPresident()`；是唯一会长则**不渲染移出按钮**，并显示原因 |
| 3 | **名下有未完成任务** → 409 `MEMBER_HAS_OPEN_TASKS` | ✅ | ①身份卡与任务卡直接展示 `open_tasks`；②移出确认弹窗预列**最多 3 条**未完成任务；③真被拒时把错误码翻译成可执行提示 |
| 4 | **状态语义** active / pending / disabled，名录默认只显示 active | ✅ | 显式传 `status=active`（不依赖服务端默认值）；非 active 用状态胶囊标出；`disabled` 成员不再提供任何写操作 |

## 3. 未实现 / 有意偏离的需求

> 以下都是**知道但没做**，逐条给原因，避免被误读成漏做。

### 3.1 P06 的「待分配」分组 —— 只做了计数，没做分组列表

| 项 | 说明 |
| --- | --- |
| 设计稿 | P06：`待分配单独成组并标出来源`，示例 `今天注册 · 来自招募链接（运营部预填）`；页眉 `42 位成员 · 4 个组织 · 待分配 3 人` |
| 已做 | 页眉的 `另有待分配 N 人（待管理员分配后进入名录）` —— 用 `GET /members?status=pending&size=1` 只取 `total`，**不传输名单** |
| 未做 | 待分配的**成员列表**与**来源标签** |
| 原因 | ① 来源需要 `dept_hint`，而它只在 `GET /members/pending` 里，该接口要求 `AssignPending` 权限（仅会长/副会长），名录却全社团可见 → 评审 **D-9（待决策：涉及最小化暴露面）**；② 组内还要显示 `registered_at`，`MemberBrief` 里没有；③ 分工文档明确「名录默认只显示 active，**别把 pending 混进来**」 |
| 建议 | 若保留设计稿做法，需服务端先决策 D-9；届时名录页加一段 `can(user,'ManageMembers')` 门控的 pending 分组即可（接口 `MemberApi.pending()` 已由 A 封装好） |

### 3.2 近千人规模的分页（评审 D-10）

| 项 | 说明 |
| --- | --- |
| 现状 | 服务端 `page/size` 默认 50、**上限 200**（`paging.cj:19,44`）；客户端用 `size=200` **循环拉全**，上限 `MAX_PAGES=20`（即 4000 人），到顶或不足一页就停 |
| 影响 | 百人级社团一次约 1–3 个请求，可接受；千人级会有 5+ 个请求且全部驻留内存（`ForEach` 一次性构建，未用 `LazyForEach`） |
| 建议 | 服务端提供"分组 + 组内分页"接口，或客户端改 `LazyForEach` + 按组懒加载。**不建议**改用本地过滤 —— 分页上限决定了本地拿不全 |

### 3.3 临时密码语义（评审 D-12）—— 界面文案按服务端实况修正

| 项 | 说明 |
| --- | --- |
| 原静态壳文案 | `请立即告知成员，首次登录后会强制改密。` |
| 问题 | 服务端**没有**"首登强制改密"标志（`h_secret.cj:89`，评审 D-12）：口令只在响应里回一次，但之后长期有效。原文案是**错的**，会让管理员误以为系统已兜底 |
| 现文案 | `该口令只在本次响应里出现，之后看不到；原密码已失效。请立即告知本人，并提醒尽快在「我的」页自行修改密码。` |
| 归属 | 文案修正（客户端）；若要"真一次性"，需服务端加标志，v1 不做 |

### 3.4 唯一会长判定的一个边界（有意选择 fail-safe）

| 项 | 说明 |
| --- | --- |
| 服务端口径 | `presidentCount` 统计 `role=='president' && status!='disabled'`（含待分配态） |
| 客户端口径 | 查询 `?role=president&status=active`，只统计 **active** 会长 |
| 差异 | 仅当存在"会长 + pending"这种数据时才会分歧（正常流程下不可能出现）。此时客户端会**更保守** —— 少显示一个移出按钮，而不会多显示一个会被 409 拒绝的按钮。破坏性操作上这是正确方向，故不修 |
| 备注 | 客户端**不做**"自己算一遍角色档位"的事，权限判定只有 `PermissionStore.can()` 一个入口 |

### 3.5 详情页不含"改部门 / 改角色"

| 项 | 说明 |
| --- | --- |
| 分工文档 | D 只负责「编辑姓名（权限受限）」 |
| 现状 | `PATCH /members/{id}` 的 `dept_id` / `role` 走的是另一套权限（仅会长/副会长），且角色枚举里**没有「会长」**（只能由会长移交产生）—— 属于 B 的管理页 |
| 结论 | 详情页只发 `name` 字段。`MemberApi.update()` 已支持另外两个字段，B 或后续扩展可直接复用 |

### 4.3 权限矩阵（按钮显隐，全部由 `PermissionStore.can()` 推导）

| 当前用户角色 | 编辑姓名 | 重置密码 | 移出社团 |
| --- | --- | --- | --- |
| 会长 | ✅ 任何人（含自己） | ✅ 除自己外任何人 | ✅ 除自己、且对方不是唯一会长 |
| 副会长 | ✅ 部长/副部长/成员 | ✅ 同上 | ✅ 同上 |
| 部长 / 副部长 | ✅ 本部门的更低档位（含自己） | ✅ 本部门更低档位 | ✅ 本部门更低档位 |
| 普通成员 | ❌ | ❌ | ❌ |

> 「自己」这一列看起来严于直觉，但**是服务端口径**（P07 原文：`不能对同权限或更高权限的人执行上述操作，会长也不能重置自己`；`perms.cj` 的 `checkAccess` 在动作语义层统一拦 `ResetPassword / SetRole / DisableMember / EditMemberName`）。
> 因为"唯一会长"的判定里会长是最高档，自己对自己的移出永远落在「最后会长保护」上 —— 想移出会长，只能先在管理页做**会长移交**，这与产品规则一致。

### 4.4 常见返回码在界面上的表现

| 返回 | 界面表现 |
| --- | --- |
| `401`（token 失效） | 全局：清登录态 → Toast「登录已过期，请重新登录」→ 回登录页（`HttpClient` 统一处理） |
| `403 FORBIDDEN_ROLE` | 全局 Toast「不能对同权限或更高权限的人执行此操作」；正常路径下按钮已隐藏，只有并发/直接调用才会看到 |
| `403 FORBIDDEN_NOT_IN_DEPT` | Toast「只能操作本部门范围内的人与事」 |
| `409 FORBIDDEN_LAST_PRESIDENT` | Toast「社团必须始终保留至少有一位会长」；正常路径下按钮已隐藏 |
| `409 MEMBER_HAS_OPEN_TASKS` | 弹窗内红字提示「名下还有 N 项未完成任务，移出社团前需先转交。」 |
