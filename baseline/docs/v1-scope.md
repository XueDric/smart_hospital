## 1. 要解决的两个问题

1. 社团里有哪些人
2. 每件事由谁负责、做到什么程度

**关键判断：这两个不是并列的功能，而是同一问题的静态面与动态面。**

名录是任务的目录，真正让人每天打开的是「我负责什么」。因此：

- 首页 = **我的任务**，不是组织架构图
- 若后续必须削减，先砍名录的花哨功能，**绝不砍个人任务视图**

> 内部工具最经典的失败模式：管理员建完部门和角色，日常协作仍回到微信群，工具在两周后变成一个没人更新的花名册。

## 2. 试用成功标准（v1 验收）

试用期定为 2 周，结束时逐条对照：

| # | 验收标准 | 判定方式 |
| --- | --- | --- |
| 1 | 新成员从**注册到被分配部门** < 2 分钟，且会长**一次操作可覆盖一批人** | 实测新成员 3 人 + 一次批量分配 |
| 2 | 任务从创建到负责人看到 < 1 分钟 | 实测 |
| 3 | **课题下的任务能被一眼看清进度**（见第 6 节规则 7） | 抽查 3 个课题 |
| 4 | 部门群里「这事谁负责」明显变少 | **真 KPI** |

**第 4 条不达标即视为失败，功能再全也不算通过。**

> **v0.4 修订说明**：原标准为「新成员从拿到邀请码到看到自己部门 < 2 分钟，**且管理员无需手动录入**」。
> 改用「先注册、后授权」模型后，每个新成员都必须经会长分配，**“无需手动录入”不再成立**。
> 因此标准改为：可批量达成，且**一次操作能覆盖一批人**——否则招新期会长会成为瓶颈，
> 而招新期恰恰是本工具最该发挥作用的时刻。

## 3. v1 范围

### 3.1 做（原定 7 项 + 1）

创建部门 · **注册与授权** · 设置角色 · 创建任务 · 分配负责人 · 更新状态 · 提醒截止时间
· **创建课题并挂载任务**（v0.3 新增，见 3.4.4 ③）

> v0.4 把原「邀请成员」改为「**注册与授权**」：注册（凭社团共享口令，得 `pending` 账号）与授权（会长分配部门+角色）是两件独立的事，后者是 v1 必须做的核心。

### 3.2 明确不做

写下来是为了防止开发中途扩大范围：

- 会议、知识库（第二 / 第三阶段）
- 群聊、私信、文件传输
- **成果提交与附件上传**（甲方答复④：完成即可，不需要提交物）
- **审核流程 / 「待审核」状态**（甲方答复⑤：暂时掠过）
- 统计报表、数据看板
- 多级部门树（v1 只做单层）
- **任务分层**：任务永远是最小执行单元，**没有子任务**。可分层的是课题（见 3.3 决策表），别把两者搞混
- 自定义角色与权限矩阵（v1 只做甲方定义的 **5 个固定预设**）
- 任务进度百分比

> 注：原「项目容器放第二阶段」一条已删除——甲方答复③确认的这个"大计划"**就是**项目容器，已提前进入 v1。**同一个东西不留两个名字。**

### 3.3 已确认决策

| 决策项 | 结论 | 说明 |
| --- | --- | --- |
| 客户端 | **鸿蒙 App 优先** | 沿用当前 `cangjie_web` 工程方向 |
| 角色 | **固定 5 档预设，只做分配** | 依甲方配置表，不做角色权限编辑器，见 3.4 |
| 账号模型 | **手机号登录 + 注册与授权解耦** | 注册后为 `pending`、无任何权限；部门与角色全部由会长授予。**换届、毕业、返校都只改角色，账号不动** |
| 分层 | **课题可层层往下分割（多级）→ 任务是叶子** | 一个课题下可挂**子课题**，任意层；任务的父节点可以是任意层级的课题。**任务本身不再分层** |
| 提醒 | **应用内高亮 + 加入系统日历** | 绕开后台推送通道，见第 7 节 |
| 服务端 | **自建，部署在老师提供的云服务器** | **Windows**（与开发机同平台） |
| 后端技术栈 | **仓颉 1.2.0 + 轻舟框架**（内置快照 = 上游 v0.12.0 之后的 HEAD `3d6c1a36`） | 学习目的之一，接受生态不确定性 |
| 部署方式 | **本机编译，拷贝制品到服务器** | 同平台 ⇒ 服务器**无需安装编译器**；制品为 exe + 4 个 DLL，见 `deploy-windows-verify.md` |
| 持久化 | **MySQL**（2026-09-20 起；此前是"文件存储 JSON 落盘"） | 原判断"仓颉生态无可用关系型数据库驱动"当时成立；2026-09-20 已用内置 MariaDB 驱动实做（`server/src/mysql_store.cj`），见第 8 节 |

#### 3.4.4 运维身份（`ops`，2026-09-16 新增）

**需求**：运维（部署、发口令、处理"登不上"、清数据、备份）不该由会长本人执行 ——
职责要分开，而且事后要能看出"这是运维做的，不是会长做的"。运维人员日常只登录后台
（**2026-09-17 起可直接用 club-server 的运维账号登录**：手机号 + 运维口令，无需改配置；
也可以用轻舟那套 RBAC 的后台账号，其口令由 `admin.exe` 首次启动随机生成并写入
`build\admin\admin.env`，不再是写死的 `admin123`，见 `code-review.md` N-29），
后端再以**专用运维账号**的身份去调 club-server。

| 项 | 值 |
| --- | --- |
| 角色代号 | `ops`（中文名"运维"） |
| 档位 | **与会长同档**（`roleRank = 5`） |
| 权限 | **除「移交会长」外与会长同权**：全社团读写、部门增删改、换注册口令、可处置任何成员（含会长） |
| 唯一的减法 | **移交会长**（治理动作，只能由会长本人发起） |
| 怎么创建 | 只能用本机命令 `club-server init-ops <手机号> <口令> [DSN]`（第 3 个位置参数 **2026-09-20 起是 DSN**，不再是数据目录）；退役用 `club-server retire-ops <手机号> [DSN]` |
| 为什么不能由 API 分配 | 它比副会长权限大；若 `POST /members/{id}/assign` 能分配它，会长就能造出**权限略高于自己**的账号，绕过"会长只能通过移交产生"这条约束。本机命令 = 需要这台机器的访问权，与 `/admin/shutdown` 的本机信任同一档 |
| 同档保护 | 与会长互不可处置：会长也不能停用/改名/降级运维账号（与"同权者不可互处置"一致） |
| 审计 | 它的每个敏感操作都记在 `<数据目录>/audit.log` 里，`actor=` 是运维账号 |

> ⚠ **它在客户端不可见（2026-09-16 定，按"隐藏系统账号"）**：`GET /members` 名录与 `?q=` 搜索
> 都**不返回** `role = ops` 的账号 —— 客户端那 5 档标签不需要为它改动，名录里也不会冒出
> 一个"待分配"的运维账号。要看/管它，用运维台（`/club`，**2026-09-20 起直连 MySQL** 读社团库，显示为「运维」）。
> 只隐藏**列表**：按 id 查详情仍可达（会长/运维需要时用得上），而 id 不会从任何成员可见的列表里露出。

>    同部门的部长因此可以重置会长密码并接管账号（P0 缺陷，详见 `code-review.md` H-1）。
>    例外：部长可以改**自己的**姓名（改名不改变角色，不构成提权）。

**v1 系统级别映射**（实现用）：

| 角色 | 系统级别 | 一句话 |
| --- | --- | --- |
| 会长 | 超级管理员 | 全部权限 + 设置角色 |
| 副会长 | 社团管理员 | **除「移交会长」与「改动会长本人」外，与会长同权**（v0.6） |
| 部长 | 部门管理员 | 管本部门成员 + 创建分配本部门任务与课题 |
| 副部长 | 部门管理员 | **与部长同权**（甲方答复①，见 3.4.4） |
| 成员 | 普通成员 | 看本部门，更新自己任务的状态与阻塞原因 |

| ① | 副部长与部长的权限边界 | 未特别区分 | 按建议：**两者同权**，仅名称区分 |

### 3.5 范围变更评估（依文末《范围变更规则》）

#### 3.5.1 v0.3：课题容器进入 v1

③ 属于**新增功能**，按规定须评估。结论：

| 维度 | 评估 |
| --- | --- |
| 是否服务于第 1 节的两个问题 | ✅ 直接服务于"每件事由谁负责、做到什么程度"——课题是任务的组织单元 |
| 是否引入新权限模型或新外部依赖 | ❌ 不引入。权限仅复用现有部门管理员级别 |
| 是否推迟验收标准 | ❌ 不推迟。仅增加一项目标（验收标准第 3 条） |
| **工作量影响** | **+1 张表、+2 个页面、+1 个外键字段，约 +20~25%** |

**裁定：准予进入 v1。** 理由：④⑤ 两项范围缩减（去掉成果提交与审核流程）抵消了相当一部分增量，净增量可控。

#### 3.5.2 v0.5：课题改为多级嵌套

| 维度 | 评估 |
| --- | --- |
| 是否服务于第 1 节的两个问题 | ✅ 服务于"每件事由谁负责、做到什么程度"——大课题确实需要层层拆分才看得清 |
| 是否引入新权限模型或新外部依赖 | ❌ 不引入。子课题沿用父课题的部门与权限 |
| 是否推迟验收标准 | ❌ 不推迟。第 2 节验收标准 3 的抽查范围从"课题目录"扩展到"课题树" |
| **工作量影响** | **+1 个自引用字段**，但真正的增量在：递归进度聚合、树形 UI、环形校验、删除上提 —— 约 **+15%** |

**裁定：准予进入 v1。** 数据模型增量很小（自引用 `parent_id`），复杂度集中在四处逻辑上，且这四处**都是必须做对的**，不能打折：

| # | 必须做对的点 | 不做对的后果 |
| --- | --- | --- |
| 1 | **环形引用校验**（移动课题时） | 进度聚合无限递归，**直接拖垮服务** |
| 2 | **递归进度聚合** | 父课题进度与子树不一致 |
| 3 | **删除上提**（不级联） | 一次误删丢掉整棵子树的工作量记录 |
| 4 | **每个课题必须有负责人** | 中间层无人认领，正是本工具要解决的"谁负责"问题的反面 |

## 6. 关键业务规则

1. **一个任务只能有一个负责人**（必填）。允许多个负责人等于没人负责，这正是本工具要解决的问题本身。
2. **状态只有 4 档，不做进度百分比**。百分比最终一定会永久停在 90%。
3. **阻塞原因**把「进度落后」翻译为「需要帮助」，是整个工具信息量最大的一个字段。
4. **最近更新时间自动记录**。一个任务三周无人动，这个事实本身就应被看见，比任何百分比都有意义。
5. **角色固定 5 档，只能分配、不能自定义**。权限矩阵见 3.4.3。
6. **人数只做软提示，不做硬校验**。换届、代理、临时增补在社团里是常态。
7. **课题不单独设状态，进度由整棵子树递归聚合**（显示为 `已完成 n / 共 m`，`n` / `m` **含所有后代任务**）。
   这样可以从结构上杜绝「任务全完成了、课题还写着进行中」这类不一致——它不需要靠人去维护。
8. **任务可以不属于任何课题**。运营部、宣传部的零散日常任务不必强行挂课题，避免为了用工具而造课题。
9. **删除课题时，其下子课题与任务一律「上提一级」**（挂到被删课题的父节点；被删的是顶层则变为顶层 / 独立），**绝不级联删除**。
   任务承载着人的工作量记录，不能因为删一个容器就消失。
10. **系统必须始终至少有一个 `president`。** 不允许把最后一个会长降级或删除——否则社团会失去全部管理能力，且**无法自助恢复**，只能改服务器数据文件。
11. **会长移交是一个明确操作**，不是"手动改两次角色"。分两步做会出现「零会长」的中间态，正好撞上第 10 条。
    > **v0.11 补充**：因此**会长只能由「移交会长」产生**。`assign` 与 `PATCH /members/{id}` 一律拒绝
    > `role = president`——否则会出现两个会长，第 10 条与第 11 条同时失去意义。
12. **注册与授权分离**：注册只创建账号（`pending`，无任何权限），部门与角色一律由会长授予。**换届、毕业、返校都只改角色，不重建账号。**
13. ⚠️ **课题树禁止环形引用。** 移动课题时，目标父节点**不能是该课题自身或其任何后代**——否则递归进度聚合会无限循环并拖垮服务。这是多级结构下最容易出的事故，**必须做校验**。
14. **任意层级的课题都必须有负责人。** 层层往下分割最大的风险是中间层无人认领，而那正是本工具要解决的「谁负责」问题的反面。
15. **「逾期」不是状态，是派生量。** 任务状态永远只有 4 档，`is_overdue` 由 `due_at` 与当前时间算出。
    与规则 7 同源：**能从事实推导的东西就不要单独存**，否则两边必然不一致。
16. **`updated_at` 必须由服务端生成**，不接受客户端传入。它是「做到什么程度」可信度的基础——一旦允许客户端写，这个字段就失去意义了。
17. **任务采用软删除**（`deleted_at`），保留工作量记录。与规则 9 同一条原则：不能因为删一个容器就让工作痕迹消失。
18. **课题树深度硬上限 6 层**（`PLAN_DEPTH_EXCEEDED`）。环形校验防的是环，防不了"上千层直线嵌套"这类病态数据——上限的意义是**防呆**，不是限制表达。
19. **`Plan.dept_id` 只存在顶层课题**，子课题的部门由所属根课题决定。「继承」若靠复制一份，就又变成同一事实存两份。

## 7. 日历同步设计

选择「加入系统日历」把提醒交付交给手机自带日历，因此 v1 **不需要**后台推送、通知权限与服务端推送，这是本版最大的技术风险规避。

**⚠️ v0.7 修正：这件事发生在客户端，不在服务端。**

初稿把 `calendar_event_id` 存在服务端的 `Task` 上，**这个位置是错的**：

1. 日历事件在**成员自己的手机上**
2. **同一任务可能被多人加入日历**（负责人、部长、关注者），服务端存一个 id 无法表达
3. 换手机后本地事件消失，服务端那个 id 成为**悬空引用**
4. 服务端**不应该也不需要**知道谁把什么事加进了自己的日历——这本身是隐私

**正确划分：**

| 位置 | 存什么 |
| --- | --- |
| **客户端本地** | `task_id → { event_id, cached_due_at, cached_status }` |
| **服务端** | 只提供事实：`due_at`、`status`、`updated_at`。**不存任何日历字段** |

客户端拉取任务时比对本地缓存与服务器值：

| 差异 | 客户端动作 |
| --- | --- |
| `due_at` 变了 | **更新**本地日历事件（不得新建） |
| `status` 变为 `done` | **删除**本地日历事件 |
| 任务已不在服务器返回中 | **删除**本地日历事件 |
| 日历权限被拒绝 | 降级为导出 `.ics` + 应用内高亮 |

服务端为此提供一个很小的辅助接口 `POST /tasks/lookup`（见 `api-design.md` §4.8），
让客户端知道"我加过日历的任务现在还在不在"。**没有它，客户端无法可靠回收日历事件。**

> 不做「更新与删除」这一步，日历里会堆积错误的过期提醒，两周后成员就不再相信它。
> **工作量没有消失，只是换到了客户端**——而且换过去**更好验证**，因为日历同步错了是用户看得见的。
> **需在客户端排期里单独列出这一项。**

## 8. 技术前提（缺一项 v1 跑不起来）

1. **服务端 + 账号体系（必须）**。「谁负责」天生是跨人共享的数据，纯本地 App 无法实现。此条不在功能清单内，但是地基。
2. **后端技术栈**：仓颉 **1.2.0** + 内置轻舟快照（v0.12.0 之后的 HEAD `3d6c1a36`），部署在云服务器（**Windows**，与开发机同平台）。`build.ps1` **按版本硬校验 1.2.0**（`PATH` 上的 1.1.3 不会被选中）。服务端与客户端的编译链版本必须对齐。
3. **部署方式：本机编译 + 拷贝制品**。因为服务器与开发机**同平台**，本机编好的 exe 可直接复用，**服务器上不需要安装编译器**。打包内容为 **exe + 4 个 DLL**（共约 18.8 MB）：`club-server.exe`、`libcangjie-runtime.dll`、`libboundscheck.dll`、`libcrypto-3-x64.dll`、`libssl-3-x64.dll`（由 `server\build-package.ps1` 产出）。详见 `deploy-windows-verify.md`。
4. **持久化：MySQL**（2026-09-20 起实做；内存 Store 仍是运行期模型，落盘改成"库与 9 张表由程序自建、一个事务增量写进去"，见 `server/src/mysql_store.cj`）。原判断"仓颉标准库 / stdx / 轻舟均无关系型数据库驱动，自建 `sqlite3` FFI 绑定不在 v1 范围内"是当时的结论；驱动来源是 `server\third_party\mariadb-driver`，由 `server\build-mysql-driver.ps1` 产出（产物不入库）。**"数据访问抽成 Store 接口"这一条已被这次替换证明是对的** —— 内存模型与业务逻辑一行未动。**代价：club-server 从此需要一台可连的 MySQL。**
5. **OpenSSL 3 必须随制品一起部署**：stdx 的 crypto / tls 硬编码 `dlopen` OpenSSL **3**。**`libcrypto-3-x64.dll` / `libssl-3-x64.dll` 必须与 exe 同目录**，缺失时密码哈希与 session 会**运行时 500 且编译期无警告**（与开发机上的现象一致）。
6. **ABI 配置**：客户端已于 2026-09-14 改为 **ArkTS**，原先 `entry/build-profile.json5` 里的 `cangjieOptions.abiFilters` 已删除（`cangjieOptions` 会被 stock hvigor 直接拒绝，见 `client-build.md`）；ABI 现由 DevEco 的 ArkTS 构建默认处理。
7. **分发渠道（非技术卡点，需尽早并行启动）**：HarmonyOS NEXT 侧载受限，把 App 发到几十位成员手上通常需走 AppGallery Connect 内部测试轨道，涉及签名证书与测试版本审核。**该流程耗时可能超过开发本身，不要等开发完成才启动。**
