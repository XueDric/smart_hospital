## 0. 一句话结论

**以已冻结的 `api-design.md` / `v1-scope.md` 为尺子，服务端是达标的**：40 / 40 接口全部注册，四套测试本次全部实跑复现通过。

**以这份 UI 设计规格 PDF 为尺子，则不然**：存在 **5 处功能性缺口（高）**、**5 处口径冲突（中）**、**5 处次要差异（低）**，另有 **4 处是设计稿自身矛盾**（应改稿而非改代码）。其中 **D-15 是队友独立复验时抓到的，我第一轮审 P01 时漏了**（§0.5 已修）。

PDF 里直接印出了本项目的字段名与接口名（`dept_hint`、`error.fields`、`GET /auth/me`、`view_scope`、`assign-batch`、`owner_id`、`DEPT_NOT_EMPTY`、`FORBIDDEN_ROLE`），说明它是与本项目**同源**的 UI 规格，因此下列差异不是"客户端的事"，而是**服务端契约要不要跟着改**的问题。

## 3. 中优先级

### D-5 逾期天数未下发

- 设计稿：P01 卡片 `逾期 2 天`；P03 提示条 `已逾期 2 天 · 该判断由服务端算出，客户端不重算`，视觉块再次强调 `逾期提示条说明「由服务端算出」`。
- 服务端：`TaskBrief` 只有布尔 `is_overdue`（`server/src/views.cj:301`），**没有天数**。
- 后果：客户端要么自己算（正是设计稿禁止的），要么另开接口。
- 建议：`TaskBrief` 增加 `overdue_days`（按服务端本地日界计算，与 `groupMine` 的 `todayStart` 同源）。
- 归属：**服务端改**。

### D-6 密码长度三方不一致 → **已定稿：8–32 字节 + 只允许数字/英文/符号**

- 设计稿 P12，密码框下方原文（本人在原图上核对过）：`长度按字节计：6-32 位，中文一字 3 字节。`
- 服务端（改动前）：注册 `h_auth.cj` 是 `pw.size >= 8`，改密同一句；**两处都没有上限**。
- 冻结文档：`api-design.md §2.3 注 5` 写「≥ 8 位」。
- **2026-09-16 定稿**（开发者决定）：

  | 维度 | 规则 | 与设计稿的关系 |
  | --- | --- | --- |
  | 长度 | **8–32 字节** | 上限 32 **采纳** P12；下限取 **8 而非 6**（6 位空间太小，且沿用服务端既有强度口径）→ 有意偏离 |
  | 字符集 | **数字 / 英文 / 符号** | P12 未提；本次新增（判定 = 可见 ASCII `0x21`–`0x7E`） |

- 实现：`h_auth.cj` 的 `passwordError()` 是**唯一入口**（先长度、后字符集），注册 / 本人改密 /
  `init-admin` 三处共用。加了字符集之后**中文、全角、空格/TAB 一律被拒**，
  P12 那句「中文一字 3 字节」只影响长度怎么算。
- 连带影响：文档里所有中文密码示例（`你的密码123` / `你的口令`）**已全部换成 ASCII**
  （README / HANDOFF / local-deploy / server-guide / client-integration-review\*），
  否则照文档敲的 `init-admin` 会被新规则拒绝。
- 归属：**已落地**（服务端改 + 文档同步）。

### D-7 成员详情身份卡缺两个计数

- 设计稿 P07 身份卡：`2025-09 加入 · 未完成 5 · 逾期 1 · 已完成 12`。
- 服务端：`memberDetailView`（`server/src/views.cj:171`）只给 `member` + `stats: { owned_tasks, open_tasks, owned_plans }`（`:191-195`）。
- 缺口：`已完成` 可由 `owned_tasks - open_tasks` 推出，但 **`逾期` 推不出来**，客户端还得再打一次 `GET /tasks?owner_id=X&overdue=true` 读 `total`。
- 建议：`stats` 增加 `overdue_tasks` / `done_tasks`（服务端一次遍历即可，成本为零）。
- 归属：**服务端改**。

### D-8 待分配列表排序方向与设计稿相反

- 设计稿：P08 列表顺序（本人在原图上核对过）`今天注册 → 昨天注册 → 2 天前注册`（**最新在前**）；P06 的「待分配 · 3」组同样以 `今天注册` 打头。
- 服务端：`pendingMembers()`（`server/src/store.cj:855`）按 `m.id` 升序 = **最早注册在前**（`:863`）；`api-design.md §3.3` 写「按注册时间正序（先来先处理）」。
- 建议：二选一。若按设计稿，改动只有一行（排序键取负）。
- 归属：**需决策**（一行改动）。

### D-9 名录「待分配」组的「来源」普通成员拿不到

- 设计稿 P06：`待分配单独成组并标出来源`，示例 `今天注册 · 来自招募链接（运营部预填）`。
- 服务端：带 `dept_hint` 的只有 `GET /members/pending`（`server/src/views.cj:200` `pendingView`），而该接口要求 `AssignPending` 权限（`server/src/h_member.cj:113`，仅会长 / 副会长）。
- 而 `GET /members?status=pending` 走的是 `memberBrief`（`server/src/h_member.cj:85`），**不含 `dept_hint`**；名录本身又是「全社团可见」的页面。
- 建议：要么让 `memberBrief` 对 `pending` 成员带 `dept_hint`，要么接受"普通成员看不到来源"并改稿。
- 归属：**需决策**（涉及最小化暴露面）。
