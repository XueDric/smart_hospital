# Part 1 · 通用约定

## 1.1 基地址与版本

| 项 | 约定 |
| --- | --- |
| 前缀 | `/api/v1` |
| 传输 | HTTP/1.1，UTF-8 |
| 请求/响应体 | `application/json`（除文件类，v1 无文件） |
| 健康检查 | `GET /health`（**不带** `/api` 前缀，不需要认证） |

**为什么路径要带 `v1`**：客户端是装在成员手机上的 App，通过 AGC 分发。**你无法强制所有人升级**，一旦接口破坏性变更，旧版本 App 会直接崩。带版本号可以 v1/v2 并行跑，给旧客户端留退路。这不是洁癖，是移动端的硬约束。

## 1.2 统一响应格式

**成功**（HTTP 200 / 201）：

```json
{
  "ok": true,
  "data": { }
}
```

列表类 `data` 为分页对象，见 1.7。

**失败**：

```json
{
  "ok": false,
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "任务不存在",
    "fields": { "title": "标题不能为空" }
  }
}
```

**同时使用 HTTP 状态码与业务错误码**，两者分工明确：

- **HTTP 状态码**给网络层用：`401` → 统一踢回登录页，不用解析 body
- **`error.code`** 给业务层用：决定弹什么文案

| 状态码 | 语义 |
| --- | --- |
| 200 | 成功 |
| 201 | 创建成功 |
| 400 | 参数校验失败 / 注册口令错误 |
| 401 | 未认证（缺 token / token 失效 / 密码错） |
| 403 | 已认证但无权限 |
| 404 | 资源不存在 |
| 409 | 冲突（手机号已注册、部门重名） |
| 429 | 请求过于频繁（登录爆破防护） |
| 500 | 服务端错误 |

## 1.3 错误码表

命名规则：`<资源>_NOT_FOUND` / `FORBIDDEN_<原因>`，客户端可直接 `switch`。

| code | HTTP | 场景 |
| --- | --- | --- |
| `VALIDATION_FAILED` | 400 | 参数校验失败，`fields` 里给逐字段原因 |
| `REGISTER_CODE_INVALID` | 400 | 社团注册口令错误（见 Part 2 §2.3） |
| `AUTH_REQUIRED` | 401 | 缺 token |
| `AUTH_TOKEN_EXPIRED` | 401 | token 过期，客户端应静默跳登录 |
| `AUTH_BAD_CREDENTIALS` | 401 | 账号或密码错误 |
| `MEMBER_PENDING` | 403 | 账号已注册，但**尚未被会长分配部门与角色**（见 Part 2 §2.1） |
| `MEMBER_DISABLED` | 403 | 成员已退出社团 |
| `FORBIDDEN_ROLE` | 403 | 角色不足 |
| `FORBIDDEN_NOT_IN_DEPT` | 403 | 跨部门操作 |
| `MEMBER_NOT_FOUND` | 404 | |
| `DEPT_NOT_FOUND` | 404 | |
| `PLAN_NOT_FOUND` | 404 | |
| `TASK_NOT_FOUND` | 404 | |
| `ALREADY_EXISTS` | 409 | 手机号已注册、部门重名等 |
| `PAYLOAD_TOO_LARGE` | 413 | 请求体超过上限（`limits.cj` 的前置闸门，64 KiB，在进内存之前就拒） |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | 请求体类型不受支持（只接受 JSON / 表单 / 文本三类） |
| `LENGTH_REQUIRED` | 411 | 请求体长度**不可判定**（`Transfer-Encoding: chunked`，或 `Content-Length` 不是十进制数字）—— 闸门无法生效，故明确拒绝 |
| `INVALID_JSON` | 400 | 请求体不是合法 JSON（框架 `bodyParser` 的解析失败，已统一到本表的错误信封） |
| `TOO_MANY_ATTEMPTS` | 429 | 登录失败次数过多 |
| `AI_RATE_LIMITED` | 429 | 智能接口的成员级节流（防刷、防费用失控；见 Part 7） |
| `INTERNAL` | 500 | 兜底，**不向客户端暴露堆栈** |

> 回退方案保留：若日后换服务端实现，这张表照搬即可，客户端不用改。

## 1.4 认证

**方案：Bearer Token**（不用 Cookie）。

| 项 | 约定 |
| --- | --- |
| 请求头 | `Authorization: Bearer <token>` |
| 颁发 | 登录成功后返回 |
| 有效期 | **30 天**，每次请求滑动续期 |
| 存储 | 服务端持久化 `token → member_id` 映射（**2026-09-20 起在 MySQL 的 `tokens` 表**；此前是 `data/db.json`） |
| 注销 | `POST /api/v1/auth/logout` 使 token 立即失效 |

**为什么用 Bearer 而不是 Cookie**：客户端是鸿蒙 App 的 HTTP 客户端，不是浏览器。Cookie 的域/路径/`SameSite` 那套语义在这里只会添乱，而轻舟的 session 是基于签名 Cookie 的，需要额外适配。

**为什么是 30 天**：社团成员不是每天登录。有效期设成 1 天，等于每次打开 App 都要重新输密码，这是最容易被卸载的理由之一。

**为什么服务端要存 token 映射**：这样"退出社团"能做到**立即踢下线**。纯无状态 JWT 做不到这点——一个被移出社团的人能继续用旧 token 到过期为止。

## 1.5 安全底线（**需你确认**）

> **2026-09-13 起本节的结论已被 §2.0 取代（下文保留为"当时还没有可用 TLS 实现"的决策背景）**：
> 已采用**框架原生 TLS**（`club-server serve-tls 8443 <DSN> --cert … --key …`），手机端正式使用走 HTTPS；
> `serve 8080` 明文只用于本机联调。

v1 走的是 `http://<公网IP>:8080`，**没有 HTTPS**。这意味着：

- 登录密码、token **以明文经过校园网/公网**
- 任何同网络的人抓包即可拿到 token，进而操作整个社团的数据

**建议：v1 必须上 HTTPS，哪怕是自签证书。** 代价是：

1. 服务端配自签证书（或申请免费证书，但需要域名）
2. **客户端要在 App 里配置信任该证书**，否则鸿蒙的 HTTP 客户端会直接拒绝连接

第 2 点是真实工作量，需要单独排。如果你认为社团内部试用阶段可以接受明文，请在评审时明确记录这个决定——**我不会默认帮你跳过它**。

## 1.6 权限判定

### 判定三层模型

每请求依次判定：

1. **认证**：有没有有效 token → 否则 `AUTH_REQUIRED`
2. **角色**：这个角色能不能做这个动作 → 否则 `FORBIDDEN_ROLE`
3. **部门范围**：目标资源是不是在本部门内 → 否则 `FORBIDDEN_NOT_IN_DEPT`

### 实现要求（重要）

**权限判断必须收敛到一个函数里**，例如：

```
can(member, action, target) -> bool
```

**绝不允许在每个 handler 里手写 if 判断。** 十几个接口各写一遍权限，一定会漏掉某个组合，而权限漏洞在社团工具里是最难被发现、后果最难受的一类 bug。

### 可见范围规则

| 角色 | 可读 | 可写 |
| --- | --- | --- |
| 会长 | 全社团一切 | 一切 + 设置角色 |
| 副会长 | 全社团一切 | 全社团任务与课题，**不能**设置角色 |
| 部长 / 副部长 | 本部门 | 本部门成员、任务、课题 |
| 成员 | **本部门全部**任务与课题 + 成员名录 | **只能改自己的任务状态与阻塞原因** |

**关于成员可读范围（需你确认）**：

建议让成员**能看本部门所有人的任务**（只读）。理由是这与第 1 节要解决的第二个问题直接相关——成员也需要能自己查到"这事谁负责"，不然会继续在群里问。如果只让成员看见自己的任务，这个工具对普通成员就只剩打卡功能。

## 1.7 分页

请求：`?page=1&size=50`

响应 `data`：

```json
{
  "items": [ ],
  "total": 128,
  "page": 1,
  "size": 50
}
```

| 项 | 约定 |
| --- | --- |
| `page` | 从 **1** 开始（不是 0） |
| `size` | 默认 50，最大 200，超出按 200 处理 |
| `total` | 满足筛选条件的总数 |

社团规模不大，分页主要为"任务会随学期累积"留余地。

## 1.8 时间与时区

| 项 | 约定 |
| --- | --- |
| 格式 | ISO 8601 带时区偏移：`2026-09-11T14:30:00+08:00` |
| 服务端存储 | **统一 UTC**，展示时转本地 |
| 可选时间 | 用 `null`，不用空字符串 |
| 小数秒 | **接受并截断**（服务端粒度到秒）。ArkTS / JS 的 `new Date().toISOString()` 产出 `2026-09-14T15:24:08.307Z`，客户端只要用标准库取"现在"就会带上毫秒 |
| 非法历法日期 | **拒绝**（400 `VALIDATION_FAILED`）。`2026-02-30`、平年的 `02-29` 一律不接，绝不静默顺延成 3 月 2 日 |
| 年份 | 4 位。排序/比较用 epoch 秒（Int64），不会有 2038 问题 |

**为什么强调时区**：`due_at` 要同步到系统日历，日历用的是绝对时间。时区处理错一次，提醒就会差 8 小时——而这类 bug 通常到截止前一刻才被发现，最伤信任。

## 1.9 幂等（创建类接口）

移动网络不稳定，用户点一下没反应就会再点一次，产生重复任务。

**约定**：所有 `POST` 创建类接口接受可选字段 `client_token`（客户端生成的 UUID）。

- 服务端记录 `(接口类型, 提交者, client_token) → 已创建资源 id`，**24 小时内**重复提交直接返回首次结果（HTTP 200，`data` 中附 `"duplicated": true`）
- 不传 `client_token` 则不做去重
- ⚠️ **幂等键必须含提交者**（2026-09-14 修订）。只按 `client_token` 索引时，
  甲用某个 token 创建了任务，乙拿同一个 token 重放就会被当成"甲的重复提交"，
  直接把甲的任务读回去——一个绕过权限判定的越权读（P0 缺陷，见 `code-review.md` H-2）。
  带上提交者后，乙的 token 匹配不到任何记录，会走正常创建流程，该 403 还是 403。
  命中回放前还会按**本次操作者**重新判一次读权限，作为防御纵深。

实现成本很低（一张临时映射表），但能挡掉"一个任务被创建三遍"这类最常见的脏数据。

## 1.10 通用请求头

| 头 | 必需 | 说明 |
| --- | --- | --- |
| `Authorization` | 除注册/登录/`/health` 外必需 | `Bearer <token>` |
| `Content-Type` | POST/PUT 必需 | `application/json` |
| `X-Client-Version` | 建议 | App 版本号，便于排查线上问题 |

服务端统一返回 `X-Request-Id`，日志按它串联——出问题时让成员报这一个 id 就能定位。

## 2.1 账号与成员身份分离（核心模型）

### 登录账号 = 手机号

**不用学号**：社团包含**校外人员**（企业指导老师、已毕业学长），他们没有在校学号。手机号人人都有、天然唯一、好记。

### 注册与授权解耦

这是本版相对初稿**最重要的结构改动**：

```
注册 ──▶ [pending 待分配] ──会长分配部门+角色──▶ [active 正式成员]
          · 无部门、无角色、无任何权限
          · 登录后只能看到「等待管理员分配」页面
```

账号与权限的**生命周期完全独立**：

| 场景 | 处理 |
| --- | --- |
| 新人加入 | 注册 → 会长分配 |
| **换届** | **只改角色，账号不动** ← 本次改动要解决的核心问题 |
| 成员退出 | `status = disabled`，账号保留，日后可恢复 |
| 毕业学长回来 | 账号还在，重新赋予角色即可 |

### 手机号不做短信验证

短信有费用、要资质，对社团规模不划算。**防冒用由会长的授权审核环节兜底**——每个账号都必须经过人工分配才能获得任何权限，冒用他人手机号会在这一步暴露。

正因为引入了解耦后的待分配状态，不做短信验证才是可接受的；如果注册即获得权限，就必须上验证。

### 数据模型调整（需同步修订 `v1-scope.md` §5）

| 字段 | 说明 |
| --- | --- |
| `phone` | **登录账号**，全局唯一；同时就是联系方式（取代原 `contact`） |
| `password_hash` | 密码哈希，不落明文 |
| `status` | 由「正常 / 已退出」改为 **`pending` / `active` / `disabled`** |

> 初稿曾建议用 `student_id` 做登录账号，**该建议已撤销**。

**密码**：服务端存哈希（用 stdx 的 crypto），任何情况下不落明文、不进日志。

## 2.2 接口总览

| 方法 | 路径 | 需认证 | 用途 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | 否 | 凭注册口令注册，**注册即登录**，得到 `pending` 账号 |
| POST | `/api/v1/auth/login` | 否 | 手机号 + 密码登录 |

## 2.3 POST /auth/register

**请求**

```json
{
  "register_code": "社团注册口令",
  "phone": "13800000000",
  "name": "张三",
  "password": "ClubPass2026",
  "dept_id": 2,
  "invite_token": "9f3c…（招募链接里的 token）",
  "client_token": "uuid"
}
```

`dept_id` 与 `client_token` 可选。`invite_token` 可选（见下方 2026-09-16 修订）。

**响应 201**

```json
{
  "ok": true,
  "data": {
    "token": "…",
    "expires_at": "2026-10-13T10:00:00+08:00",
    "member": { "…MemberBrief…", "status": "pending" },
    "permissions": { "view_scope": "none", "…其余全部 false…" },
    "dept_hint": { "id": 2, "name": "运营部" }
  }
}
```

> **2026-09-16 修订（D-16：部门预填的两条来源与优先级）**
>
> 部门预填现在有两条来源，**优先级**如下：
>
> | 顺序 | 来源 | 谁说了算 |
> | --- | --- | --- |
> | ① | `invite_token`（招募链接） | **服务端**用 `GET /api/v1/join/{token}` 的同一套逻辑解析，链接**启用中**才作数 |
> | ② | `dept_id`（客户端自报） | 仅在 ① 缺失 / 无效 / 已停用时才采纳 |
>
> - 有了 `invite_token`，客户端**不必**自己把 token 换成 `dept_id` —— 也就不会出现
>   "客户端报的部门和链接实际指向的部门不一致"。
> - **链接失效不阻断注册**：链接是便利，注册口令才是准入（§3.7）。此时退回 ②，
>   两者都不可用则预填为空。
> - 响应里的 **`dept_hint`** 是**本次实际采纳**的预填（`null` = 没有），
>   让"预填到底生效没有"可观察 —— 不让调用方自己猜（本项目一贯纪律）。
>   `POST /auth/login` 的响应里该字段恒为 `null`（预填只在注册时采纳一次）。

**错误**

| code | HTTP | 场景 |
| --- | --- | --- |
| `VALIDATION_FAILED` | 400 | 字段级原因放 `fields` |
| `REGISTER_CODE_INVALID` | 400 | 注册口令错误 |
| `ALREADY_EXISTS` | 409 | 手机号已注册 |

**说明**

1. **注册即登录**：直接签发 token。但账号是 `pending`，权限全为 `false`，**客户端应跳转「等待管理员分配」页，而不是主界面**
2. **注册口令只决定"能否注册"，不决定任何角色。** 它是社团共享口令，会长可在管理页随时更换。相比逐个发放一次性邀请码，**换届时不需要重发**，新成员问一句就能注册
3. **`dept_id` 来自部门招募链接**（如「运营部招新」）。它**只做部门预填**，角色一律默认 `member`，且**仍需会长确认**才转为 `active`。这样既减轻会长负担，又不让任何人凭一个链接自动获得成员身份
4. ⚠️ 请求体**不接受** `role`。任何角色都必须由会长在管理界面授予——这是防越权的关键，否则任何人都能把自己注册成会长
5. 密码规则 = **8–32 字节**，且**只允许数字、英文与符号**（不强制大小写数字混合——
   社团内部工具，复杂度要求只会逼出 `Aa123456` 这种更差的密码）
   > **口径说明（2026-09-13 确认，2026-09-16 修订定稿）**
   >
   > | 维度 | 规则 | 说明 |
   > | --- | --- | --- |
   > | 长度 | **8–32 字节** | 按**字节**计（服务端 `String.size` 即字节数） |
   > | 字符集 | **数字 / 英文 / 符号** | 判定 = 每个字节都是**可见 ASCII**（`0x21`–`0x7E`） |
   >
   > - **上限 32** 是 2026-09-16 新增的：此前只有下限 `≥ 8`，超长密码会一路进 PBKDF2，
   >   与注册口令（6–32）不对称。这里采纳 UI 设计规格 P12 的上界。
   > - **下限取 8 而不是设计规格 P12 的 6**：6 位口令空间太小（纯数字只有 100 万种），
   >   而服务端既有的强度口径就是 8；这是**有意偏离设计稿**的一处，已记录在
   >   `ui-spec-conformance-review.md` 的 D-6。
   > - **字符集**同样来自 2026-09-16 的决定：只允许数字 / 英文 / 符号（如 `._/\-!@#`）。
   >   于是中文、全角字符与空格/TAB 一律被拒 —— 排除输入法全角半角造成的
   >   "看起来一模一样、登录却失败"，那是移动端最难排查的一类问题。
   >   ⚠️ 加了字符集之后，"中文一字 3 字节"只影响**长度怎么算**；中文密码本身会被字符集挡掉。
   > - 服务端实现：`h_auth.cj` 的 `passwordError()` 是**唯一入口**，注册 / 本人改密 /
   >   `init-admin` 三处共用（避免多处各写一遍而漂移）。重置密码签发的临时密码是
   >   8 位 ASCII，落在区间内。
6. **注册口令长度下限 6 位，且注册接口按客户端 IP 做失败节流**（2026-09-14 二次修订：无节流 → 全局节流 → **按 IP + 递增退避**）。
   口令是**全社团共用的单一秘密**，只需猜中一次就能拿到账号，4 位空间只有约 45 万种，
   在线爆破是小时级的事。规则：同一 IP 在 15 分钟内口令错 10 次 → 锁定该 IP
   （返回 `TOO_MANY_ATTEMPTS`）；锁定时长**递增退避**：首次 5 分钟，同一 IP 每再触发一次翻倍，上限 1 小时。
   > **按 IP，而不是全局**（2026-09-14 更正）。本节此前写"轻舟没有暴露可信的客户端 IP，
   > 伪造 `X-Forwarded-For` 即可绕过"——**这句是错的**，它把两个概念混在了一起：
   > 轻舟通过 `ctx.http.request.remoteAddr` 暴露 **TCP 对端地址**（即 `h_ops.cj` 的 `peerOf` / `clientIpOf`），
   > 那是传输层事实，客户端伪造不了；可伪造的是 `X-Forwarded-For` **请求头**，
   > 而本项目直连部署、根本不读它。
   > 实测该字段的文本形如 `IP:端口`（例 `127.0.0.1:14764`），所以按 IP 分桶前**必须先剥掉端口**，
   > 否则同一台机器每个连接都是新 key，限流形同虚设。
   > 旧全局锁的真实代价：攻击者每 15 分钟丢 10 个错口令，就能把**所有人**挡在注册门外。
   > **已知局限**（别高估）：NAT / 校园网出口下整个社团可能共用一个公网 IP，那时按 IP 会近似退化成全局锁；
   > 取不到对端地址时 key 为空串，同样退化为全局。两种情况都比"无条件全局锁"更窄。
   > 另外，按 IP **不阻止分布式尝试**（IPv6 在一个 /64 内轮换源地址尤其便宜），
   > 所以它挡不住"换着源地址爆破"，安全性最终依赖口令长度（≥ 6 位，26⁶ ≈ 3.09 亿种）。
   > 别把"按 IP"读成"不可爆破"。
   > 锁定**只影响注册**，不影响登录与其它接口；也**没有新增"解除锁定"接口**——改成按 IP 之后，
   > 被锁的只有攻击者自己那个地址，正常用户不受影响，不需要会长介入。
   > 节流状态**只存在内存**（不落盘）：失败是高频路径，每失败一次就写一次整库本身就是可被利用的放大杠杆。
   > 重启后计数清零可以接受——攻击者没有让服务重启的手段。

## 2.4 POST /auth/login

**请求**

```json
{ "phone": "13800000000", "password": "…" }
```

**响应 200**：`data` 与 register 相同（`token` + `expires_at` + `member`）

**错误**

| code | HTTP | 场景 |
| --- | --- | --- |
| `AUTH_BAD_CREDENTIALS` | 401 | 手机号不存在**或**密码错误 |
| `MEMBER_DISABLED` | 403 | 成员已退出社团 |
| `TOO_MANY_ATTEMPTS` | 429 | 失败次数过多 |

**说明**

- ⚠️ **"手机号不存在"与"密码错误"必须返回同一个错误码**，不得泄露某手机号是否注册过
- ⚠️ **登录限流必须做**。这个服务会暴露在公网，登录接口一定会被撞库扫描。规则：同一手机号 15 分钟内失败 5 次 → 锁定 15 分钟。实现很简单，但 v1 里省不掉
- **`pending` 账号可以正常登录**，只是 `permissions` 全为 `false`、`view_scope` 为 `none`。客户端据此显示「等待管理员分配」页，**不要**当成错误踢回登录页

## 2.5 POST /auth/logout

请求体为空。响应 `200 { "ok": true }`。

**说明**：服务端删除 `token → member_id` 映射，旧 token **立即**失效。这正是 Part 1 §1.4 选择"服务端存 token 映射"而非纯无状态 JWT 的原因——成员退出社团或被移出后，能立刻踢下线。

## 2.6 GET /auth/me

**响应 200**

```json
{
  "ok": true,
  "data": {
    "member": { "…MemberBrief…" },
    "permissions": {
      "view_scope": "all",
      "manage_members": false,
      "set_role": false,
      "create_plan": false,
      "create_task": false,
      "update_any_task": false,
      "manage_depts": false,
      "view_register_code": false,
      "change_register_code": false,
      "manage_invite_links": false,
      "transfer_presidency": false
    }
  }
}
```

**说明**：这是客户端启动时调的第一个接口，一石二鸟：

1. **校验 token 是否仍有效**（返回 401 就跳登录页，不需要额外接口）
2. **拿到权限摘要**，客户端据此决定 UI 显示什么

> 权限判定**只保留服务端一份**。客户端读 `permissions` 是为了画界面，绝不能用它替代服务端校验——真正的拦截仍在 `can(member, action, target)`（见 Part 1 §1.6）。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | |
| `name` | string | 姓名 |
| `role` | string \| null | `president` / `vice_president` / `lead` / `vice_lead` / `member`；**`pending` 时为 `null`**。另有一个**内置运维身份 `ops`**（2026-09-16 新增，不可由 API 分配、只能 `init-ops` 创建；权限=会长去掉移交会长。见 §3.8 的运维口径与 `v1-scope.md` §3.4.4） |

## 3.2 成员名录

### GET /members

**权限**：全体 `active` 成员

**Query**：`dept_id` / `role` / `status` / **`q`** / `page` / `size`（默认只返回 `active`）

> **`q`（2026-09-16 新增，设计规格 D-2）**：按**姓名或部门名**模糊匹配（包含、大小写不敏感）。
> 设计规格 P06 的搜索框占位符原文就是「搜索姓名或部门」。
> ⚠️ **手机号不参与匹配** —— P06 底部明确「名录不含手机号——这是隐私最小化」，
> 接口里既然不返回它，就不该能被检索出来（否则等于换个方式泄露）。
> 待分配成员（`dept_id = 0`）按其 `dept_hint` 的部门名参与匹配，否则名录里搜「运营部」会漏掉他们。

**响应 200**：分页的 `MemberBrief` 列表

> **建议：成员名录对全体成员开放（全社团可见）。**
> 理由：这是第 1 节要解决的**第一个问题**——「社团里有哪些人」。如果成员只能看自己部门，这个问题就没被解决。
> 注意区分：**名录全社团可见，但任务与课题仍按部门限制**。这两件事的可见性不必一致。
> ⚠️ 2026-09-16 起**后半句不再成立**：任务与课题的**读**也已全社团开放（见 §4.2），
> 详见 `v1-scope.md` §3.4.3 的修订。

**权限**：全体 `active` 成员

**响应 200**：`MemberBrief` + 计数摘要

  "data": {
    "member": { "…MemberBrief…" },
    "stats": { "owned_tasks": 17, "open_tasks": 5, "done_tasks": 12,
               "overdue_tasks": 1, "owned_plans": 1 }
  }

只给**计数**，不展开任务明细——明细属于 Part 4 的列表接口。

> **`done_tasks` / `overdue_tasks`（2026-09-16 新增，设计规格 D-7）**：设计规格 P07 的身份卡是

### PATCH /members/{id}

**权限**：见 3.8 的权限表

请求体字段全部可选：`name` / `dept_id` / `role`。

> **字段级权限（2026-09-13 明确）**：`name` 走 **编辑成员姓名**（部长/副部长限本部门），
> `dept_id` / `role` 走 **调部门/改角色**（仅会长、副会长）。两者权限不同，
> 不能因为它们在同一个请求体里就合并判定。
>
> **待分配成员**只接受 `name`；对它传 `dept_id` / `role` 返回 `VALIDATION_FAILED`，
> 提示改用 `POST /members/{id}/assign`——避免两条路径各写一半授权逻辑。

**错误**

| code | HTTP | 场景 |
| --- | --- | --- |
| `FORBIDDEN_LAST_PRESIDENT` | 409 | 试图把**最后一个** `president` 降级 —— 见 `v1-scope.md` 规则 10 |
| `VALIDATION_FAILED` | 400 | |

### POST /members/{id}/disable

**权限**：会长 / 副会长

**说明**：把 `status` 置为 `disabled`，**账号与历史记录全部保留**（不删除）。该成员名下未完成的任务需要先转移——见下方错误。

| code | HTTP | 场景 |
| --- | --- | --- |
| `MEMBER_HAS_OPEN_TASKS` | 409 | 名下有未完成任务，响应里给出任务列表，要求先转交 |
| `FORBIDDEN_LAST_PRESIDENT` | 409 | 不能禁用最后一个会长 |

> **`MEMBER_HAS_OPEN_TASKS` 的响应形状（2026-09-13 明确）**：任务清单放在
> `error.fields.tasks`，每项为 `{ "id": 12, "title": "…", "status": "doing" }`。
> 这样不必为错误响应新增字段、也不改动统一包封——客户端按 `code` 分支后直接读 `fields.tasks` 即可。
>
> **幂等**：对已经 `disabled` 的成员重复调用返回 200（客户端重试不该产生错误）。

> 不允许"人走了任务跟着烂尾"。这也是本工具要解决的问题——**谁负责，得有人接手**。

## 3.3 待分配与授权

### GET /members/pending

**权限**：会长 / 副会长（可选增强见 3.8 待拍板项 4）

**响应 200**：`pending` 成员列表，按注册时间正序（先来先处理）

```json
{
  "ok": true,
  "data": {
    "items": [
      { "…MemberBrief…": "", "status": "pending",
        "dept_hint": { "id": 2, "name": "运营部" },
        "registered_at": "2026-09-13T10:00:00+08:00" }
    ]
  }
}
```

`dept_hint` 来自部门招募链接，**只是提示**，不是已生效的部门。

### POST /members/{id}/assign

**权限**：会长 / 副会长

```json
{ "dept_id": 2, "role": "member" }
```

**响应 200**：更新后的 `MemberBrief`（`status` 变为 `active`）

**说明**：**幂等**。对已是 `active` 的成员重复调用同样的分配，返回 200 而不报错——客户端重试不该产生错误。

> 对 `disabled` 成员调用即**恢复**：账号一直在，重新赋角色即可（见 §2.1 的生命周期表）。
> 分配成功后 `dept_hint` 清空——预填信息已完成使命。
>
> ⚠️ **恢复必须可追溯（2026-09-14 明确，见 `code-review.md` M-4）**。`disable` 保留全部数据、
> 文档也写明"日后可恢复"，所以本接口不拒绝 `disabled` 目标——但恢复与普通分配**混成了同一个语义**：
> 没有专门接口、没有额外确认，审计日志里也只记成普通的分配。
> 现状按"保持行为、补全可追溯性"处理：
> 1. 目标原本是 `disabled` 时，审计动作名记为 **`restore-member`**（普通分配仍是 `assign-member`），
>    note 里写明"恢复已退出成员"；
> 2. `assign-batch` 的审计 note 增加"其中恢复已退出成员=N"；
> 3. 本行为在此**明确成文**，不再是实现先跑、文档后补的空白区。
>
> 如果后续认为"恢复"应当是一个需要更高确认度的动作，第 2 个方案是给它一个独立入口
> （如请求体带 `restore: true`，或单独的管理接口）——那属于 v1 之后的范围扩展，
> 会改变接口清单数量，需先确认。

> ⚠️ **`role` 不得为 `president`**（2026-09-13 补充）。
> 会长**只能由 `POST /members/{id}/transfer-presidency` 产生**——那是唯一的原子移交路径。
> 若允许本接口直接授予 `president`，就会出现两个会长，规则 10「系统必须始终至少有一个 `president`」
> 与规则 11「会长移交是一个明确操作」同时失去意义。传入 `president` 返回 `VALIDATION_FAILED`。

### POST /members/assign-batch

**权限**：会长 / 副会长

```json
{ "member_ids": [11, 12, 13], "dept_id": 2, "role": "member" }
```

**响应 200**——**逐条报告结果，允许部分成功**：

```json
{
  "ok": true,
  "data": {
    "succeeded": [11, 12],
    "failed": [ { "id": 13, "code": "MEMBER_NOT_FOUND" } ]
  }
}
```

> ⚠️ **批量接口绝不能"一条失败就整体回滚"。** 招新期一次处理 20 个人，因为其中 1 个数据有问题就全部不生效，
> 会长会疯掉。逐条报告、让成功的生效，才是可用的批量语义。

**这是招新期最重要的一个接口**——它直接决定第 2 节验收标准 1 能否达成。

## 3.4 会长移交

### POST /members/{id}/transfer-presidency

**权限**：**仅现任会长**

```json
{ "self_role": "vice_president" }
```

**响应 200**

**说明**：这是**一个原子操作**，内部同时完成：

1. 目标成员 `role → president`
2. 自己 `role → self_role`（默认 `vice_president`）

> ⚠️ **这是产生会长的唯一入口**（2026-09-13 补充）。
> `POST /members/{id}/assign` 与 `PATCH /members/{id}` 一律**拒绝** `role = president`，
> 因此系统里换会长只有这一条路可走：**原子、两步同时生效、不会出现零会长窗口**。

> ⚠️ **为什么必须是一个接口，而不是"改两次角色"？**
> 分两步做，中间会出现**零会长**的状态。虽然只是短暂窗口，但如果第二步失败（网络、进程重启），
> 社团就永久失去管理能力，只能改服务器数据文件——见 `v1-scope.md` 规则 10 与 11。

**错误**

| code | HTTP | 场景 |
| --- | --- | --- |
| `MEMBER_PENDING` | 403 | 目标成员尚未被分配部门与角色，不能接任 |
| `MEMBER_DISABLED` | 403 | 目标成员已被移出社团，不能接任 |
| `VALIDATION_FAILED` | 400 | 目标就是自己 |

> **2026-09-14 修订（`code-review.md` L-8）**：`pending` 与 `disabled` 原先共用 `MEMBER_PENDING`，
> 客户端会提示"尚未被分配"，而真实原因是"已被移出社团"。两种状态给两个码，
> 与 `POST /auth/register` / 任务创建路径保持一致。

## 3.5 密码

### PUT /auth/password（本人改密）

**权限**：本人

```json
{ "old_password": "…", "new_password": "…" }
```

`new_password` 与注册走**同一口径**：**8–32 字节**、**只用数字 / 英文 / 符号**
（见 §2.3 注 5）。不满足时 `VALIDATION_FAILED`（400），`fields.new_password` 给字段级提示 ——
校验发生在**验证旧密码之前**，所以被拒的请求连旧口令都不会去比，更不会改动任何状态。

改密成功后**当前 token 之外的其他 token 全部失效**（见 Part 1 §1.4）。若怀疑账号被盗，这是有效的自救手段。

| code | HTTP | 场景 |
| --- | --- | --- |
| `AUTH_BAD_CREDENTIALS` | 401 | 旧密码错误 |

### POST /members/{id}/reset-password

**权限**：会长 / 副会长 / 部长 / 副部长，但**只能作用于档位低于自己的人**——
**不可重置与自己同权或更高权的人**（对自己而言就是同权，因此任何人都不能用本接口改自己的密码）。
本人改密一律走 §3.5 的 `PUT /auth/password`（需原密码）。

**响应 200**

```json
{ "ok": true, "data": { "temporary_password": "k7m2p9qd" } }
```

**说明**：

- 服务端**随机生成**临时密码，**只在这一处返回一次**，之后不再可查
- 这是 v1 里"忘记密码"的唯一出路（不做短信 / 邮箱自助找回）
- 被重置者用临时密码登录后，应自行用 `PUT /auth/password` 改掉
- 该操作**记入日志**（谁在什么时候重置了谁）——这是敏感操作，需要可追溯
- ⚠️ **本接口不含"本人"**（2026-09-14 口径统一）。对本人而言与操作者同权，正是下面那条
  通用规则的第一个特例。本人改密走 §3.5 的 `PUT /auth/password`
  （需要验原密码，更安全）；本接口签发一次性临时密码，属于**管理员救济动作**。
  此前 §3.8 汇总表与 `v1-scope.md` 曾把成员列写成「仅本人」，与本节及 §6.1 自相矛盾，现已统一。
- ⚠️ **不能作用于会长本人**，且部长 / 副部长**只能作用于档位低于自己的成员**
  （部长动不了另一位部长，也动不了副会长与会长，即使目标与自己同部门）。
  这条约束原先只写在副会长那一档，导致同部门的部长可以重置会长密码并接管账号，
  已作为 P0 缺陷修复（见 `code-review.md` H-1）。
- ⚠️ **不可重置与自己同权或更高权的人**（2026-09-14 定，见 `code-review.md` N-7）。
  这条通用规则一次覆盖三种情况：
  - **对自己同权** → 任何人都不能用本接口重置自己（会长 / 副会长 / 部长都一样）。
    此前"不含本人"只是文档与注释口径，代码里并没有拦：会长与副会长的角色分支都是
    **直接放行**，所以他们重置**自己**会成功；而该操作收尾会把目标的全部令牌作废，
    表现为"响应 **200**、自己当场掉线"（客户端拿到成功，下一个请求却 401）。
  - **副会长对副会长同权** → 同权之间不能互相踢下线（原先没有这条约束）。
  - **会长档位最高**，除自己外无人与之同权 → 会长仍能重置任何更低档的人。
  约束落在 `perms.cj` 的 `checkAccess`（**动作语义层**），不靠各 handler 自觉 ——
  权限判定仍然只有一处。
  > 该规则随后**推广到"调部门 / 改角色"、"移出社团"、"编辑姓名"**（同一天），
  > 因为只保护重置密码时，副会长仍可把另一位副会长降级或禁用。详见 §3.8 的
  > 2026-09-14 修订第 3 条。
- ⚠️ **本人改自己密码的通道不变**：`PUT /auth/password`（会长也一样，需原密码）。
  唯一的边界是"彻底忘记原密码"——该通道要验原密码，此时 v1 没有自助找回
  （见 `README.md` 未决事项 #4），不在本节范围内。

### GET /dept-invite-links

**权限**：会长 / 副会长

### POST /dept-invite-links

**权限**：会长 / 副会长

```json
{ "dept_id": 2 }
```

**响应 201**

```json
{
  "ok": true,
  "data": {
    "token": "a1b2c3d4",
    "url": "https://<host>/join/a1b2c3d4",
    "dept": { "id": 2, "name": "运营部" },

  }

```

### DELETE /dept-invite-links/{token}

**权限**：会长 / 副会长 —— 停用链接（招募结束后关闭）

> **语义是"停用"而不是删除记录（2026-09-13 明确）**：置 `enabled = false`，记录保留，
> 便于在列表里看到"已停用的秋招链接"。与 `GET /dept-invite-links` 的 `enabled` 字段一致。
>
> **幂等**：对不存在或已停用的 token 重复调用一律返回 **200**——与 `assign` 同理，
> 客户端重试不该产生错误（也因此不需要引入新的"链接不存在"错误码）。
>
> **响应形状统一（2026-09-14 修订）**：链接不存在时也返回**同一个视图**
> （`token` 回显、`enabled: false`、`dept` 为空对象、`created_at: null`），
> 原先返回空对象 `{}`，客户端要多写一个"有没有 `data.link`"的特例。

**说明**：

- 招募链接**只做部门预填**，**不赋予任何角色**。通过它注册的人仍是 `pending`，必须经审批才转为 `active`
- **链接不免除注册口令**。设计上保持**单一门槛**：链接是便利，口令才是准入。否则就有了两套平行凭证，泄露时要想两处
- 每个部门可以有多个链接（如"2026 秋招"和"补录"），便于分别停用与统计来源

### GET /api/v1/join/{token}（招募链接的**公开 JSON 解析**，2026-09-16 新增）

**权限**：公开（无需登录）

**响应 200**

```json
{ "ok": true, "data": { "dept": { "id": 2, "name": "运营部" }, "enabled": true } }
```

链接不存在或已停用时，**返回同一个形状**（不引入新错误码）：

```json
{ "ok": true, "data": { "dept": null, "enabled": false } }
```

**为什么需要它（D-16）**：链接是发到群里的 `https://<host>/join/<token>`，而 HarmonyOS App
在 v1 **不做 deep link 配置**（见下），所以 App 拿到 token 之后**没有任何免认证的途径**
把 token 换成 `dept_id` —— 落地页只回 HTML。没有这个端点，P12 的
「来自于招募链接的部门预填」就只能靠客户端自报部门，链路不闭环。

- 客户端用它渲染预填块（「来自于招募链接的部门预填：运营部。它只是 dept_hint，审批前不生效。」），
  注册时把同一个 `invite_token` 原样带上（§2.3），**部门由服务端解析**。
- 只暴露部门名与启停状态：那本来就是链接持有者能看到的信息，不含口令、成员或任务数据。
- 形状与停用接口同源（见下 L-3 口径）：客户端不必为"有没有 `data.dept`"写特例。

### GET /join/{token}（链接落地页，**不在 /api/v1 下**）

**权限**：公开（无需登录）

返回一个最小可用的 HTML 说明页，告诉打开链接的人这个链接属于哪个部门、下一步该做什么。

**说明**：

- 客户端是 HarmonyOS 应用，浏览器打开链接**无法**直接唤起 App（v1 不做 deep link 配置），
  所以落地页必须自己存在——否则招募链接点开就是 404，而它是要被发到群里的
- 页面**只暴露部门名**：那本来就是链接持有者能看到的信息，不含口令、成员或任务数据
- 链接已停用或不存在时同样返回 200，页面提示"链接已失效"
- 生成的 `url` 用请求的 `Host` 头拼装（避免把域名写死进配置）。
  ⚠️ 已知取舍：`Host` 头是调用方可控的，响应里的 `url` 会被污染——只影响调用方自己的响应，
  不落盘、不影响他人，因此定为低危；正式上线时应改为服务端配置项

## 4.1 GET /tasks/mine —— 我的任务（首页）

**这是 v1 最重要的接口。** 第 1 节已经论证过：真正让人每天打开 App 的是「我负责什么」，不是组织架构图。

**权限**：全体 `active` 成员（主体永远是自己负责的任务）

**响应 200**——**服务端直接分好组**：

```json
{
  "ok": true,
  "data": {
    "overdue":  [ { "…TaskBrief…" } ],
    "blocked":  [ { "…TaskBrief…" } ],
    "due_today":[ { "…TaskBrief…" } ],
    "due_week": [ { "…TaskBrief…" } ],
    "later":    [ { "…TaskBrief…" } ],
    "no_due":   [ { "…TaskBrief…" } ],
    "counts": { "overdue": 2, "blocked": 1, "open_total": 7, "borrowed_blocked": 0 }
  }
}
```

> **部长 / 副部长的例外（2026-09-16 新增，设计规格 D-4）**
>
> 设计规格 P03 的阻塞原因块里写着「需要帮助 · 宣传部 陈屿（**部长在首页即可看到这条**）」，
> 对应 P01 首页上部长看到的那条「运营部 · 负责人 王砚」的**别人的**阻塞任务。
> 因此：**部长 / 副部长**调本接口时，除自己负责的任务外，**额外**返回
> 「本部门其他成员处于 `blocked` 的任务」——它们**同样进 `blocked` 组，也按同一套时间桶
> 进入 `overdue` / `due_today` / `due_week`**（与下面"阻塞项同时出现在时间分组"一条一致），
> 并计入 `counts.blocked` 与 `counts.open_total`。
>
> - `counts.borrowed_blocked` = 其中"不是自己负责、而是本部门被阻塞"的条数。
>   部长 / 副部长之外的角色恒为 `0`（不会出现别人的任务）。
> - 会长 / 副会长**不参与**这一条：他们要全貌走 `GET /tasks`，首页不该被全社团的阻塞项淹没。
> - 客户端不需要额外标志位判断"这条是不是我的"：比 `owner.id` 与自己的 `id` 即可
>   （P01 的卡片本来就把负责人渲染出来了）。
> - ⚠️ 这是**首页聚合口径**，不是可见性放宽——读范围本身已全社团开放（见 §4.2）。

**为什么由服务端分组，而不是客户端算：**

1. 「今天 / 本周 / 逾期」的判定依赖**时区口径统一**（Part 1 §1.8）。客户端各自算，跨设备会不一致
2. 客户端少一份逻辑，就少一处 bug——这块逻辑每个客户端都要写一遍

**排序**：组内按 `due_at` 升序；`no_due` 排最后。

**⚠️「逾期」是派生量，不是状态。** 任务状态永远只有 4 档，`is_overdue` 由 `due_at` 与当前时间算出。
这与「课题不单独设状态」同源：**能从事实推导的东西就不要单独存**，否则两边必然不一致。

`blocked` 组里的任务同时也会出现在其他组（阻塞是状态，逾期是时间事实，两者不互斥）。

## 4.6 PUT /tasks/{id}/status

**权限**：负责人本人 / 部门管理员 / 会长 / 副会长

```json
{ "status": "blocked", "blocker": "等场地审批，已提交 3 天",
  "help_dept_id": 3, "help_member_id": 12 }
```

| status | 说明 |
| --- | --- |
| `todo` | 未开始 |
| `doing` | 进行中 |
| `blocked` | 阻塞 |
| `done` | 已完成 |

| 可选字段 | 说明 |
| --- | --- |
| `help_dept_id` | **求助部门**（设计规格 D-4）。0 / 不传 = 未指定求助对象 |
| `help_member_id` | **求助人**（可到人）。只填人时按该成员所在部门**自动补齐** `help_dept_id` |

**规则**

1. **进入 `blocked` 时必须带 `blocker`**，否则 `BLOCKER_REQUIRED`（400）。
   这是整个工具信息量最大的一个字段——它把「进度落后」翻译成「需要帮助」。允许留空就等于允许它变成摆设。
2. **离开 `blocked` 时自动清空 `blocker`**（历史由 `updated_at` 体现，v1 不做完整变更历史）
3. 进入 `done` 记 `completed_at`；从 `done` 退回其他状态时清空
4. **允许任意状态互跳，不设状态机流程图**。社团场景下限制跳转只会添堵——真实情况是"这事其实早做完了，我忘了标"
5. **求助对象（2026-09-16 新增，设计规格 D-4）**：对应 P03 阻塞原因块里的那一行
   「需要帮助 · 宣传部 陈屿」。规则：
   - **只在 `blocked` 下有意义**：非阻塞状态传了非零的 `help_*` → `VALIDATION_FAILED`（400）。
     不静默忽略——静默忽略会让调用方以为求助已经登记上了（本项目一贯纪律）。
   - **离开 `blocked` 时与 `blocker` 一起清空**（同一个信息块，不该留下半截状态）。
   - `help_member_id` 必须是 `active` 成员（`pending` → `MEMBER_PENDING`，`disabled` → `MEMBER_DISABLED`）；
     与 `help_dept_id` 同时给出且**不在同一部门** → `VALIDATION_FAILED`。
   - 返回体里以 `needs_help: { dept, member }` 出现，没有求助对象时为 `null`（见 §4.9）。

## 4.8 日历同步 —— ⚠️ 数据模型需要修正

`v1-scope.md` §7 把 `calendar_event_id` 放在**服务端的 `Task` 表**上。**这个位置是错的**，理由有四条：

1. **日历事件在成员自己的手机上**，不在服务端
2. **同一个任务可能被多个人加入日历**（负责人、部长、关注者），服务端存**一个** id 无法表达
3. 换手机后本地事件消失，服务端那个 id 就成了**悬空引用**
4. 服务端**不应该也不需要**知道谁把什么事加进了自己的日历——这本身是隐私

### 正确模型：事件 ID 由客户端本地维护

| 位置 | 存什么 |
| --- | --- |
| **客户端本地** | `task_id → { event_id, cached_due_at, cached_status }` |
| **服务端** | 只提供事实：`due_at`、`status`、`updated_at`。**不存任何日历字段** |

客户端在拉取任务时比对 `cached_*` 与服务器值：

| 差异 | 客户端动作 |
| --- | --- |
| `due_at` 变了 | **更新**本地日历事件（不是新建） |
| `status` 变为 `done` | **删除**本地日历事件 |
| 任务已不在服务器返回中 | **删除**本地日历事件 |
| 本地没有、服务器有 | 不动（用户没加过日历） |

### 为此需要一个辅助接口

客户端需要知道"我加过日历的任务，现在还在不在"。

### POST /tasks/lookup

**权限**：`active` 成员

```json
{ "task_ids": [12, 15, 27] }
```

**响应 200**

```json
{
  "ok": true,
  "data": {
    "items": [ { "id": 12, "due_at": "…", "status": "doing", "updated_at": "…" } ],
    "missing": [ 15, 27 ]
  }
}
```

`missing` 里的 id 表示**任务已删除或无权访问** → 客户端据此清理本地日历事件。

**说明**：这个接口很小，但没有它，客户端就无法可靠地回收日历事件，日历里会堆积错误提醒——这会让成员再也不相信它。

### 对 v1-scope 的影响

| 位置 | 需要修订 |
| --- | --- |
| `v1-scope.md` §5 `Task` 表 | **删除 `calendar_event_id` 字段** |
| `v1-scope.md` §7 | 从"服务端唯一的真工程量"改为**客户端机制** |

> **工作量没有消失，只是换到了客户端**。而且换过去之后**更好验证**——日历同步错了是用户看得见的，
> 藏在服务端反而难以发现。这一项需要在客户端排期里单独列出。

## 4.9 公共数据结构

### TaskBrief（列表用）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | |
| `title` | string | |
| `status` | string | `todo` / `doing` / `blocked` / `done` |
| `owner` | MemberBrief | 负责人 |
| `dept` | object \| null | 部门标签 |
| `plan` | object \| null | `{ "id": 5, "title": "…" }` |
| `due_at` | string \| null | ISO 8601 |
| `is_overdue` | bool | **服务端算好的派生量** |
| `overdue_days` | int | **逾期天数**，服务端算（见下）。未逾期为 `0` |
| `blocked` | bool | |
| `blocker` | string \| null | **阻塞原因**（见下）。非阻塞时为 `null` |
| `needs_help` | object \| null | **求助对象** `{ dept, member }`；无求助时为 `null`（见下） |
| `updated_at` | string | **自动记录，不可由客户端设置** |

> **`blocker` 进 TaskBrief（2026-09-16，队友复验 P0）**：设计规格 P01 的「阻塞中」分组卡片里
> **直接渲染阻塞原因高亮块**（「阻塞原因（进入 blocked 必填）」+ 原因原文）。
> 原先 `blocker` 只在 `TaskDetail` 里，首页想让这张卡显示原因就得**为每张卡再打一次详情接口**——
> 而 P01 的原话正是「服务端已排好序，客户端只渲染、不重算」。
> 因此 `blocker` 上移到 `TaskBrief`：`/tasks`、`/tasks/mine`、`/plans/{id}` 的任务列表都直接带原因。
> 无泄漏：阻塞原因本来就在任务详情里，而任务读范围已是全社团（§4.2）。

> **`overdue_days`（2026-09-16 新增，设计规格 D-5）**：设计规格 P01 卡片写「逾期 2 天」、
> P03 提示条写「已逾期 2 天 · **该判断由服务端算出，客户端不重算**」——所以天数也必须由服务端下发。
> 口径 = **本地日界的整数差**（不是 24 小时取整）：
> `09-12 18:00` 截止、`09-14 09:00` 现在 → `2`；
> 今天 09:00 截止、今天 18:00 现在 → `0`（即 `is_overdue = true` 且 `overdue_days = 0` 表示"今天逾期"，
> 客户端据此显示「已逾期」而不是「逾期 0 天」）。
> ℹ️ **不需要额外的 `server_now`**：分组（今天 / 本周 / 逾期）已由服务端算好下发，
> 天数也由服务端给，客户端不需要用本地时钟参与任何判定。

> **`needs_help`（2026-09-16 新增，设计规格 D-4）**：对应 P03 阻塞块里的
> 「需要帮助 · 宣传部 陈屿」。形状：

> `member` 为 `null` 表示只求助到部门、不指定到人；整个 `needs_help` 为 `null` 表示没有求助对象

# Part 5 · 课题

## 5.0 本部分范围

课题是**可层层往下分割的容器**，任务是叶子。`v1-scope.md` 3.5.2 已经列明四个"必须做对"的点，全部落在这一部分：

| # | 必须做对的点 | 在哪一节 |
| --- | --- | --- |
| 1 | **环形引用校验** | 5.6 |
| 2 | **递归进度聚合** | 5.8 |
| 3 | **删除上提**（不级联） | 5.7 |
| 4 | **每个课题必须有负责人** | 5.4 |

## 5.1 树结构的两条数据规则

### 规则 A：`dept_id` 只存在**顶层课题**上

初稿给每个 `Plan` 都存 `dept_id`，并规定"子课题继承父课题"。但**"继承"如果靠在子节点复制一份，就又是同一事实存两份**——和 `Department.lead_id` 完全一样的问题。

**正确做法：子课题不存 `dept_id`。** 其部门由所属**根课题**决定。

这样做换来三个好处：

1. 「子课题不允许跨部门」**自动成立**，不需要写校验
2. **移动课题时不需要级联更新部门**——因为根本没存
3. 又消灭一类不一致

### 规则 B：深度硬上限 6 层

**创建与移动时校验**：超过 6 层返回 `PLAN_DEPTH_EXCEEDED` (400)。

环形校验防的是环，防不了"上千层直线嵌套"这类病态数据——**上限的意义是防呆，不是限制表达**。6 层足够覆盖任何真实的社团拆分（顶层课题 → 子课题 → 孙课题 …）。

`GET /plans` 的 `depth` 参数同样以 **6** 为上限。

> UI 上建议实践控制在 **3 层以内**——超过 3 层，横向空间和人的短期记忆都会崩，成员会找不到自己在哪。

## 5.2 GET /plans —— 课题树

**权限**：按 `view_scope`

**Query**

| 参数 | 说明 |
| --- | --- |
| `dept_id` | 只看某部门的树（按**根课题**的部门） |
| `depth` | 展开层数，默认全展开，**上限 6**（与 5.1 的深度硬上限一致；原写 10 属笔误） |
| `include_progress` | 默认 `true`；关掉可减少计算量 |

**响应 200**——返回**森林**（顶层节点数组），每个节点内嵌 `children`：

```json
{
  "ok": true,
  "data": {
    "items": [
      {
        "id": 5, "title": "2026 招新", "owner": { "…MemberBrief…" },
        "dept": { "id": 2, "name": "运营部" },
        "due_at": "2026-10-01T18:00:00+08:00",
        "progress": { "done": 3, "total": 8 },
        "task_count": 2, "child_count": 2,
        "children": [ { "…同结构…" } ]
      }
    ]
  }
}
```

不分页——社团规模的课题数量（几十个）一次返回更实用，也省掉客户端拼树。

## 5.3 GET /plans/{id}

**权限**：按 `view_scope`

**响应 200**

```json
{
  "ok": true,
  "data": {
    "plan": { "…PlanBrief…" },
    "path": [ { "id": 1, "title": "顶层课题" }, { "id": 5, "title": "…" } ],
    "children": [ { "…PlanBrief，不含 children…" } ],
    "tasks": { "items": [ { "…TaskBrief…" } ], "total": 5, "page": 1, "size": 50 }

```

- `path` 是**面包屑**（从顶层到本级，不含自身或含自身由客户端决定，这里含自身）

## 5.5 PATCH /plans/{id}

**权限**：课题负责人 / 部门管理员 / 会长 / 副会长

字段全部可选：`title` / `desc` / `owner_id` / `due_at`

> ⚠️ **`owner_id` 不能置空**——同任务，课题必须始终有人负责。
> ⚠️ **`dept_id` 不可通过此接口修改**（子课题不存该字段；顶层若要换部门，用 5.6 的移动语义或单独确认）。
> ⚠️ **响应里的 `progress` 必须是真实聚合值**（2026-09-14 修订，见 `code-review.md` M-1）。
> 该字段与 `POST /plans` 的响应原先走的是"不算进度"的分支，序列化出来恒为 `total: 0 / done: 0`；
> 客户端改一次标题，进度条就归零——一个看起来像数据丢失的假象。
> 凡返回课题对象的地方（详情、创建、编辑、移动、幂等回放）一律取真实聚合值。

## 5.6 POST /plans/{id}/move —— ⚠️ 环形校验

**权限**：会长 / 副会长；部长 / 副部长限本部门

```json
{ "new_parent_id": 3 }
```

`new_parent_id` 为 `null` 表示**提升为顶层课题**。

**校验（按顺序）**

| # | 校验 | 失败错误码 |
| --- | --- | --- |
| 1 | `new_parent_id != id`（不能挂到自己下面） | `PLAN_CYCLE_DETECTED` (409) |
| 2 | `new_parent_id` **不能是自身的后代** | `PLAN_CYCLE_DETECTED` (409) |
| 3 | `new_parent_id` 存在且未删除 | `PLAN_NOT_FOUND` (404) |
| 4 | 提升为顶层时，需要确定 `dept_id` | `VALIDATION_FAILED` (400) |
| 5 | **目标部门也要判权限**（提升为顶层时带 `dept_id` 的情形） | `FORBIDDEN_NOT_IN_DEPT` (403) |
| 6 | **禁止跨部门移动**（换父节点与提升为顶层两条路都禁止） | `VALIDATION_FAILED` (400) |

> ⚠️ **校验 5 是 2026-09-14 补的 P0 缺陷修复（见 `code-review.md` H-3）**。
> 换父节点那条路先判了"目标父节点所在部门"的权限，但**提升为顶层那条路原先没有判**：
> 部长可以把自己部门的课题 `dept_id` 一填就"提升"到别的部门去。
> 现在两条路都判：先按操作真正落地的部门跑一次权限，再执行"跨部门禁止"的一致性检查。
> 顺序上权限在前——否则会先给出"v1 不允许跨部门"这种与调用者权限无关的提示。

### 环形校验的实现提示

**从目标父节点向上遍历到根**，而不是向下扫子树：

```
cur = new_parent_id
while cur != null:
    if cur == id:  -> 拒绝 PLAN_CYCLE_DETECTED
    cur = parent_of(cur)
```

向上遍历的深度通常远小于子树规模，且实现简单。**这是多级结构下最容易出的事故**——一旦成环，5.8 的递归进度聚合会无限循环并拖垮服务。

### 移动为什么不需要级联更新部门

因为 `dept_id` 只存在顶层（5.1 规则 A）。把一棵子树挂到另一个根下，它的部门**自动**跟随新根，无需 UPDATE 任何子节点。

## 5.7 DELETE /plans/{id} —— 上提一级

**权限**：部门管理员 / 会长 / 副会长

**语义：删除课题 P 时，对 P 的「直接子节点」执行上提，绝不级联删除。**

| 子节点类型 | 上提后 |
| --- | --- |
| 子课题 | `parent_id = P.parent_id` |
| 本级任务 | `plan_id = P.parent_id` |

**P 是顶层课题时**（`P.parent_id` 为空）：

- 子课题变为**顶层课题**，并**继承 P 的 `dept_id`** ← 因为 `dept_id` 只存在顶层，这一步不能漏
- 本级任务变为**独立任务**（`plan_id = null`）

**响应 200**

```json
{ "ok": true, "data": { "moved_plans": 2, "moved_tasks": 5 } }
```

> **为什么不做级联删除：** `v1-scope.md` 规则 9——任务承载着人的工作量记录，不能因为删一个容器就消失。
> 一次误删丢掉整棵子树，是这个设计里最不可接受的失败模式。
>
> 整个上提操作必须**原子完成**，不能出现"子课题提上去了、任务还挂在已删课题下"的中间态。

## 5.8 递归进度聚合

```
progress(P) = 
    done  = P 本级已完成任务数 + Σ done(子课题)
    total = P 本级任务总数   + Σ total(子课题)
```

**含所有后代任务**，不只是直接下挂的。

**实现提示（很重要）**：构建树时**自底向上一次算完**，不要对每个节点独立递归。

- ✅ 一次后序遍历，O(n)
- ❌ 每个节点各自递归 → O(n²)，课题一多就明显变慢

在 `GET /plans` 返回整棵树时，这个差别从"几十个课题"开始就能感觉到。

> `Plan` **不设 status 字段**——进度完全是派生的（`v1-scope.md` 规则 7）。
> 这样从结构上杜绝了「任务全完成了、课题还写着进行中」这类不一致，不需要靠人去维护。

# Part 7 · AI 能力（服务端智能接口）

> **状态**：2026-10-04 新增。本部分是 `/api/v1/ai/*` 的**唯一权威**——改代码前先改这里。
> **配套文档**：设计要求见 `llm-client-spec.md`；服务端落地步骤见 `llm-backend-guide.md`；
> 客户端接入见 `llm-frontend-guide.md`。

## 7.0 通用约定

| 项 | 约定 |
| --- | --- |
| 前缀 | `/api/v1/ai/`，**一律 POST**（上下文放请求体，避免把长文本塞进 URL） |
| 成功信封 | 沿用 §1.2：`{ "ok": true, "data": { ... } }` |
| **失败语义** | **永不返回 5xx**。模型不可用属「降级」，HTTP 仍 200，用 `data.source` 表达 |
| `data.source` | `model` = 模型给出的；`fallback` = 模型不可用、退回规则或历史统计；`none` = 连兜底都给不出。**⚠ 实现状态（2026-10-06）：服务端目前不会发出 `none`** —— 4 个接口在模型不可用（含「AI 未配置」）时**一律给得出规则兜底**，所以走 `fallback`。`none` 保留为契约里的第三态，客户端照常处理即可，只是现在收不到 |
| `data.note` | 可选，给用户看的一句话；`fallback` / `none` 时**必填** |
| 鉴权 | 与其它接口一致（`Authorization: Bearer`），401 / 403 语义不变 |
| 权限 | **一律经 `can(member, action, target)`**；禁止在 AI 链路里另写一套判定（会与 `perms.cj` 漂移） |
| 幂等 | **不做幂等键**——读语义的建议，重复调用无副作用（客户端也不要放进离线队列） |
| 超时预算 | 服务端单次预算 **20 s**（含重试）；客户端建议同样 20 s 上限 |
| 输入闸门 | 沿用 `limits.cj`：请求体 64 KiB、类型白名单、非 UTF-8 → 400 `INVALID_JSON` |

**为什么不用错误码表达模型故障**：§1.2 的分工是「HTTP 状态码给网络层、`error.code` 给业务层」。
模型不可用既不是网络故障也不是业务错误，而是**能力的暂时缺失**。走 `data.source` 降级，
客户端才能区分「没权限（403）」与「暂时给不出建议（200 + `fallback`）」。

## 7.1 `POST /ai/task-suggest` — 创建任务时的建议

**请求**

```json
{ "title": "筹备秋季招新", "desc": "可选", "plan_id": 12, "dept_id": 3 }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 任务标题 |
| `desc` | 否 | 任务描述 |
| `plan_id` | 否 | 所属课题，给了可参考该课题下的历史任务 |
| `dept_id` | 否 | 目标部门；不给则按创建者所在部门 |

**响应 `data`**

```json
{
  "owner": { "id": 7, "name": "张三", "dept": { "id": 3, "name": "宣传部" } },
  "due_at": "2026-10-20T18:00:00+08:00",
  "granularity": "建议拆成 2—3 个子任务：物料、场地、宣传",
  "reasons": ["张三近 3 个月按期完成率 92%", "宣传部当前在途任务 2 件，负载最低"],
  "source": "model"
}
```

- `owner` 用 `MemberBrief`（**不含手机号**）· `due_at` 为 ISO 8601 带时区（口径见 §1.8）
- `reasons` 是**给用户看的依据**，必须能对上真实数据；模型给的依据要经 schema 校验
- **权限**：与创建任务同权（`can(member, "create_task", …)`）
- **兜底**：按「本部门**在途任务数最少**」给规则建议，`source = "fallback"`
  > ⚠ **「历史按期率最高」这半条尚未实现**（`docs/ai-module-review.md` **F-9**）。
  > 实际实现在 `server/src/h_ai.cj` 的 `aiFallbackOwner`：**只比对在途任务数**，同档按 id 升序取。
  > `server/src/ai_schema.cj` 里也已注明这点。以下正文保留原设计意图，**以本条为准**。
- **数据源**：**内部历史数据为主**。联网信息只作可选增强——对社团任务价值有限，
  且会把运行绑死在第三方服务上（§5.1 d 条对"第三方不可用"有明确归责）

## 7.3 `POST /ai/retrospective` — 成效总结与延期归因

**请求**（`task_id` 与 `plan_id` **二选一**）

```json
{ "task_id": 42 }
{ "plan_id": 12 }
```

**响应 `data`**

```json
{
  "summary": "该课题 6 个任务已完成 5 个，整体按期率 83%。",
  "overdue": {
    "is_overdue": true,
    "days": 3,
    "causes": [ { "kind": "dependency", "detail": "等待宣传部物料交付" } ]
  },
  "suggestions": ["下次把物料准备前置到活动前 3 周"],

```

- `overdue.is_overdue` / `overdue.days` **必须**取自服务端既有派生量（`views.cj` 的
  `is_overdue` / `overdue_days`），**不得由模型生成**——否则与列表页数字打架
- `causes[].kind` 取固定枚举：`dependency` / `overload` / `granularity` / `scope_drift` / `external` / `unknown`

- ⚠ **本接口的价值全在归因与建议**：单纯报「是否延期」不必用模型（一句 SQL 的事）。
  实现时若只做查表，等于没做智能
- **兜底**：用既有派生量拼出**事实摘要**（不含归因），`source = "fallback"`

## 7.4 `POST /ai/ask` — 权限感知问答

**请求**

```json
{ "question": "我作为部长有哪些权限？" }
```

**响应 `data`**

```json
{
  "answer": "你可以创建/编辑本部门课题与任务、审批本部门新成员的分配……",
  "basis": [

} }
```

> ⚠ **`basis` 只有一种形状**：对象数组，元素是 `{ "kind", "ref" }`，`kind ∈ permission / data / doc`
> （与 §7.4 一致）。
> **2026-10-06 勘误**：本节实现里，**模型路径曾手搓成字符串数组** `["permission: …", "data: …"]`，
> 而降级路径是对象数组 ⇒ **同一个字段、同一份 `source=fallback`，形状却取决于「AI 配没配」**，
> 客户端无法可靠消费（前端据实报障）。已修正，并在 `tests\ai-e2e.ps1` 里对
> `agent` / `agentloop` / `agentbad` **三条剧本各加断言钉死形状**。

**工具白名单是静态表**（`server/src/ai_tools.cj` 的 `aiToolSpecs()`）：
`list_my_tasks` · `task_detail` · `dept_stats` · `list_dept_open_tasks` · `list_pending_members`。
**模型不能新增工具，也不能改参数语义。**

> **写工具（P2 起）**：白名单里另有 **`set_my_task_status`**（改**自己负责**的任务状态，L1）。
> 它**不在循环里直接执行** —— 模型提出后，本接口**只返回 `proposal`**（含确认令牌），
> 由用户在界面上确认后走 **§7.9** 执行。
> **L3（删任务、停用成员、移交会长、重置口令等）永久排除**，且不是配置项。

| 约定 | 内容 |
|---|---|
| 权限 | 每个工具声明一个所需的 `can()` 动作；`dispatchAiTool` 内部**只**用 `can()` 判定（spec §5.6 T6）。判定失败即**不执行** |
| denied 的呈现 | `allowed=false`，且 `payload` 是**中性文案** —— **不告诉模型缺哪个权限**，避免这个接口被当成权限探测面 |
| 上限 | 轮数 ≤ **4**；总预算 **20 s**（**整个请求共享**，不是每轮各给一份）；单次回灌 ≤ **2 KB**（防 prompt 膨胀） |
| 审计 | 每次工具调用都落审计（**denied 也落**）：`ai_tool … tool=<名> allowed=<bool> round=<n>`。**不记**参数与结果全文 |
| 失败语义 | 与 Part 7 一致：**永不 5xx**。模型中途不可用时，`answer` 退化为**已查到数据的直接拼接**（兜底不为空） |
| 升级路径 | 写操作**已按 P2 落地**：`set_my_task_status` → 只回 `proposal` → §7.9 确认执行。再加写工具时：往白名单加条目（`write: true`）+ 在 `aiToolPropose` / `aiToolExecute` 加分支即可 —— 权限门 / 未知工具拒绝 / 审计 / 截断都是共用的 |

## 7.9 确认并执行 AI 提议（**写操作**，2026-10-06 新增）

> **排版说明**：同 §7.8 —— 本节排在 §7.5 之前，因为本节落地时 §7.5（邀请风控）尚未实现
> （**§7.5 现已实现**，见该节）。编号顺着 §7.8 取 7.9，物理位置不重排以免破坏既有引用。

`POST /api/v1/ai/agent/confirm` —— 执行一个**已由用户在界面上确认**的提议。

### 为什么写操作要拆成两段

读操作可以在一次 `/ai/agent` 请求里直接执行；**写操作不行**。
拆分后，**模型永远不能单次往返就产生副作用**：

```
① POST /ai/agent          → 模型只产出「提议」，服务端**不执行**，返回 proposal + 令牌
② （前端展示 diff，用户点确认）
③ POST /ai/agent/confirm  → 服务端**重新校验**后执行
```

### 请求

```jsonc
{ "token": "ap_7f3c9e12…" }     // 来自上一步 data.proposal.token
```

### 响应

```jsonc
{ "ok": true, "data": {
    "tool": "set_my_task_status",
    "resource_id": 501,
    "summary": "已把「招新物料」的状态改为 done"
} }
```

### 失败**全部显式**（此节与 Part 7 其余接口**有意分家**）

Part 7 的读接口铁律是「永不 5xx；模型不可用就 `200 + source=fallback`」。
**写操作不适用** —— 用户必须知道"没写成"。

| HTTP | `error.code` | 场景 |
|---|---|---|
| 404 | `AI_PROPOSAL_NOT_FOUND` | 令牌不存在 / **不属于当前用户**（key 里含 actorId） |
| 409 | `AI_PROPOSAL_USED` | **已消费**（重放）—— 不会二次执行 |
| 410 | `AI_PROPOSAL_EXPIRED` | 超过 **5 分钟**窗口 |
| 409 | `AI_PROPOSAL_EXEC_FAILED` | 执行被业务规则拒（如进入 `blocked` 却没给 `blocker`）；**此时不标记已消费**，用户可重试 |

### 六条安全属性（对应设计目标 G1–G6）

| | 落地方式 |
|---|---|
| **G1 令牌绑定「谁 + 做什么 + 什么参数」** | key = `idemKey("ai_prop", actorId, token)`；提议正文（tool + args）存在 `idem.payload`，**客户端只能传 token，不能传参** |
| **G2 一次性** | `used_at` 在**与执行同一个锁内**标记 ⇒ 单次消费是原子的 |
| **G3 执行时重新授权（TOCTOU）** | 执行那一刻**重新**跑 `can()`，不复用提议时的判定 |
| **G4 幂等** | 重复提交同一 token ⇒ 命中 `used_at` ⇒ 409，**不二次执行** |
| **G5 参数只能填槽位** | 提议阶段预筛 + 执行阶段由共享的业务核心**权威**校验（见 §7.6 的 T3） |
| **G6 确认的是服务端 diff** | `proposal.diff` 由服务端读当前值算出来，**不是模型的措辞** |

### 其它约定

- **不调模型**：confirm 没有句柄、没有出站请求 ⇒ **不消耗 AI 配额**，也不做 rate check。
- **过期自己判**：`idem` 的 `IDEM_TTL` 是 24 小时，而确认窗口是 **5 分钟** —— 靠 `idemHit` 的 TTL 会让令牌活一整天，那是安全问题。
- **审计**：`ai_tool_confirm … tool=<名> token=<前 8 位> resource=<id>`。**只记令牌前 8 位**，日志里的人拿不到完整令牌。
- **令牌来源**：复用既有会话令牌那条路径（`randHex(32)`），**不自己 `Random()`**。

## 7.5 邀请风控（**不单独开接口**）

> ✅ **实现状态（2026-10-06）：已实现。** `server/src/ai_risk.cj` +
> `handleMemberPending` 的下发；前端（`PendingRisk` / 角标 / 三档配色）已就位。
>
> **三条实现口径（与本文原描述不同，以这里为准）**：
> 1. **不做「低风险自动通过」** —— 分档**只影响排序与呈现，不影响审批动作**，
>    每一笔都要人点。按模型判断自动批准入社是**安全决策**，且违反模块铁律
>    「模型输出不得直接成为写库值」（spec D4）。
> 2. **懒算 + 内存缓存**（进程级、按 member id）：打开列表时算，**每个申请人只花一次
>    模型调用**；**不在注册流程里算**（注册必须快）。单次刷新最多为 5 个申请人调模型。
> 3. **IP 不落库** —— 下面举例的「同一 IP 短时间内 5 次申请」需要把 IP 存进 `Member`，
>    而它没有该字段（IP 只用于注册时的内存限流 `reg_fail`）。改用**现在就有**的三个信号：
>    申请时间的聚集度（`joined_at` 窗口）/ 有无招募链接（`dept_hint>0`）/ 队列长度。
>
> 另外：**模型给的分档若没有 `reasons`，一律不采信**、回落规则兜底 ——
> 一个没有依据的「高风险」比不报还糟（用户会去处理一个不存在的问题）。

在既有 `pending` 审批流内部对申请做**风险分档**，结果作为待审批列表的一个字段暴露：

```json
{ "risk": { "level": "high", "reasons": ["同一 IP 短时间内 5 次申请"], "source": "fallback" } }
```

- `level` 取 `low` / `medium` / `high`
- **不要**做成「自动通过」的开关——那只是 `if`，不是智能。要做成**分档处置**：
  低风险自动通过 / 中风险通过但标记待抽查 / 高风险转人工
- 该字段出现在 `GET /members/pending` 的每条记录上（Part 3 该接口的响应结构相应扩展）

## 7.7 客户端契约要点（详见 `llm-frontend-guide.md`）

- `source` **必须透传到 UI**，三态呈现要能区分（`fallback` 需弱化样式并标注「依据历史数据」）

- 三态都不能阻塞主流程；`none` 时留一句「暂不可用」，不放骨架、不留空白
